# agent-hub-host

## Purpose

`@dineug/erd-editor-agent-hub-host` is the editor-window side of the document hub `agent-hub` specifies, on Node: the pipe a window listens on, serving one connection (hello, authorization, routing, framing), path authorization over the real file system, the lock file a window writes and the dead windows' locks it sweeps, and the hub's lifecycle as the host's state changes. It came out of `vscode-extension` so the Obsidian plugin could serve the same hub. Each host keeps its document side — `vscode-extension`'s registry and handlers over its webviews, `obsidian-plugin`'s over its tabs — and hands it in as effect services: `HubHost` (its name, whether it wants a hub, its root folders, the events that change them), `HubDocuments` (the open documents the lock lists) and `HubHandlerService` (every request after `hello`). The join-window rules (`joinWindow.ts`) and the ERD file rules (`documentRules.ts`) live here too, so an agent meets one behaviour in either editor. `private: true`, built for Node; `effect` and `@effect/platform-node` are its peers.

## For AI Agents

### Working In This Directory

- **Two sides, one hub.** This package owns what a connection meets before a document is involved, and the lock that advertises it; a host owns its documents. A host composes one runtime: `withDocumentHub(<its documents layer>, documentHubLayer)`, the hub provided with the host's `HubHandlerService`, `HubHost` and `HubDocuments` layers, `nodeHubServices(version)` and `nativeFileSystemLayer` (`vscode-extension`'s `src/hub/index.ts`, `obsidian-plugin`'s `src/hub/runtime.ts` and `src/main.ts`). No editor API may reach this package: `imports.test.ts` lets shipping code import only its own modules, `node:net`, `node:fs`, `node:fs/promises`, `node:os`, `node:crypto` and `node:path` (never a bare builtin name), effect's named entries, `@effect/platform-node/<Module>` and `@dineug/erd-editor-agent-hub`, and it reads `require` and dynamic `import` calls as imports.
- **`HubHost`.** `ide` is what the lock's `ide` and every `hello` answer carry (`vscode`, `obsidian`), and what the MCP server names the editor by. `isEnabled()` may throw, as reading a broken setting does: the hub logs it and keeps the state it had. `folders()` gives the host's roots, each taken by its native real path; a folder whose realpath fails stays as given. The two events stay apart: an enabled change runs through `enqueueListen`, counted in `listensAhead` because it may listen, a folder change through `enqueue`. VS Code maps trust and `dineug.erd-editor.agentHub.enabled` to the first and workspace folders to the second; Obsidian maps its Coding agents setting to the first and has no folder event, a vault window having one root.
- **`HubDocuments`.** `setPublisher(publish)` must publish the documents open now at once, then again on every change. The hub hands the publisher over at the end of its acquire without awaiting that first publish, which queues behind the startup task, so a window disposed in the same tick binds nothing and writes no lock.
- **The hub never throws at the editor.** Every failure goes to `console.warn` under `[erd-editor hub]` (`HubLogger`, the prefix byte-for-byte as the extension always wrote it). `withDocumentHub` builds the host's documents first, which cannot fail, then the hub on them under `Layer.catchCause`, which logs `could not start the document hub` and leaves the documents serving every editor; finalizers run hub first. One runtime of two layers, not one layer, since a hub that failed would take the documents' IO down with it, and not two runtimes, which a host would have to order and time out apart. Once built, the hub's state changes run on one promise queue whose `.catch` logs. It listens before its lock names the pipe and rewrites the lock to `hub: false` before closing the pipe. A hub that cannot listen still writes a `hub: false` lock (empty `pipe`), because a window with no lock invites headless writes over its open editors.
- **The publisher** queues every lock write in order but resolves at once while the startup task or an `apply` is queued ahead, the tasks that may listen: an editor opening never waits on a hub coming up, a listen that does not return or a hub that failed. Once the hub is up it waits for the rewrite that lists the document, so an agent resolving the file finds this window's lock before the editor takes an edit, but for `PUBLISH_WAIT` (one second) at most, after which it logs and lets the editor open: a task ahead of that rewrite can stall for good (the realpath of a folder just added or of a listed document on a stalled mount, or a lock write) and every later rewrite queues behind it. A stalled task or a listen that never returns also holds `close`. `DocumentHub.test.ts` pins the fast path, the wait and the warning.
- **`close` and `releaseSync`.** `close`, the layer's finalizer, runs after the queue: it deletes the lock, then closes the pipe and deletes the socket; VS Code's `deactivate` awaits it through the runtime's dispose. `releaseSync` is for a host whose process or page goes down without awaiting `close` — Obsidian's `quit` event and `pagehide` (a window closing, reloading or quitting, where `onunload` never runs). It deletes the lock, its temp file and both socket files `socketFilePaths` names through `removeFileSync` (`unlinkSync`) before it returns, lets go of the host's events and marks the hub closed so no queued task writes the lock again; a write already on its way to disk when it ran is deleted again when its rename lands (`keepUnlessReleased`). It is idempotent, and a `close` may still follow.
- **An earlier hub of the same pid.** Before it listens the hub removes any socket file at its pipe path: a dead process with this pid can have left one, and so can an earlier hub of this very process — an Obsidian reload, or the plugin disabled and enabled again or updated, which keep the renderer pid. Without it `listen` fails `EADDRINUSE`. A host whose new instance can start before the old one's `close` finished must serialize the two, since both use the same paths (Obsidian keeps the closing promise under a `Symbol.for` key and its next instance awaits it).
- **The lock on disk.** `write` removes a leftover temp file (a `writeFile` keeps an existing file's mode), writes `<pid>.json.tmp` with `LOCK_FILE_MODE` (`0o600`) and renames it over the lock, so the lock is never readable by others; the directory is made `LOCK_DIR_MODE` (`0o700`). A failed write logs, answers `false` and is retried on the next state change. At startup `cleanStale` reads the directory through agent-hub's `readLockDirectory` and `selectHub`, its own pid filtered out, and deletes the lock, temp file and both possible socket files of every `stale: 'dead'` pid; a live pid's malformed lock is left alone. `isAlive` takes a pid for dead when signal 0 fails, but for `EPERM` on Windows: there it is an elevated window of this user, and deleting a live window's lock sends agents to write its files behind the editor. On POSIX `EPERM` is another user's process, which a lock in this user's home never names, so a crashed window's pid reused by a root daemon still counts dead and its lock is swept. The MCP server's `isAlive` reads the same way. Pids name windows only within one pid namespace: a host in a sandbox with its own (Flatpak) must start no hub, as the Obsidian plugin does, since its sweep would take every window outside for dead and a sweep outside would take its lock for dead.
- **Path authorization** (`authz.ts`) resolves the real path, then leaves the folder and document rule to agent-hub's `authorize` Effect. It climbs past a path's missing tail only when `realPath` fails `NotFound` and `HubEnvironment.lstat` fails `NotFound` too. A dangling symlink, any other `realPath` error, or a `..` behind a missing directory is refused as `outsideWorkspace`: `realpath` cannot see where a write through it would land. `lstat` stays on `HubEnvironment` with its raw errno rather than move to `FileSystem.readLink`, whose `PlatformError` folds EINVAL, EPERM, EIO and ENAMETOOLONG all into `Unknown` and would read a file the hub cannot examine as one that exists.
- **Every real path the hub takes is the native realpath's**: the lock's `workspaceFolders` and `documents`, authorization, and each host's registry keys and `listDocuments` resolve through `nativeFileSystem.ts`, `NodeFileSystem` with `realPath` on `node:fs/promises`' `realpath`, as `mcp-server` resolves an agent's path (its `io/fileSystem.ts`). `NodeFileSystem`'s own is the JS `fs.realpath`, which keeps the spelling it is given: on macOS a differently cased path, and a folder handed over in NFC whose name the disk holds in NFD (as Finder writes Korean names), came back as given while the MCP server's came back as on disk, so `selectHub` found no lock covering a document open in the window, answered headless where a `hub: false` lock should have blocked, and a write landed under the editor. When the native realpath fails, `NodeFileSystem`'s runs for the reason tag. `nodeHub.test.ts` holds both spellings to the disk's through `realpathOrSelf`; `vscode-extension`'s `nodeRegistry.test.ts` does it through its registry's keys.
- **Unit specs must not provide the node layers** (`hubEnvironmentLayer`, `hubListenerLayer`, `NodeFileSystem.layer`, `nativeFileSystemLayer`, or `nodeHubServices`, which carries them), here or in a host — build the memory layers of `src/__test-utils__/hubLayers.ts` (or the host's own) instead, or they bind a socket and write a lock under the real home directory. The exceptions are `src/services/nodeHub.test.ts` and `src/services/netSocket.test.ts`, which run the node layers (and `authorizePath` on them) against a `mkdtemp` directory.
- **Frames.** `serveConnection` reads through agent-hub's `decodePeerToHubFrames`: a request `PeerToHubMessage` takes is served as decoded, fields it does not know dropped, and a frame it refuses is read by hand as every frame was before, so it keeps its answer — a hang-up for a first frame that is no hello, `unauthorized` or `protocolMismatch` for a hello whose token or protocol is off, `badRequest` with its id for an unknown method or a missing `path` or `actions`, admission for a `hello` without `client`, under the name `''`, and the handler for `listDocuments` without params, with `{}`. After `hello`, a frame without an id is logged and skipped. A token of another length is refused at once; one of the same length is compared character by character to the end, whatever the first difference. Notifications go out through `encodeHubNotificationFrame`; a response is `encodeFrame` of what the handler returned, and one JSON cannot frame answers `internal`. A `HubRequestError` answers with its code, any other failure or defect with `internal`.
- **Order within a connection.** Frames pass authorization in arrival order, and an `applyActions` holds the frames behind it until it is answered, so one peer's edits land in its own order; any other request is left running and does not hold back the frames behind it. `serveConnection` reads in a fiber of its own and serves from a queue, so a peer hanging up marks the connection closed at once rather than behind the request in flight; that request is forked detached, so a save or an open already writing runs to its end and only its response is dropped. A peer's id is taken when its `hello` passes, so a refused peer consumes none. Closing the serving scope destroys every accepted connection, including one accepted in that very tick, which is also what lets `server.close` settle.
- **Its two halves are apart** — `Socket.readerString` for the frames it reads, a fiber of its own draining the outbound queue through `socket.writer` — rather than one duplex `Socket.toChannelString` channel, which couples them: a write failure there fails the read side too, and a `CloseEvent` offered after it can no longer reach the socket. Apart, a write that cannot reach a peer is logged and leaves the connection serving, and a hang-up still destroys the socket of a peer whose frame could not be read, where a refused `hello` only ends the write side. The connection waits on that writer fiber before its scope closes, so the last frames still go out. `drain()` resolves once every frame queued before the call has been written, refused or not, or once the connection stopped writing: Obsidian's plugin, turning off, sends `documentClosed` to its peers and awaits their drains (for one second at most) before it disposes the runtime and the listener destroys the sockets.
- **`fromNetSocket`** is this package's own adapter, because platform-node's `NodeSocket` re-exports `ws` into every host's bundle. It attaches its no-op `error` listener where the connection is accepted, not inside the reader: a reset peer emits `error` right before `close`, and a socket nothing has read yet would throw it in the host instead. It sets `setEncoding('utf8')`, a streaming decoder, so a character split between two reads survives.
- **The join window** (`joinWindow.ts`) holds rules both hosts must apply alike, over their own view key (`vscode.Webview`, an Obsidian tab). A change notes the ready views it reached, copied at that moment: each owes one replica save. The wait ends once every one of them saved or closed (`dropRecipient`) and at least one save came, so a view that becomes ready later never holds it open and its save settles nothing by itself, while a change that reached no view still waits for one save. A save sooner than `REPLICA_DEBOUNCE_MS` after a peer batch was sent cannot hold it and is not counted; a relay bounds nothing, since it can arrive after its replica saved. `waitForQuiet` answers `true` at once with nothing pending and `false` at its cap. `filterJoinQueue` drops what the snapshot holds (a version up to `snapshotVersion`) and every version-less action, since a relative move applied twice moves twice. `hasChangeAction` counts every action but the six LWW and tracker types as a change, so a stranger only costs a wait. `drainJoinQueue` ends a window: it runs the captured batches through `filterJoinQueue`, logs a drop (`dropped <n> queued actions joining <path>: …`) and hands back those plus every batch queued after the capture, whole, in order; each host's `endJoinWindow` delivers them once its peer is still the one that joined. The hosts' specs pin where each calls them.
- **`documentRules.ts`** is the one list of what the hub serves and the refusal of anything else: `badRequest` `<path> is not an ERD file; the hub serves .erd, .vuerd, .erd.json, .vuerd.json only`, the path lowercased first, as the MCP server's own check does. `vscode-extension` builds its activation glob from `ERD_FILE_EXTENSIONS` and asserts the list against its manifest; the Obsidian plugin filters its vault listing with `erdFileProblem`. `OPEN_READY_TIMEOUT_MS` and `SAVE_QUIET_CAP_MS` are the two waits every host's `openDocument` and `save` use. Every refusal an agent can meet in both hosts in the same situation is a constructor here, pinned once in `documentRules.test.ts`, so the hosts cannot drift apart; one that names the editor takes its name (`editorCouldNotOpen('VS Code', …)`), and a situation only one host has (the read-only views, Obsidian's plugin turning off) keeps the host's own words.
- **Built for Node.** `node: true` makes `defineLibraryConfig` target `node22` and keep every builtin a bare import, with and without the `node:` prefix; without it a builtin resolves to Vite's empty browser stub with only a warning, and `net.createServer` is undefined at runtime. `createExternal` keeps `dependencies` and `peerDependencies` bare too. The `@dineug/erd-editor-agent-hub` import must stay bare in `dist/`: a copy inlined here would give a host two `HubRequestError` classes, and every refusal its handlers throw would fail `toHubError`'s `instanceof` and answer `internal`. The string `createLibraryTasks` must not appear in `vite.config.ts`, not even in a comment: `check-task-inputs.mjs` tells the two library helpers apart by it.
- **`engines.node` (`>=22.12.0`, the root's floor)** binds the bundles this package is inlined into: the extension's, on the VS Code 1.101 host (Node 22.15), and the Obsidian plugin's `main.js`, on the Node of the Electron its installer brought (Node 22.22.1, Electron 39.8.3 under the Obsidian 1.12.7 installer, measured 2026-09-26; an older installer was not checked).

### Common Patterns

- Service tags are keyed `@dineug/erd-editor-agent-hub-host/<Name>`. A module with a node or memory implementation exports it as `layer`, which the barrel renames (`lockFileLayer`, `documentHubLayer`, `hubEnvironmentLayer`, `hubListenerLayer`, `hubLoggerLayer`, `nativeFileSystemLayer`); `services/HubHost.ts` holds the three tags a host provides itself (`HubHost`, `HubDocuments`, and `HubHandlerService`, keyed `HubHandler`) and no layer.
- Every service a host provides is a plain object shape (`HubHostShape`, `HubDocumentsShape`, `HubHandler`), so a host adapter is `Layer.succeed` or a `Layer.effect` over its own registry.
