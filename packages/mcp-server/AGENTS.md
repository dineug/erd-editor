# mcp-server

## Purpose

`@dineug/erd-editor-mcp` is the stdio MCP server a coding agent runs with `npx -y @dineug/erd-editor-mcp`, published to npm by hand on its own version line. Its 77 tools are nine session tools, one per `actionTools` entry (67 in `src/tools/registry/`, each with a leading `path` argument) and `erd_batch`, several as one edit. Each document gets one long-lived agent peer (`createPeerStore` from `@dineug/erd-editor/peer.js`), editing live through the hub (`packages/agent-hub` protocol) that ERD Editor runs in a VS Code window, an Obsidian vault window or a JetBrains IDE, or headless on the file. MCP is effect's `McpServer` over stdio (`effect/ai`); sessions, discovery, the hub client and the file system are effect services.

## Rules

### Process and stdio

- **Write only the protocol to stdout.** A stray `console.log` corrupts the client's stream, and effect's default logger and `runMain`'s error report write there. So `ServerLayer` and `serve` provide `StderrLogger` (a cause appended with `Cause.pretty`), `runMain` runs with `disableErrorReporting: true`, every diagnostic is an Effect log call, and fibers a session forks inherit the logger of the call that made them.
- **Wrap the registrations in `layerStdio`.** It interrupts its building fiber at stdin's end; a `Layer.mergeAll` member's fiber is gone after the build, and the server would never stop. So `layerWithSessions` provides it around `ToolsLayer`, and `serve` runs the layer in a child fiber: stdin's end exits 0, a signal 130, a failure 1.
- **Filter stdin through `MessageStdin`.** Effect's decoder skips, unlogged, a line `JSON.parse` refuses (a blank one included) and a value that is not an object, and takes a non-string `method` for an unknown one (-32601 when it carries an id). It throws on a malformed `headers`, losing the chunk's rest and reading on 500 ms later (measured 2026-10-03, effect 4.0.0). A client's `Eof` among the RPC layer's `@effect/rpc/` methods stops every answer. `MessageStdin` cuts stdin on `\n` and passes only the lines `isMessageLine` takes: JSON objects or arrays of them, with `method` absent or outside that namespace and readable `headers`. It logs the rest but blank lines, and a line stdin never ends is never passed on.
- **Take the client name per request.** `McpSchema.McpRequestContext`, a dependency of every tool, carries `clientInfo`, and `SessionManager.rememberClient` keeps the first name seen. A peer made before any name, or with an empty one, is `DEFAULT_CLIENT_NAME`.
- **Take the platform from layers.** `SessionManager.layer` takes `HubDiscovery.layer` and a `Platform` (`FileSystem`, `FileStats`, `FileAccess`, `Path`, `ProcessInfo`, `HubConnector`): `NodePlatform`, or `createMemoryHost().layer` in specs. The manager captures clock and platform at build, so specs drive calls and the sweep on one TestClock.

### Tools on the wire

- **Use a toolkit unless answering plain text.** 73 tools are effect `Tool`s in `SessionToolkit` (5), `EditToolkit` (67) and `BatchToolkit` (1), registered with `McpServer.registerToolkit`, so effect lists, answers and decodes them. The read tools use `McpServer.addTool`, since a toolkit would send their text as a JSON string and again as `structuredContent`; `addTool` decodes nothing, so they decode with `onExcessProperty: 'error'` and fail with `McpSchema.InvalidParams`.
- **Register in sequence.** `Layer.mergeAll` would build concurrently, so `ToolsLayer` registers session toolkit, read tools, edit toolkit and batch toolkit in turn. `tools/list` reads `erd_list_documents`, `erd_open_document`, `erd_save`, `erd_undo`, `erd_redo`, `erd_read`, `erd_list`, `erd_get`, `erd_list_checks`, the registry's, `erd_batch`.
- **Speak three dated protocols.** `PROTOCOLS` (2025-06-18, 2025-03-26, 2024-11-05) answer a malformed argument with -32602; a later client gets 2025-06-18. The older two drop `outputSchema`, `structuredContent` and top-level input `additionalProperties` (nested ones stay); 2024-11-05 also drops annotations.
- **Some answers are effect's own.** Before `initialize` every request but `ping` gets -32603, unlogged; an early `ping` gets an empty result. `initialize` offers `logging` and `completions`, so `logging/setLevel`, `resources/list` and `prompts/list` are answered, and an unlisted tool gets -32602 (`Tool 'x' not found`), as MCP 2025-06-18 says (`server.test.ts`, `toolSurface.test.ts`).
- **Decode strictly, except in session tools.** Edit tools and `erd_batch` are `Tool.Strict` (`validateToolArgs` checks each operation's arguments as it runs), and read tools refuse excess properties. A bad argument is -32602 and touches no session, deliberately unlike the SDK-based server, which dropped unknown ones. The five toolkit session tools keep that server's meaning: an unknown key is ignored, and a malformed or missing argument is an `isError` refusal, code `invalidArgs`, message `Invalid arguments for tool <name>: …`. A toolkit tool with a schema decodes before its handler and answers -32602, so `erd_open_document`, `erd_save`, `erd_undo` and `erd_redo` are `Tool.dynamic` tools listing `toolInputSchema` of their `SessionParams` struct (the listing unchanged), and their handlers decode it. `erd_list_documents` takes `Schema.Record(Schema.String, Schema.Unknown)`, since a parameterless tool refuses every key. `toolSurface.test.ts` pins all three answers.
- **Keep the SDK-based server's result bytes.** Success schemas declare keys in emission order, so the text block matches; 2025-06-18 clients also get `structuredContent` and an `outputSchema`. A refusal is `ToolRefusal`, a struct written whole as `isError` text; read tools write their own. `result.test.ts` pins the bytes against that server's two writers. One key is new since: a headless edit, batch, undo or redo says `saved: true` after `mode` (an owner decision of 2026-10-23), since agents read a headless edit as one still waiting for `erd_save` and called it or told the user to save; `SERVER_INSTRUCTIONS` names the key.
- **Hints are MCP defaults with two exceptions.** The five reads set `readOnlyHint` (MCP reads their default `destructiveHint: true` only beside `readOnlyHint: false`); tools that neither remove nor import, `erd_batch` aside, set `destructiveHint: false`.

### Prose an agent reads

- **Write agent-facing words in `tools/copy.ts`, in English.** The registry stays machine-readable, so wording and length are managed in one place. Agents get nothing else (`files` publishes `dist` alone), so a rule for them goes in `SERVER_INSTRUCTIONS`, a description or a result note (`erd_batch`'s `undoNote` answered a misreading), never in this file or the README.
- **Give each tool and argument its prose.** `copy.exhaustive.test.ts` fails on missing prose and on unused entries. An argument with a tool-specific meaning (`value` always) gets that tool's entry.
- **Warn about older editors in fixed sentences.** The hub tells a peer nothing of what an editor supports.
  - `OLDER_EDITOR` ends the referential action prose (eight texts): an extension or plugin released before referential actions ignores the setting, losing a live edit while the tool reports success, so the user should update it. The owner chose to say so and never refuse (2026-10-02); a hub capability signal is separate work.
  - `OLDER_EDITOR_GROUPS` ends six of the seven table group tools: an editor released before table groups ignores the edit and drops every group on save (the owner's call to ship groups before a parser that keeps unknown fields).
  - `OLDER_EDITOR_GROUP_MOVE` ends `erd_move_table_group`: that editor reduces the `table.move` sent beside `tableGroup.move`, so only the tables move.
  - `OLDER_EDITOR_GROUPS_IMPORT` ends `erd_import_dbml` and comes next to last in `erd_import_json`, which bring groups.
  - `OLDER_EDITOR_DICTIONARY` ends the nine dictionary tools, the three that set a logical name or a domain, `erd_derive_physical_names` and `erd_import_json`, whose document brings them: an editor released before dictionaries, logical names and domains ignores what the edit writes of them and leaves them out when it saves. A table or column rename needs none, since that editor applies the rename and ignores the flag beside it. The four schema imports need none either, since their parsers give no logical name and they keep the dictionaries as they are.
  - `erd_set_ddl_script`'s description ends on a sentence of its own, not a constant: an extension or plugin released before the Schema SQL scripts neither shows nor keeps them, so the user should update it.
  - All are pinned and checked for a release number alike.
- **Keep descriptions short.** Every agent reads `tools/list` first. `toolSurface.test.ts` logs its bytes, gating nothing (fewer under the older protocols), up from the SDK-based server's 40,821 because toolkit tools list an `outputSchema`.

### Reads

- **Read in two sizes.** A 55 table, 1,233 column schema (`data/YOUNGCART5.sql`) snapshots to 300,387 characters, too much for one result; its `erd_list` is 10,988 and `erd_get` of its widest table, 172 columns each with its logical name, domain link and derived flag, 41,204, which comes whole with a note (measured 2026-10-20).
  - `erd_list` gives the settings without the scripts, which only the snapshot and the scripts format give, so a page never spends its room on them. It gives the counts (`tableCount`, since an agent miscounted 55 tables, and `wordCount`, `termCount` and `domainCount`) and pages of tables, then, unsearched, table groups (each by its stored rect, with `tableCount`), memos, domains, terms and words, one offset running through all six (the owner's call on the dictionaries' order, 2026-10-20). Entries come by id with what placing takes: position, size, column count, `groupId` only when grouped and `logicalName` only when set. Each table brings its indexes. A dictionary row comes by what a name takes of it: a word's `name` and `abbreviation`, a term's `name`, `physicalName` and `domainId`, a domain's `name` and `dataType`.
  - `erd_get` gives whole entities by ids (`tableGroupIds` with their tables, `wordIds`, `termIds` and `domainIds` with every field) or `tableNames`, unknown ones under `missing`.
  - `erd_read` gives the whole document, or the DDL and held foreign keys of `tableIds`, `tableNames` or `groupNames` (any case, joined). A relationship stays when its child end is selected.
  - `erd_list_checks` gives what the editor's check sheet lists (`listDictionaryChecks`, an owner decision of 2026-10-23), filtered by `level` and by `tableIds` or `tableNames`, which leave the dictionary rows out, a page at a time (`limit` 100 by default, `nextOffset`, a `note`) that stops where one read is full, and `counts` of each code over every page. Each check carries its target's names (a column's table, a logical name), so fixing one takes no `erd_get`; a document with no dictionary row says nothing is checked.
- **The sql format takes `statements`, `header` and `logicalNameAsComment`.** `statements`: `create` (default), `ifNotExists`, `recreate`; `header`: `none` (default), `use`, `createAndUse`; `logicalNameAsComment`: `false` (default), or `true` to write a table's or column's logical name where its comment is empty, as the Schema SQL tab's switch does. `createSchemaSQL` resolves them per database as the Schema SQL tab does, never refusing (`createAndUse` writes `use` on Oracle, `use` nothing on PostgreSQL, SQLite none; a logical name goes where each vendor writes a comment); other formats refuse them, `false` included. Only the whole document's DDL carries the `before` and `after` scripts, so a large script never blocks the tables.
- **The scripts format gives the scripts alone.** It answers `{ before, after }`, `''` while unset, as the snapshot's `ddlScripts` always does, so an agent reads one before `erd_set_ddl_script` replaces it whole (the owner's call on 2026-10-07). Only scripts alone over `MAX_READ_CHARS` refuse it (`tooLarge`), which says no read gives them in parts. Sql arguments are `invalidArgs`, and no lock touches scripts.
- **Answer at most `MAX_READ_CHARS` (40,000 characters).** Claude Code sets a result over 50,000 characters aside in a file, which an agent with only these tools cannot read: 48,000 characters of DDL or Korean came through, 52,000 did not, so it counts characters (measured 2026-09-24). Before the budget a 400 table `erd_list` ran 99,000 characters, and the agent stopped without a table name. Session notes, a few hundred characters, ride outside the budget.
  - A larger single entity still comes: whole from `erd_get` with a note, alone on an `erd_list` page with what of its relationships and indexes fits, the note counting the rest by the table's id. Only a table name of tens of thousands of characters could still pass the bound.
  - `erd_list` pages (100 by default, `nextOffset`, a `note`), searches (`query`: words in table and column names, logical names and comments, in any case, ranked by how many words a table name or logical name holds, then by where they were found; never dictionary rows, the owner's call of 2026-10-20) and lists names (`namesOnly`, 2,000 an answer). The unsearched list goes by document order and search by rank, so a page boundary moves when tables are added or removed between calls.
  - `erd_get` names what did not fit in `notReturned`, refusing (`tooLarge`) only when the ids alone overflow; `erd_read` refuses with `tooLarge` and says how to narrow.
- **Give each relationship on one page.** Its table with fewer relationships owns it (ties to the later), and it comes on that table's page, so unsearched pages give it once however cut. Carrying every touching relationship made a 268,919 character page for a tenant table 2,000 others refer to. A page that filled with tables before the relationships to other pages lost them from both pages. In a search the found table owns it.
- **Read only what the file form keeps.** Ids come from `doc.*Ids` and `columnIds`, never collection keys, since removed entities stay as LWW tombstones. `liveRelationships` (both tables live) and `liveIndexes` (on a live table, each index with the columns its table lists) leave out what a crossing removal orphaned, in the snapshot, `erd_list` and its counts, and `erd_get`, which names them under `missing`, as the json and sql formats do. A link to a domain the document does not list reads `''`, as the file form writes it, though the peer keeps it, so an undo of the removal brings it back.
- **Size tables as the sort does.** `measureTableSize` from `peer.js` with `defaultToWidth` (10 px a character) gives the sort's box, measured on copies, so reads before and after a load agree; the height is exact and the width approximate, wide for Latin text. Canvas widths are per replica, so a live session would need a bridge command for them.

### Batches

- **`erd_batch` runs all or nothing, one undo unit.** `runBatch` checks the list (non-empty, at most 100, registry tools, unique `as`; the listed schema shows the bounds). It rehearses on a peer loaded from `peer.runtimeValue` (removed entities included), so a refusal names its operation (`operations[5] erd_remove_table: …`) and nothing lands. Then it plays them inside `PeerStore.group`.
- **Refer to created ids as `$name`.** An agent cannot know them beforehand. `$name`, `$name.n` or `$name.last` (a relationship's id last, after its key columns) resolve only in `entityId`, `entityIdList` and table position arguments, so a name `$x` stays text.
- **Send one request per batch.** Live sends one `applyActions`, so the editor takes all or none, and reruns the whole batch after a `notOpen` rejoin; focus follows separately. Headless writes once. A peer failure after the rehearsal is `BatchInterrupted`: live sends nothing and reseeds, headless reloads.
- **Explain undo in `undoNote`.** `historyEntries` runs into dozens, once read as that many undos, so every result says one `erd_undo` reverts the batch. It names what that undo leaves: tools without undo entries (`erd_set_database`, `erd_set_database_name`, `erd_resize_memo`) and changes that made none (`erd_move_table_group` under 20 pixels in all), which `undoable` alone would miss.

### The eight rules a tool obeys

- **One tool, one dispatch, declared in machine terms.** It is a generator where the engine has one, else an atom with an `atomReason`. It declares `actionTypes`, `undoable`, `stream`, `expectedBatches` / `expectedHistory` (a number, or a range when state decides), `focus`, `snapshotPaths` and `args`. `runTool` checks the counts; a new tool adds its call to `__test-utils__/scenarios.ts`.
- **Reach every change type or say why not.** `tools/reachability.test.ts` pins 76 `ChangeActionTypes` (57 emitted, 19 in `NOT_EMITTED`, `PENDING_COVERAGE` empty) and that tools emit only what they declare. A new type gets a tool, or a `NOT_EMITTED` entry with its `EXCLUSION_REASONS` line; `PENDING_COVERAGE` holds one awaiting its tool.
- **Give viewer-local changes no tool.** Zoom, scroll, `settings.changeCanvasType` and `settings.changeNameViewMode` are `SharedFollowingActionTypes`, dropped by receivers, so a tool would report success and change nothing. The name view is the one exception: a switch made while its lock is off is shared and every peer takes it, and any other applies only on the store that sent it; which names a diagram shows stays the user's to pick in the editor. `tools/reachability.test.ts` keeps `SharedFollowingActionTypes` inside `NOT_EMITTED`. Reads omit the viewport, the tab and the name view, each reader's own, though the snapshot's lock flags name `unlockNameViewMode`.
  - `memo.move` is a relative drag step with a `moveTo` twin. Groups invert that: `erd_move_table_group` dispatches `tableGroup.move` and the tables' `table.move`, the step the editor's drag takes, computed from the point the agent names, so the tables stay inside. The peer's outbound pipe sends them, as it sends a drag, as the absolute points they end at, `tableGroup.moveTo` and `table.moveTo` in one batch, so a move made at once elsewhere ends on the later of the two, not their sum (`packages/erd-editor/src/engine/AGENTS.md`, Geometry registers). Dispatched alone, `tableGroup.moveTo` would strand the tables; no gesture dispatches it, and it has no tool.
  - `relationship.changeColumns`, which the editor's Map Columns dialog sends, has no tool either: an agent re-maps a relationship with an `erd_batch` of `erd_remove_relationship` and `erd_link_columns`, which every editor applies.
- **Set only the schema's own settings.** Screen and editing-habit settings are the user's (the owner's call on 2026-10-06), so the settings tools are `erd_set_database`, `erd_set_database_name` and `erd_set_ddl_script`. What the diagram shows, the column order, the comment width, the relationship data type sync, the language, both name cases, the bracket type and every lock are set in the editor, their nine change types in `NOT_EMITTED` with a reason each, and no tool replaces the settings tools the server had.
  - The scripts (`settings.changeDDLScript`) are schema content, written into the DDL as is, with an undo entry; DDL statements and header live per editor window, so no tool sets them. `erd_set_ddl_script` takes at most `MAX_DDL_SCRIPT_CHARS` (10,000), a bound of the tool's alone, since the document holds a script of any length, and replaces whole, so its description sends agents to the scripts format first.
  - Reads give a locked code setting at its saved value (`toSavedSettings`), and the sql format quotes with that bracket type, since what a peer shows of a locked setting is its own screen, not what a reader of the file opens. Known limit: an editor released before locks saves no `lockSettings`, read as all locked, so reads lag its code setting changes until it is updated.
  - `erd_import_json` takes the document's settings, scripts and locks, as Import JSON does, and its description says so and that an agent keeps this document's by starting from `erd_read json`. The four schema imports keep them but the view, which goes to the start of the canvas, in the file too where a lock held it (`withImportSettings`; `tools/import.test.ts`), and keep the word, term and domain dictionaries, as the editor's schema imports do (`keepDictionaries`), which their descriptions say.
- **`erd_sort_tables` sends `table.moveTo`, never `table.sort`.** `sortTable` places by each replica's own `toWidth`, so a replay lands tables apart. The tool dispatches `sortTablesToMoveAction$`, which runs the reducer on copies of the live tables and groups and sends absolute points plus a `tableGroup.resize` per group with members, in one undoable batch (0 or 1). Imports write the sorted grid points into the `loadJson` value (`loadSchemaAction$`), so editors agree whatever their fonts (`tools/import.test.ts`). `table.sort` is in `NOT_EMITTED`; only an older editor still sends it. `erd_move_tables` sends its points in one dispatch (one batch, one undo entry) and refuses a table named twice, since list order would pick the winning point.
- **`mode: 'append'` adds instead of loading.** The five `erd_import_*` tools take `mode`, `replace` by default. Append (`appendSchemaAction$`, `appendSchemaJsonAction$`) adds new entities in the grid below every table, memo and table group of the document, a hidden group's box included. Json keeps its placement, its table groups under new ids with their tables; DBML `TableGroup`s become groups wrapped round their tables, and only `erd_import_dbml` and `erd_import_json` declare the group types. It is one undoable batch touching no setting, table, selection or scroll. Flow placement stays in the editor, since elkjs is outside the peer graph. Text that declares nothing sends nothing, so the five declare 0..1 batches and entries; an empty json text is refused for an append. `APPEND_SCENARIOS` (`__test-utils__/scenarios.ts`) runs each through the registry, undoable and reachability specs.
- **Send nothing when the value already holds.** Undo records the negation of what was sent, so a repeated set would leave an undo flipping an unchanged value. The four column flags, `erd_set_index_unique`, `erd_set_index_column_order`, `erd_add_index_column` on a covered column, `erd_set_table_group` for tables already there (`setTableGroupAction$` skips them), `erd_move_table_group` / `erd_resize_table_group` at the same point or rect, and the three logical name and domain setters, the three dictionary updates and `erd_derive_physical_names`, whose generators send only what changes, declare 0 or 1 batch and entry. A group move under 20 pixels in all makes no entry, by the group history's threshold. The flags and the two index setters are atoms, since their generators toggle (`toggleColumnValueAction$`, `changeColumnPrimaryKeyAction$`, `changeColumnsPrimaryKeyAction$`, `changeIndexUniqueAction$`, `changeIndexColumnOrderTypeAction$`) and a retry would flip back; `erd_add_index_column` is the generator `addIndexColumnOnceAction$`.
- **`erd_derive_physical_names` takes a scope, never the selection.** It sends `rederiveNamesAction$` for one column, one table or the document (an owner decision of 2026-10-23); the editor's selection scope would read the agent peer's own selection, which no tool sets. Its `refine` gives each scope exactly the ids it names. `validateToolArgs` refuses an id whose optional parent argument is left out (`columnId needs tableId`), where the lookup would search no table. It composes no term's own physical name again, which its description says.
- **Change group membership only when told.** As in the editor, where only a drop does it, `erd_move_table`, `erd_move_tables`, `erd_move_table_group`, `erd_resize_table_group` and `erd_sort_tables` keep each table's group. `erd_add_table_group` (named tables, leaving their old group, or the ungrouped ones centred in a rect, `addTableGroupAction$`; named and colored in one undo entry), `erd_set_table_group` and `erd_remove_table_group` (clearing `groupId` in the same batch) change it. `erd_resize_table_group` refuses a rect under 160 by 100 or not holding its tables with padding (`getTablesGroupRect`), naming the box where the sash stops, so agents learn the bound. It reads this peer's widths; an editor whose text runs wider draws the box grown round the table.

### Sessions, hubs and the file on disk

- **No write lands on disk under an editor.** Discovery runs before every call and each retried Windows headless attempt, since an editor opening the file during the 2 s retry is what holds it. A lock listing the document refuses (`hubAppeared`, `blocked`, or `invalidPath` for another spelling) and removes the temp file; a `hub: false` lock refuses writes, its message saying the hub is off or failed to start in that editor and how to turn it back on there. A hub appearing over a headless session refuses that write and closes it, so the next call joins live.
- **Fall back to the file only on release.** With no lock covering the document, a live session drops to the file, with a note, only after `documentClosed` (connected or not) or after its connection closed and its pid died. Turning the Obsidian plugin off sends `documentClosed` while the process lives, where a pid check would answer `hubGone` until the plugin came back or Obsidian quit. `documentClosed` sets `released`, cleared by a new connection or a write's registered join. So a window hanging up without it (VS Code deactivating) still gets `hubGone` for a write, and a disk read with a note, while its pid lives. A JetBrains IDE closing a project sends `documentClosed` and takes the project's folder out of the lock while the IDE runs on. Its hub then ends that document's connection, but a call in between, or one to a hub that keeps a released connection open (as `fakeHub` does), finds the session released and still connected. So headless discovery keeps a session only while `existing.connected && !existing.released`: a released one falls back like a closed one, and a connected one never released still edits live though its lock is gone. `sessionState.test.ts` pins it per host and the forgetting on reconnect; the note says the editor no longer serves the document (`fellBackNote(ide, exited)`).
- **Name the editor from the lock.** `hubUnreachable`, `blocked`, `hubAppeared`, `hubGone`, `notSaved`, the `invalidPath` of a document held under another spelling, the disconnected and timeout refusals, and the fall-back, left-disk and disk-read notes take their words from `hostWords(candidate.record.ide)`, through agent-hub's `ideDisplayName`. VS Code's are the sentences it always got, byte for byte where `hubClient.test.ts` pins them, and so are Obsidian's and any other `ide`'s; an unknown `ide` gets a neutral sentence. Remedies are per host (`src/hub/host.ts`). A JetBrains IDE is never called a window, since one IDE process serves all its projects from one hub. The `hubGone` remedy is never a reload of Obsidian or a closed project window, since both keep the pid.
- **Windows `EPERM` on connect is `hubUnreachable`.** The editor runs elevated or the agent in a Low integrity sandbox; the pipe's default descriptor is deliberate (`agent-hub-host`'s AGENTS.md). Its sentence asks, for every host, to run both with the same rights (`hubClient.test.ts`).
- **State the save difference in two texts.** The static texts (`SERVER_INSTRUCTIONS` and the `erd_list_documents`, `erd_open_document` and `erd_save` descriptions) name the three editors, and `SERVER_INSTRUCTIONS` and the `erd_save` description give the one difference an agent acts on: VS Code keeps agent edits unsaved until `erd_save`, Obsidian and JetBrains IDEs save them as they save the user's and `erd_save` writes them at once.
- **A read never opens an editor.** Without a registered join it sends `join` alone, and the hub answers a closed document from disk without registering, and registers for an open one.
- **Refuse text the engine cannot read.** `setInitialValue` would fall back to an empty document. So `assertDocumentText` (non-blank text is a JSON object, a non-empty one with a v3 or v2 top-level key) checks every disk read and `join` answer, failing `invalidDocument` before any write.
- **New documents start as an empty peer's `value`.** It carries `$schema` and every lock on (`lockSettings` 63, `erd-editor-schema`'s `createSchema`), never `'{}'`. `erd_import_json` of empty text loads it too, as the element's value setter does (`create.test.ts`, `tools/import.test.ts`), and append refuses it. An older editor or server reads an unwritten file's `''` as `'{}'`, so paired live they hold different settings until a load; the editor alone writes the file, so only what the agent reads differs. A replicated `editor.loadJson` carries whole JSON, which both read alike.

### Windows paths

- **Refuse names Win32 reads as other files.** A segment `unsafeSegment` flags (`packages/agent-hub/AGENTS.md`) is `invalidPath` on the absolute and the real path, before any disk access, since Node would write another file than a Win32 caller reads.
- **Refuse a document held under another spelling.** A local file is reachable by drive path and through shares (`\\localhost\C$\…`, `127.0.0.1`, host name, LAN or IPv6 address, custom shares, mapped drives). The native realpath keeps the typed one, so a lock listing `C:\ws` misses `\\localhost\C$\ws\a.erd` and the call would go headless under the editor. So when `selectHub` goes headless on win32, discovery compares the target and its folders with live lock paths spelled the other way. It compares by `FileStats.identity` (bigint `dev:ino`), which matched across all those spellings (measured 2026-09-27, Windows 11 26200, Node 22.21.1). The local host's share prefix matches in any case (`LOCALHOST`). A document lock matches the target alone, a folder lock the target or any folder above it, so a document not created yet matches through its folder. The ranking is `selectHub`'s own (agent-hub's `matchRank` and `outranks`). A list of this computer's names would miss every custom share and some name for it, so identity decides.
- **Refuse rather than reroute.** A match refuses with `invalidPath` naming the window's path (`aliasError`), reads and `erd_open_document` included, and closes the other spelling's session. The session key precedes discovery, and a refusal writes nothing even on a false match. `erd_list_documents` from such a folder lists through that window, which answers with its own paths. The editor hosts keep two real paths for such a file (`vscode-extension`'s and `intellij-plugin`'s AGENTS.md) and point here.
- **Keep the check cheap.** It is free off win32 or with spellings alike; a share target's 15 stats took a median 7 ms through loopback, 0.4 ms by drive (measured 2026-09-28). Identities are cached per lock version (`pid:mtimeMs`), versions gone forgotten on each look, so an offline share costs its timeout once per lock rewrite.
- **Known limits.** A string match wins over a deeper identity-only one; hard links and two share spellings of one file are not compared; a disk cloned from one image can falsely match, which only refuses.

### The live session

- **Decode frames into one queue per connection.** The reader only decodes (`decodeHubToPeerFrames`, one `Result` per frame) and reads by hand the JSON `HubToPeerMessage` refuses. A numeric `id` settles the request it names: `ok: true` gives the result as sent, anything else a refusal with the hub's code and message (`internal` for a code that is not a string, `The hub refused <method>` where no message came), so no caller waits out the timeout. A notification never carries an id, since the protocol refuses the key there. A string `method` with object `params` goes to the session as a notification, an unknown method or one without its `path` or `actions` included; the rest is logged and skipped. Only non-JSON or an over-bound line hangs up. Requests (`encodePeerToHubFrame`, the conformance corpus's bytes) may overlap. When the reader ends they fail `disconnected` and the fiber closes the connection's scope, so a hub that hung up leaves nothing open until the session closes.
- **Take frames on one fiber, in stream order.** The fiber takes the queue back to back (`Effect.forever` with `disableYield`, a chunk in one go), settling a response's request and handing a notification to the session. A `request`'s caller resumes there before the next frame, so before the notifications read with its answer. A caller that must see them waits on `drained`, which succeeds once the frames read with the answer are taken, and at once when the taker is idle; it does not wait for a later read's frames. The live session awaits it before each dispatch and after a call's last batch, else an edit made as `openDocument` is answered would carry a lower version than relayed actions and lose in the editor's LWW while reporting success.
- **Reseed in `requestThen`.** Its continuation runs before the next frame, so `join`'s reseed keeps actions sent after the snapshot, even in the same chunk, and wipes earlier ones. The caller also waits one scheduler turn, so it sees relayed actions and the reseed's cleared focus goes out before its own edit. `hubClient.test.ts` and `live.test.ts` pin these orders.
- **Open, join, reseed.** Each write sends `openDocument`, then `join` if the editor just opened or the agent is unregistered, then `setInitialValue` + `mergeClock(snapshotVersion)` + `setReadonly`. The join answers the runtime value the editor holds, removed entities included, or the file while the editor holds none (agent-hub's `JoinResult`), so a table the user removed before the agent joined comes back whole on the agent's peer too when the user undoes the removal (`live.test.ts`).
- **Clear stale registers on reseed.** `setInitialValue` drops the peer's registers and, once subscribed, asks the editor for its own (`getLWW`, answered by `mergeLWW`), so a reopened document has none refusing edits. The join holds that batch until it marks this agent registered, since the peer's one way out (`enqueueOutbound`) drops every batch made before. A reseed without the hold left the peer taking a relayed edit older than the editor's register, which the editor refused (`live.test.ts`). The peer subscribes only after its first registered join.
- **Send one `applyActions` per batch, in order.** An outbound fiber sends them and a call awaits its own. A close sends untaken batches on the closed connection, so waiting calls fail `disconnected` instead of hanging the shutdown. Focus leaves on a microtask after a dispatch, so a call yields once before taking its last batch.
- **Rejoin on `notOpen`; reseed after other refusals.** `notOpen` rejoins and reruns the call once. Any other refused batch, `readonly` too, forgets the join, so the next call reseeds the edit the editor never took. A reseed with undoable agent edits behind it adds a note that they can no longer be undone.
- **`mergeClock` lets agent edits win.** Otherwise the agent's versions start below the editor's on fields the user changed, and the webview's LWW drops them while the call reports success. `live.test.ts` pins it.
- **Carry `CLOSED_NOTE` after `documentClosed`.** With agent edits behind it, every call, `erd_save` included, carries the note that they reached the file only if saved before the editor closed, until the next reseed.
- **Name both causes in `notSaved`.** `saved: false` carries no reason: no replica confirmed the last batch, or the editor did not write. VS Code keeps a tab changed on disk unsaved; a JetBrains IDE times out (under a modal dialog, say), fails, or cannot write. The second cause is in the host's words (`unsavedReason`).

### The headless session

- **Write a temp file, compare stats, then rename.** Writes go to `.<name>.<id>.tmp` with the document's mode plus owner write, so the temp file can always be removed. Before the rename the load's `(size, mtimeMs)` is compared, and a mismatch reloads and returns `conflict`. Load stats before reading and a write keeps the temp's stat, so no outside write becomes the baseline unseen. A file changed between calls is simply reloaded, with a note when that dropped undo history.
- **Refuse a document without owner write.** The POSIX bit or the Windows read-only attribute (`0o444` to node) gives `readonly` on every platform (`isReadonlyMode`, which a disk listing reports too), by the stat of the swap. A Perforce or TFVC checkout or revert changes the mode alone and keeps size and mtime. It is the code and remedy the JetBrains hub answers live (`DocumentRules.readonlyFile`), so such a file gets one answer live and headless, and a rename would turn `0o444` into `0o644` on POSIX.
- **Stat with `FileStats`, not `FileSystem.stat`.** `File.Info`'s whole-millisecond mtime hid a same-size outside write, later overwritten: back-to-back 4-byte APFS writes shared the millisecond in 1,935 and 1,943 of 2,000 tries, the nanosecond never (measured 2026-09-23; `headless.test.ts` stamps one on a real disk).
- **Write `peer.value` one scheduler turn late.** It is the file form `erd_read json` gives, read once after `Effect.yieldNow` (a `setImmediate` under effect's default scheduler): the engine sets a primary key's not-null in an `asapScheduler` microtask, so a value read at once left it out until a later write, and a session closed first lost it for good. What else that microtask derives (the foreign-key mark, `identification`, `startRelationshipType`, anchors) is not in the file form. `headless.test.ts` pins the not-null, a link written as `erd_read json` gives it with none of those fields, and their `erd_undo`, which takes back a key but not the not-null, as in an editor.
- **Retry a held swap on Windows.** A rename there fails over any open handle, this process's included; one looping reader failed 173 of 300. So on win32 the swap retries 10 ms doubling to 100 ms for 2 s (`SWAP_RETRY`: 24 attempts, the last 2,050 ms after the first on the clock) while `isBusyReplace` reads `Unknown` (libuv's `EPERM`, which platform-node folds into it), `PermissionDenied` or `Busy`. It twins `agent-hub-host`'s lock write by the same three tags, with a schedule of its own. Each attempt runs `recheck` and compares the stat again, so a write landing between two is a `conflict`, never written over. Then 0 of 300 failed (longest wait 738 ms); three readers made 3 of 100 give up, as `internal` quoting the `EPERM`. POSIX tries once, since its renames never fail on an open file.
- **Write in place when renaming would change access.** A rename gives the document the temp's folder-inherited DACL, so `FileAccess.keepsAccess` compares the two through one `icacls /save` (21 to 64 ms; a standard user may run it), equal for a document whose ACL is only its folder's. A document with its own ACE or no inheritance is written in place (`writeInPlace`) after the compare, the temp file kept until then and removed after; icacls failing writes every document in place, logged once. Node cannot set a DACL: `icacls /restore` needs SeRestorePrivilege (exit 1300 for a standard user), and `ReplaceFileW` needs PowerShell, about 200 ms a write.
- **An in-place write is not atomic.** The text overwrites the old bytes, then the tail is cut, so a reader in another process may find text that does not parse (`invalidDocument`). Under a tight loop 1,198 of 11,655 reads were torn and none blank; cutting first left 8,358 blank and 419 torn of 15,460; a rename tore or blanked none of 12,163, though 458 could not open the file mid-rename. A crash leaves the temp file. The baseline is the stat once the handle closed, equal to the handle's own in 200 of 200 writes. Hidden and System attributes follow a rename. Measured 2026-09-27, Windows 11 26200, Node 22.21.1, NTFS.
- **Read failures by reason tag, never errno.** `NotFound`, `AlreadyExists` (`isPlatformReason`), and `Unknown`, `PermissionDenied` or `Busy` for a held rename (`isBusyReplace`); `internal` quotes the system error (`messageOf`). `realPath` is native, since the JS `fs.realpath` keeps the typed spelling on a case-insensitive disk; when it fails, `NodeFileSystem`'s runs for the tag.

### Call order and cancellation

- **Run a document's calls in arrival order.** `ToolsLayer` wraps each handler in `SessionManager.arrive`, placing the call in a `session/line.ts` line as the request starts; a place taken inside a handler let a later `erd_read` overtake edits, since toolkits fork first. A call waits for earlier calls' path lookups, never their work, and other documents run side by side; a listing touches no document and gives up its place at once. A sweep never closes a document with a call running, and it removes every idle session before closing them, so `paths` answers at once. `manager.test.ts` pins a burst of edits and reads, a read behind an edit whose realpath was held, and a call beside a held listing.
- **Finish a call once it holds its document.** A cancel (`notifications/cancelled`) or stdin's end interrupts the tool's fiber; a cut between a peer change and its write, or before a refusal arrives, would leave the session unlike the file or editor. So the held part is `Effect.uninterruptible`; the wait stays cancellable, and a cancelled call's response is dropped. Shutdown waits for calls in flight, up to 30 s per hung hub request, so `ToolsLayer`'s finalizer first closes every session, failing pending requests as `disconnected` and refusing the batches queued behind them; the call ends without its response written (`manager.test.ts`). `bin.test.ts` stops the built file against a silent hub by stdin (exit 0) and, POSIX only, SIGINT (exit 130).
- **A throw in a session fails the call.** `failOnDefect` turns a session call's defect (a `TypeError` on an odd hub answer, say) into `{ error: { code: 'internal', message } }`. Outside the manager the toolkit's answer and `erd_read`'s JSON-RPC internal error stand.
