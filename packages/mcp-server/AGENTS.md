# mcp-server

## Purpose

`@dineug/erd-editor-mcp` is the stdio MCP server a coding agent runs with `npx -y @dineug/erd-editor-mcp`. It exposes 62 tools: eight session tools (`erd_list_documents`, `erd_open_document`, `erd_read`, `erd_list`, `erd_get`, `erd_save`, `erd_undo`, `erd_redo`) and one per entry of its own `actionTools` (`src/tools/registry/`, 54), each with a `path` argument in front of the registry's own. Every document gets one long-lived agent peer, driven through `createPeerStore` from `@dineug/erd-editor/peer.js`, live through a VS Code window's hub (`packages/agent-hub` protocol) or headless on the file. MCP is effect's `McpServer` over stdio (`effect/unstable/ai`), and the sessions, hub discovery, the hub client and the file system are effect services. Published to npm on its own version line, manually, like the other published packages.

## For AI Agents

### Working In This Directory

- **stdout is the MCP channel.** Nothing but the stdio protocol writes to it. Effect's default logger and `runMain`'s error report write to stdout, so `ServerLayer` and `serve` both provide `StderrLogger` and `runMain` runs with `disableErrorReporting: true`; every diagnostic is an Effect log call, and fibers a session forks inherit the logger of the call that made them. A stray `console.log` corrupts the client's stream.
- **Services and their layers.** `ServerLayer` is `layerWithSessions` over `SessionManager.layer`, which takes `HubDiscovery.layer` and a `Platform`: `FileSystem`, `FileStats`, `Path`, `ProcessInfo` and `HubConnector`. `NodePlatform` gives `io/fileSystem`'s `layer` (`NodeFileSystem` with the native `realPath`, and `FileStats` on node's stat), `NodePath`, `ProcessInfo.layer` and `HubConnector.layer` (`connectPipe`); the specs give `createMemoryHost().layer` instead, where `HubConnector.layerWith(memoryConnect)` runs the same client over memory pipes. The manager captures the clock and the platform when it builds, so a call and the sweep fiber read one clock, TestClock under the specs.
- **One inbound queue per hub connection, one fiber taking it.** The reader only decodes frames into the queue, with agent-hub `decodeHubToPeerFrames`, one `Result` per frame: a response or notification `HubToPeerMessage` takes is handled as decoded, and JSON it refuses is read by hand as the client read every frame before it decoded by schema. A numeric `id` makes it an answer, which settles the pending request it names (`ok: true` gives the result as sent, anything else a refusal carrying the hub's code and message, `internal` and `The hub refused <method>` where it gave none), so no caller waits out the timeout on an answer that came; a notification never carries an id, since the protocol refuses the key there. A string `method` with object `params` goes to the session as a notification, an unknown method or one without its `path` or `actions` among them, as it always did. Anything else is logged and skipped. Only a line that is not JSON or is over the size bound hangs up. Requests go out through `encodePeerToHubFrame`, the same bytes as before. One fiber takes the queue in stream order and back to back (`Effect.forever` with `disableYield`, a chunk in one go), settling a response's request and handing a notification to the session. A plain `request`'s caller resumes on that fiber as its answer is taken, before the next frame, and so before the notifications read with its answer; a caller that must see them waits on `drained`, which succeeds once the frames read with the answer are taken and at once when the taker is idle (a frame read after that is a later read's, which it does not wait for). The live session waits on it before every dispatch and after a call's last batch: an edit made as the `openDocument` answer is taken would carry a version below the actions read with it and lose to them in the editor's LWW while the tool reports success. `requestThen` runs its continuation on that fiber before the next frame is taken: `join` reseeds there, so actions the hub sent after its snapshot, even in the same chunk, land on the seeded peer and those sent before it are wiped by the reseed. Its caller is held until the frames already read are taken and one scheduler turn has run the microtasks the continuation queued: a call that joined sees the actions relayed with the answer, and the focus the reseed cleared goes out before the call's own edit. `hubClient.test.ts` pins the orders (a continuation that waits, `drained`, a close in the releasing turn included), `live.test.ts` what a call sees of the `join` and `openDocument` chunks and of its last batch's, and the focus order. Requests may overlap. When the reader ends, pending requests fail as `disconnected` and the fiber closes the connection's scope, so a hub that hung up leaves nothing open until the session closes.
- **`layerStdio` wraps the registrations, never sits beside them.** It interrupts the fiber that builds it when stdin ends; inside `Layer.mergeAll` that fiber is a concurrent member's, gone right after the build, and the end of stdin never stops the server. So `layerWithSessions` provides it around `ToolsLayer`, and `serve` launches the whole layer in a child fiber, whose interruption-only exit is a clean one: stdin end exits 0, a signal 130, a failure 1.
- **Stdin passes through `MessageStdin`.** Effect's line decoder cuts its buffer only once every line in it parsed: a line `JSON.parse` refuses (a blank one included) stays at its head and every later request goes unanswered until stdin ends, and a line that parses but throws further on (`null`, a non-string `method`, a `headers` field that is neither a record nor string-keyed pairs) loses the rest of its chunk. Its `@effect/rpc/` methods and `headers` are the RPC layer's own, and a client's `Eof` there stops every answer. `MessageStdin` passes on only JSON objects, or arrays of them, whose `method` is absent or a string outside that namespace and whose `headers` the decoder can read, and skips the rest; a line stdin never ends is never passed on.
- **Two ways onto the server.** 59 tools are effect `Tool`s in two `Toolkit`s, `SessionToolkit` (5) and `EditToolkit` (54), registered with `McpServer.registerToolkit` (what the `McpServer.toolkit` layer runs), so effect lists their `inputSchema` and `outputSchema`, writes their results and decodes their arguments, all but those of the four dynamic session tools (see Arguments). The three read tools alone are hand-built `McpSchema.Tool`s added with `McpServer.addTool`, because they answer the document as plain text, which a toolkit would encode as a JSON string inside the text block, and a 2025-06-18 client would get a second time as `structuredContent`. A new tool goes into a toolkit unless it answers plain text; `addTool` decodes nothing, so a hand-added tool decodes its own arguments with `onExcessProperty: 'error'` and fails with `McpSchema.InvalidParams`, as `read.tool.ts` does.
- **One order in `tools/list`.** `ToolsLayer` registers the session toolkit, then the read tools, then the edit toolkit, one after another: `Layer.mergeAll` would build them concurrently. The listing order is therefore `erd_list_documents`, `erd_open_document`, `erd_save`, `erd_undo`, `erd_redo`, `erd_read`, `erd_list`, `erd_get`, then the registry's.
- **Three dated protocols** (`PROTOCOLS`: 2025-06-18, 2025-03-26, 2024-11-05): the ones that answer a malformed argument with JSON-RPC -32602. A client on a later version is answered with 2025-06-18; the two older ones drop `outputSchema`, `additionalProperties` and `structuredContent` on the wire, 2024-11-05 the annotations too. Three answers are effect's `McpServer`'s, reached before any code of ours: every request before `initialize`, `ping` included, gets -32603 with nothing logged (clients initialize first); `initialize` also offers `logging` and `completions`, so `logging/setLevel`, `resources/list` and `prompts/list` are answered rather than refused with -32601; a tool name not listed gets -32602 (`Tool 'x' not found`), the protocol error MCP 2025-06-18 names, not an `isError` result. `server.test.ts` and `toolSurface.test.ts` pin them.
- **Arguments.** The 54 edit tools are `Tool.Strict` and the three read tools decode with `onExcessProperty: 'error'`: an unknown argument or a malformed one is JSON-RPC -32602 and no session is touched, a deliberate change from the SDK-based server, which dropped unknown ones silently. That decision covered only the edit tools and the read tools, so the five toolkit session tools keep the SDK-based server's meaning: an unknown key is ignored, and a malformed or missing argument is an `isError` refusal, code `invalidArgs`, message `Invalid arguments for tool <name>: …`. Any toolkit tool with a schema decodes its arguments before its handler and answers -32602, so `erd_open_document`, `erd_save`, `erd_undo` and `erd_redo` are `Tool.dynamic` tools listing `toolInputSchema` of their `SessionParams` struct, the listing unchanged, and their handlers decode it; `erd_list_documents` takes `Schema.Record(Schema.String, Schema.Unknown)`, since a parameterless tool refuses every key. `toolSurface.test.ts` pins all three answers.
- **Results keep the SDK-based server's text bytes.** Each success schema declares its keys in the order the body emits them, so the text block the toolkit writes from the encoded value is the one that server wrote; a 2025-06-18 client also gets it as `structuredContent` and every toolkit tool lists an `outputSchema`. A refusal fails with `ToolRefusal`, a struct and not an Error, which the toolkit writes whole as the text of an `isError` result. The read tools have no output schema (plain text) and write their refusals themselves. `result.test.ts` holds both to those bytes, with that server's two writers kept there as the reference. The hints are the MCP defaults but for `readOnlyHint` on the four reads and `destructiveHint: false` on every tool that neither removes nor imports.
- **The client name is per request**: `McpSchema.McpRequestContext` (a dependency of every tool) carries `clientInfo`, and `SessionManager.rememberClient` keeps the first name seen; a peer made before any name, or with an empty one, is `DEFAULT_CLIENT_NAME`.
- **The size budget.** `bin.test.ts` holds the built file to `BUNDLE_GZIP_BUDGET` = 239,420 bytes gzip level 9, because npx downloads the file on every cold start: 15% over 208,191, the `gzip -9` size projected before the move for this server on effect's `McpServer`, from a prototype bundle plus the engine it carries. By the spec's own `zlib` level 9 the file measured 216,852 (raw 809,278) when it moved onto `McpServer`, and measures 224,660 (raw 832,694, 14,760 under the budget, measured 2026-09-23) with the sessions, hub client and IO on effect services, effect imported from its named entries, hub frames decoded and requests encoded by the protocol schemas, and `erd_list`, `erd_get` and `erd_move_tables` (222,824 at raw 827,140 before those three tools, 222,658 at raw 826,679 before the protocol schemas, 222,840 at that raw size with effect's module paths); the SDK-based server, on the MCP SDK and zod, measures 214,066 (raw 844,291) the same way. The same spec finds no `Sec-WebSocket-Accept` (ws), no `undici`, no `SchemaAOTCompiler` or `Migrator` and no literal dynamic import: effect is imported from the entries its `package.json` exports by name (`effect`, `effect/testing`, `effect/unstable/ai`, `effect/unstable/socket`), never `effect/unstable/schema` or `effect/unstable/sql` nor a module path (lint and `imports.test.ts`), and `@effect/platform-node` by module path, only `NodeRuntime`, `NodeStdio`, `NodeFileSystem` and `NodePath`: its barrel re-exports `NodeRedis`, whose `redis` nothing here installs, and a build from the barrel stops on `Rolldown failed to resolve import "redis"` and Node's own import of it on `ERR_MODULE_NOT_FOUND` (both measured 2026-09-23); the socket adapter is this package's own, since platform-node's `NodeSocket` re-exports ws.
- **The build is one ESM file with no bare import.** `vite.config.ts` copies `vscode-extension`'s SSR shape — `ssr.noExternal: true`, node builtins the only externals, `minify: true` and `sourcemap: false` (here because npx downloads the tarball on every cold start; the extension does the same) — with two differences: `format: 'es'` (no `main` contract forces CJS, and the ESM-only dependencies inline without a bridge) and a `#!/usr/bin/env node` banner. The `es` format costs two lines the extension does without: Vite's lib mode keeps the whitespace of an `es` build under `build.minify` (1,091,151 B against 826,679 B, measured 2026-09-23), where the extension's `cjs` build comes out the same with or without `rolldownOptions.output.minify`, and this build names its file after the entry module (`main.js`) whatever `lib.fileName` says, so `rolldownOptions.output` sets `minify` and `entryFileNames` itself. `bin.test.ts` runs a copy of the built file from a folder with no `node_modules`.
- **The floor is Node 22.12, the root's.** `engines.node` (`>=22.12.0`), `build.target: 'node22'` and `@types/node` `^22` are raised by hand together, and nothing gates them; `bin.test.ts` runs the build on the toolchain's Node (22.23.2), not on the floor.
- **Everything is a devDependency** — `effect`, `@effect/platform-node`, `@dineug/erd-editor`, `@dineug/erd-editor-agent-hub`, `@dineug/erd-editor-schema`, `@dineug/r-html`, `es-toolkit`, `nanoid` — because it is all inlined; `dependencies` stays empty, and a package this source imports is listed here even when the engine already brings it. `@dineug/erd-editor` resolves to its built `dist/peer/index.js`, so the `build` and `test` tasks depend on the siblings' builds and track a `dist/**/*.d.ts` glob per workspace dependency, which `check-task-inputs.mjs` matches to the declared dependencies. The `test` task also builds this package first, for `bin.test.ts`; `pnpm --filter @dineug/erd-editor-mcp test:coverage` does not, so build before it.
- **The registry reaches the engine only through `./peer.js`.** Action creators come from the per-module barrels (`tableActions.changeTableNameAction`, `tableActions$.addTableAction$`), constants and `bHas` from the same entry, the document parser from `@dineug/erd-editor-schema` and `CompositionActions` from `@dineug/r-html`. `src/peerSurface.test.ts` holds the entry's 46 exported values to the names this package imports, so neither side keeps a dead one.
- **Prose lives in `tools/copy.ts`, in English.** The registry is machine-readable only, so every word an agent reads, and its length, is managed in one file apart from the tools' declarations. `copy.exhaustive.test.ts` fails on a tool or argument without prose and on an entry nothing uses; an argument that means something particular in one tool (`value` always does) gets that tool's own entry. Keep descriptions short: every agent reads `tools/list` before its first call. Its result is 80,262 bytes under 2025-06-18 (41,194 under 2025-03-26, 34,703 under 2024-11-05; `toolSurface.test.ts` logs it), up from the SDK-based server's 40,821 because the 59 toolkit tools list their `outputSchema` (77,488 before `erd_list`, `erd_get` and `erd_move_tables`).
- **Reads come in two sizes.** `erd_list` answers the settings and every live table, relationship, index and memo by id with what placing it takes (a table's position, size and column count), and `erd_get` the entities its id lists name, in full, with the ids no live entity of that kind holds under `missing`; `erd_read` `snapshot` answers everything at once. The snapshot of a 55 table, 1,233 column schema (`data/YOUNGCART5.sql`) is 228,518 bytes, more than an agent can take in from one tool result, where its `erd_list` is 10,093 and `erd_get` of its widest table 31,569 (measured 2026-09-23 on the built file). The id lists come from `doc.*Ids` and each table's `columnIds`, never from a collection's keys, since a removed entity keeps its record as an LWW tombstone. A table's size is `calcTableWidths(...).width` and `calcTableHeight(...)` from `peer.js`, the box the table sort places by: the height is exact; the width is built from text widths `recalculateTableWidth` estimates with `defaultToWidth` (10 px a character) on copies of the tables and columns, as the peer's own table hooks estimate them a few milliseconds after a document loads whatever the file carried, so a first read right after a load and a later one agree. It is approximate, wide for Latin text. The widths the editor measures on its canvas are local to each replica and never replicated, so a live session cannot ask for them without a bridge command of its own.

**The five rules a tool obeys**

- **A tool is one dispatch and declares what it does, in machine terms only**: a generator where the engine has one, otherwise an atom whose `atomReason` says why no generator fits; `actionTypes`, `undoable`, `stream`, `expectedBatches` / `expectedHistory` (a number, or a range when state decides), `focus`, `snapshotPaths`, `args`. `runTool` holds the measured counts against the declared ones, and a new tool needs its call in `__test-utils__/scenarios.ts`.
- **Every change type is reachable or excluded with a reason.** `tools/reachability.test.ts` pins 56 `ChangeActionTypes`, 49 emitted by some tool and the 7 of `NOT_EMITTED`, and requires every tool to emit only what it declares. A new change type gets a tool, or a `NOT_EMITTED` entry plus its `EXCLUSION_REASONS` line; `PENDING_COVERAGE` (`tools/reachability.ts`, empty) is where one waits for its tool.
- **Viewer-local settings have no tool.** Zoom, scroll and `settings.changeCanvasType` are `SharedFollowingActionTypes`, which every receiver drops, so a tool would report success while no one's screen or file changed; `tools/reachability.test.ts` keeps `SharedFollowingActionTypes` inside `NOT_EMITTED`. `table.move` / `memo.move` are relative drag steps with `moveTo` twins.
- **`erd_sort_tables` sends `table.moveTo`, never `table.sort`.** `sortTable` places by each replica's own `toWidth`, so replaying it lands tables apart; the tool dispatches the engine generator `sortTablesToMoveAction$`, which runs the reducer on copies of the live tables and sends the absolute points in one undoable batch (0 or 1). An import's `table.sort` is safe because the widths travel inside its `loadJson` payload. `erd_move_tables` sends an agent's own points the same way, every `table.moveTo` in one dispatch, so one batch and one undo entry; a table named twice is refused, since the list order would pick the point that wins.
- **Value-setting tools send nothing when the value already holds**: the four column flags, `erd_set_show`, `erd_set_index_unique`, `erd_set_index_column_order`, and `erd_add_index_column` on a covered column, each declaring 0 or 1 batch and entry. The engine's undo records the negation of what was sent, so a repeated set would leave an undo that flips a value that never changed. The column flags, `erd_set_index_unique` and `erd_set_index_column_order` are atoms because their generators toggle (`toggleColumnValueAction$`, `changeColumnPrimaryKeyAction$`, `changeIndexUniqueAction$`, `changeIndexColumnOrderTypeAction$`), which an agent's retry would flip back; `erd_set_show` is an atom because no generator sets it, and `erd_add_index_column` is a generator, `addIndexColumnOnceAction$`, that skips a covered column.
- **A write never lands on disk under an editor.** Discovery runs before every call. A hub false lock refuses writes (its message says the hub is off or failed to start in that window); a hub appearing over a headless session refuses that one write and closes the session, so the next call joins live; a live session drops to the file only when its window's lock is gone and its pid is dead, and says so in `notes`.
- **The live write path**: `openDocument` on every write (the hub answers at once for a ready editor), `join` when the editor was just opened or this agent is not registered, then `setInitialValue` + `mergeClock(snapshotVersion)` + `setReadonly`. The peer subscribes only after its first registered join; each outbound batch becomes one `applyActions`, sent in order by the session's outbound fiber, and a call waits for the ones it produced. A close interrupts that fiber and sends each batch it never took on its own connection, closed by then, which refuses it at once: the call waiting on it fails as `disconnected`. A batch left unsettled would hold an uninterruptible call, and with it the shutdown, forever. The focus a dispatch moves goes out on a microtask after it (the peer's `rxStore.dispatch`), so a call yields once before it takes the last batch to wait for. A `notOpen` refusal rejoins and runs the call once more; any other refused batch, `readonly` included, forgets the join so the next call reseeds the edit the editor never took. A reseed with undoable agent edits behind it adds a note that they can no longer be undone.
- **`mergeClock` is what lets an agent edit win** on a field the user changed before the agent joined: without it the agent's versions start below the editor's and the webview's LWW drops them while the call reports success. `live.test.ts` pins it.
- **`documentClosed` with agent edits behind it** makes every call, `erd_save` included, carry `CLOSED_NOTE` (those edits are in the file only if saved before the editor closed) until the next join reseeds. `saved: false` from the hub has two causes (no replica confirmed the last batch, or VS Code kept the tab dirty), so the `notSaved` message names both; the protocol carries no reason.
- **A read never opens an editor.** Without a registered join it sends `join` alone: the hub answers from disk for a closed document without registering, and registers for an open one.
- **Headless writes** go to `.<name>.<id>.tmp` beside the document, created with the document's permission bits (owner write added so the temp file can always be removed), then compare the `(size, mtimeMs)` taken at load before the rename; a mismatch reloads and returns `conflict` without writing. Load takes that stat before reading, and a write keeps the temp file's stat (a rename keeps size and mtime), so no outside write can become the baseline unseen. A file changed between calls is simply reloaded, with a note when that dropped undo history. The stat is `FileStats`, not `FileSystem.stat`: `File.Info` gives mtime as a `Date`, whole milliseconds, and an outside write of the same size in the millisecond of the session's own went unseen, so the next edit wrote over it (two back-to-back 4-byte writes on APFS shared the millisecond in 1,935 and 1,943 of 2,000 tries and the nanosecond in none, measured 2026-09-23); node's `mtimeMs` keeps the fraction. `headless.test.ts` stamps such a write on a real disk; the memory disk counts mtimes in whole numbers, so its `FileStats` on `FileSystem.stat` loses nothing. `memoryFs.rename` keeps mtime and mode, as a real rename does.
- **Failures are reason tags**: a missing file is `PlatformError` reason `NotFound`, an exclusive create over one `AlreadyExists` (`isPlatformReason`), and no errno is read. A failure the result reports as `internal` quotes the system error under it (`messageOf`). `realPath` is the native realpath (`io/fileSystem.ts`): `NodeFileSystem`'s is the JS `fs.realpath`, which keeps the spelling an agent typed on a case-insensitive disk (macOS, Windows) where the native one answers with the disk's; when the native one fails, `NodeFileSystem`'s runs for the reason tag, so the climb in `paths.ts` reads no errno either, and `FileStats` fails the same way.
- **Text the engine cannot read is refused, never seeded.** `setInitialValue` falls back to an empty document on a parse failure, so `assertDocumentText` (non-blank text must be a JSON object, and a non-empty one must carry a v3 or v2 top-level key) runs on every disk read and on every `join` answer, and fails with `invalidDocument` before anything is written.
- **Calls on one document run one at a time, in the order they reached the server**, different documents side by side. `ToolsLayer` registers every tool through an `McpServer` whose `addTool` wraps the handler in `SessionManager.arrive`, which takes the call's place in a `session/line.ts` line as the server starts the request: a toolkit forks its handler off before running it and `erd_read` has no such hop, so a place taken inside a handler let a read sent after edits overtake them. A call resolves its path, then waits until every call that arrived before it has queued on its document or ended, and queues on its own document's line (dropped once empty); a listing touches no document and gives up its place at once. The cost is that a call waits for the earlier calls' path lookups, never for their work. `manager.test.ts` pins a burst of edits and reads, a read behind an edit whose realpath was held, and a call running beside a held listing. A sweep never closes a document with a call running, and it removes every idle session before closing them, so `paths` answers at once.
- **A call runs to its end once it holds its document.** A cancel (`notifications/cancelled`) or the end of stdin interrupts the tool's fiber, and a call cut between a peer change and its write, or before it hears the editor refuse a batch, would leave the session unlike the file or the editor. So the task a call runs holding its document is `Effect.uninterruptible`: the wait for its turn can still be cancelled, and the response of a cancelled call is dropped. A shutdown would wait on such a call (the server waits for the calls in flight), up to 30 s per hub request of a hung window, so `ToolsLayer` closes every session in a finalizer that runs before that wait: a pending hub request fails as `disconnected`, the batches still queued behind it are refused on their closed connection, and the call ends. Its response is not written. `manager.test.ts` pins both cancels and the shutdown on stdin end and on an interrupt, with one batch or two in flight; `bin.test.ts` runs the built file against a `node:net` hub that stops answering and ends it by stdin (exit 0) and by SIGINT (exit 130).
- **A throw inside a session is a failed call.** Session code is effect code, where a throw (a `TypeError` on a hub answer of an unexpected shape, say) is a defect; the manager turns every defect of a session call into a failure (`failOnDefect`), which the handlers answer `{ error: { code: 'internal', message } }` in the throw's words. A defect outside the manager keeps the toolkit's answer, and `erd_read`'s JSON-RPC internal error (`tools/read.tool.test.ts`).
- New documents start as an empty peer's `value`, which carries the `$schema` stamp; never `'{}'`.
