# app

## Purpose

`@dineug/erd-editor-app` (private) is the React PWA at erd-editor.io and the workspace's only React package. It wraps `<erd-editor>` in a backend-free shell: IndexedDB behind a Comlink worker, cross-tab sync over BroadcastChannel, a Workbox service worker, and end-to-end-encrypted peer-to-peer collaboration.

## For AI Agents

### Working In This Directory

- **The editor is a custom element, not a React component**: `viewer/editor/Editor.tsx` creates it and drives it through its methods.
- **`import '@dineug/erd-editor';` on its own line registers `<erd-editor>`.** A file importing only the `ErdEditorElement` type loses the import to type elision and mounts an unupgraded element (`getSharedStore is not a function`), past `tsc` and the build. `erdEditorRegistration.test.ts` pins it beside every caller.
- **`updateAt` moves on content edits only**, peer edits and imports included. `SchemaService` compares a fingerprint of `{ doc, collections, settings.databaseName }` (`toFingerprint` in `utils/documentFingerprint.ts`) on every replica `change`; zoom, scroll and other view state still persist `value` but no `updateAt`. The baseline is taken one microtask after `setInitialValue`, past the tombstone collection the engine queues on every load. A bump reaches the tabs as `updateSchemaEntity` over the service's own `BroadcastChannel('@@bridge')`.
- **The fingerprint leaves out what the engine derives and rewrites after a load without an action**, or opening a document saved on another machine or build would count its first zoom as an edit: table and column `ui.width*` (`recalculateTableWidthHook`, this machine's fonts), relationship `start` / `end` `x`, `y`, `direction` (`relationshipSort`), `identification` and `startRelationshipType` (read off the end columns' key and not-null flags), and the foreign key bit of column `ui.keys` (kept in step with the relationships; that hook runs before the baseline today). Each has its source in the fingerprint. A new engine hook that writes persisted state after a load joins this list, with a case in `service.test.ts`. `toDriveFingerprint` leaves out the same fields and keeps every setting but the six a view writes (`scrollTop`, `scrollLeft`, `originX`, `originY`, `zoomLevel`, `canvasType`), since a Drive file is the whole document and a changed database or column order has to reach it. It also leaves out every entity's `meta`, which each replica stamps with its own clock as it applies an action: tabs compare their content with a base another tab computed, and with `meta` in it the same document never matched, so a handoff re-saved and two tabs without Web Locks PATCHed each other's saves back and forth without end. And it leaves out what no longer hangs off `doc`: tables and memos the document no longer lists, and the columns, indexes and relationships of such a table, index columns with them, relationship and index ids in `doc` included. `<erd-editor>` collects those tombstones three days on, in a shared worker that answers a macrotask or more after `setInitialValue`, long after the baseline, so with them in it merely opening an old file saved it.
- **Nothing else bumps it**: `updateSchemaEntity` in `modules/schema` writes only the fields given, and rename, move to trash, restore, open and select never pass `updateAt`. The list sorts on it, so a stray bump reorders the sidebar.
- **The trash is `deletedAt` on the entity** (not indexed, so no Dexie version bump). A trashed schema leaves the list, is deselected, has its collaboration session stopped, and cannot be opened. **After 30 days in the trash it is deleted for good** (the user's call on 2026-09-20, replacing keep-until-emptied). `isTrashExpired` counts calendar days in the local zone, so a DST change moves the deadline by no hour, and a `deletedAt` ahead of the clock waits its full 30 days. Each open tab purges when its list loads, when it is shown again, and on the first `now` tick of a new day (`usePurgeExpiredTrash`, from `Sidebar`; no timer of its own), through `deleteSchemaEntityAtom` like Delete permanently, so IndexedDB, the worker's replica and the other tabs (`deleteSchemaEntity`) follow. Tabs purging one schema at once are harmless: deleting a missing row resolves, and a tab drops an id it no longer lists without a word. Between the deadline and the next purge the dialog says "deletes today".
- **The selected schema lives in the URL as `/?schema=<id>`** — a query string, so the static host needs no SPA fallback. Selecting pushes an entry, deselecting replaces it, back and forward switch schemas, and an unknown or trashed id clears the parameter. The tab title is `<name> · erd-editor`, else `erd-editor`.
- **A backup is `{ format: 'erd-editor-app-backup', version: 1, exportedAt, schemas: [{ name, value, createAt, updateAt }] }`**, trash excluded, recognised by `format` whatever the file is called. Importing one always adds new copies under new ids, keeping their times, and never overwrites. A time outside 0–8.64e15 (what a `Date` holds) skips its schema; one after the import is taken as the import time, so it cannot pin the schema to the top of the list.
- **SQL, DBML, AML and GraphQL are converted before their schema is stored**: the app has no parser, so `convertSource` creates an `<erd-editor>` it never attaches, calls `setSchemaSQL` / `DBML` / `AML` / `GraphQL` and reads `value` at once. The layout is synchronous; connector anchors and relationship flags follow from hooks milliseconds later, so the stored value lacks them until the first open derives them, which the fingerprint leaves out and so saves without an `updateAt` (a `service.test.ts` case and `import-export.spec.ts` pin it). The element is destroyed in a `finally`. The module is imported on demand, since it brings in the whole editor. A source it throws on counts as an invalid file.
- **An import stores everything in one `importSchemaEntities` call** and opens the last document or source, unless the selection changed while it ran. `.erd` / `.vuerd` / editor `.json` are stored as they are, but only in a shape the editor recognises (`isEditorDocument`: version `3.0.0` with `doc`, or v2 with `canvas` and `table`), since its parser takes any object as an empty schema. Source extensions are an own-key `Map` lookup.
- **An import reads no file over 64 MB** (`MAX_IMPORT_FILE_SIZE`) and says so in the notice. A document takes about 600 bytes a column (the `data/` fixtures), so 1,000 tables are some 14 MB and a backup of several fits; `file.text()` of a larger stray file risks the tab.
- **File drops are taken only when `dataTransfer.types` includes `Files`** (`useFileDrop.ts`); the editor's own drags of tables and columns carry none and must keep passing through.
- **A new service worker waits for the user.** `registerSW.ts` turns `waiting` into the prompt (mounted in `Root`, so `/live` has it too); taking it sends `SKIP_WAITING` through `messageSkipWaiting()`, and only that tab reloads on `controlling` — the others show "reload to finish". Nothing reloads unasked. The first deploy of this flow meets tabs still running the old worker's code, which has no prompt, so the new worker waits until every tab is closed.
- **A chunk that fails to load prompts a reload** (`outdated`): after a deploy the new worker has dropped the old precache and the server the old files, so a tab on old code, `updatedElsewhere` ones included, cannot load its lazy chunks. Vite dispatches `vite:preloadError` for every failed dynamic import of a build; `watchStaleChunks` leaves it unprevented, so the import still rejects to its caller. A waiting worker found later replaces `outdated` with `available`.
- **Action hooks settle instead of rejecting.** Components call them without waiting, so each `use*` action is wrapped in `useSettleReported`: a failure is logged and sent to Sentry (a no-op outside production, where `main.tsx` never initialises it), after the atom has rolled back what it showed early. A failed update puts back exactly the fields it set, deleting those the entity lacked. Import and export failures also show in the import notice. A new action hook follows suit.
- **`addSchemaEntity` carries the list entry, not the document**: the other tabs keep no values. `store.ts` still drops a `value` a tab on an older build sends.
- **Known limitation, the per-tab fallbacks**: where `SharedWorker` is missing, each tab runs its own `SchemaService` (a dedicated `Worker`, or in-thread), and a replica it cached once stays in memory. Another tab's edits reach IndexedDB but not that replica (the shared store passes no remote action on to its subscribers), so this tab's backup export, duplicate and reopen of the schema read the stale replica, and its next edit there saves the replica over the other tab's edits. Not addressed; it needs replicas evicted, or fed the other tabs' batches.
- **Collaboration stays on the main thread** — `RTCPeerConnection` is window-only. `leader.ts` elects one tab via `navigator.locks`; `atoms/modules/sidebar/index.ts` sends each batch as `collaborativeDispatch`, through `bridge.emit` in the leader and `dispatch` elsewhere, because BroadcastChannel never echoes to the poster.
- **Join rooms only via `joinCollaborativeRoom`**: it ref-counts one trystero room per strategy and room id, so a bare `joinRoom` lets one caller's `leave()` destroy another's peers.
- **Send through `sendQuietly`** (`room.ts`), never a bare `action.send`: a send rejects when a data channel closes as its peer leaves, and an unhandled rejection lands in Sentry.
- **Participants**: `hello` carries `{ role, nickname? }`, and a peer that sends a `nickname`, even an empty one, reads the list. The host keeps `peerId → nickname` per session and sends the whole list, itself first, as the encrypted `participants` action — only to guests that sent a nickname, because trystero buffers a message for an action the receiver never registered forever. A guest takes a list only from a peer that said hello as host. That guards against a buggy guest, not a hostile one: every peer holds the key, can claim to be host, and can edit the document anyway. The leader tab publishes `collaborativeParticipants` over the bridge, and a newly opened tab asks with `collaborativeParticipantsRequest`.
- **The secret key stays in the URL fragment** (`/live/#<roomId>,<secretKey>`, read in `LiveCollaborative.tsx`): it doubles as the trystero password, and a query string would leak it to server logs and referrers.
- **Theme**: `appearance` is `'dark' | 'light' | 'system'`, default `dark`; `system` is opt-in and follows `matchMedia`. The inline script in `index.html` applies a stored preference before first paint with the rules of `parseThemeState` / `resolveAppearance`, and `theme.test.ts` runs that script against them — change both together, and keep the script inline.
- **Icons are `lucide-react`**; brand marks, which lucide 1.x does not ship, are inline SVG (the GitHub mark in `Viewer.tsx`).
- **The sidebar is `<nav aria-label="Schemas">`** with one roving Tab stop across the date groups: arrows, Home and End move, Enter and Space open, F2 renames, Delete or Backspace moves to the trash. A row's collaboration and menu buttons show on hover or focus and take Tab on the focused row only, since a running session keeps its trigger on screen. The e2e locators rely on these names and labels.
- **The sidebar is fragments put together by an adapter.** `SidebarShell` (the landmark, the header, list and footer slots, the bar the sash folds it to), `SidebarSearch`, `SidebarGroups` (the date groups, `data-schema-list`, No results, a `leading` row), `useSidebarList` (query, groups, Tab stop) and `SidebarItemView` (rename field, row keys, menu, with `menuItems`, `trailing`, an optional remove and `renameDisabled`) read no atom. `trailing` sits in a wrapper hidden like the menu trigger until the row is hovered or focused; an element that sets `visibility: visible` itself, as a running session's trigger does, stays shown. `Sidebar` and `SidebarItem` are the local adapter: they bind the IndexedDB atoms, keep the header buttons, the Duplicate item and the footer, and pass the landmark, search field, name field and remove labels and the name placeholders. The fragments own Rename, `Actions for <name>`, No results and the Search placeholder; the e2e locators read the first two, so another adapter inherits them and changing one in a fragment changes `/` too. The two remove paths stay apart: Delete or Backspace focuses the row taking its place before removing, the menu item once the menu has closed. A change to a fragment is a change to `/`: the e2e specs guard its names, the menu's Rename and Move to trash and the date groups, and `SidebarItemView.test.ts` and `SidebarSearch.test.ts` the row and search keys, both remove paths, a row without remove and `renameDisabled`.
- **`src/server/auth/` relays Google OAuth for `/gdrive` on web standard APIs only** (`Request`, `Response`, `crypto.subtle`), so the Pages Function (root `functions/api/auth/[[route]].ts` re-exports `pages.ts`) and `vp dev` run the same handlers. `start` (GET) seals state, PKCE verifier, the opener's attempt id and the `login_hint` into `__Host-erd_oauth` (Lax, 10 minutes, which the sealed `expiresAt` enforces on the server too, since a copied value outlives `Max-Age`) and sends the popup to Google with `prompt=consent` and `access_type=offline`, so every browser gets a refresh token of its own. `callback` (GET) checks the state, exchanges the code, refuses a grant without `drive.file` (`scope_missing`) and seals the refresh token into `__Host-erd_gdrive_rt` (Strict, 180 days). It clears the state cookie once consumed, or when it no longer opens; a cookie that opens under another state stays, since it belongs to a sign-in still open in another popup, so a stale popup or a stray callback link cannot end it. `token` (POST) answers `{ access_token, expires_in, scope }` and renews the cookie, with Google's new refresh token when one comes. `logout` (POST) revokes the grant, which signs every device of the account out, and clears the cookie. Every answer is JSON, the callback page or `start`'s 302 to Google: 401 JSON means sign in, anything else an unavailable relay. None carries a CORS header, and a POST passes only with an `Origin` equal to its own origin and `X-Requested-With: XMLHttpRequest`.
- **The callback page reflects nothing from the request.** Its result is a fixed enum (`access_denied`, `state_mismatch`, `invalid_grant`, `scope_missing`, `upstream`, `unknown`; Google's `error` survives only as `access_denied`) in escaped `data-*` attributes of `<meta name="erd-editor-auth-callback">`. Its one script is constant text under a nonce CSP with `base-uri`, `form-action` and `frame-ancestors` at `'none'`; it posts `oauth-done` on `BroadcastChannel('@dineug/erd-editor-app/gdrive-auth')` and closes the popup. The attempt comes out of the state cookie, and only when the state matches, so a callback link made elsewhere reaches no opener. The relay logs event names alone, never a token, cookie, code or callback URL.
- **What `pages.ts` reaches imports only relative paths inside `src/server/`** and names no `Buffer`, `process` or `require` (`imports.test.ts`), since workerd has neither Node's globals nor the DOM; the root `tsc`, which has no DOM lib, rejects DOM names, so a DOM type like `CryptoKey` is derived from a value instead. `nodeAdapter.ts`, the one Node file, stays outside that graph.
- **fetch is bound where the relay is assembled** (`fetch: (input, init) => fetch(input, init)` in `pages.ts` and `nodeAdapter.ts`), and the handlers call it without a receiver: workerd and Chrome throw Illegal invocation on a fetch called through another object, and the client would read that as an unavailable relay.
- **The relay's variables**: `GOOGLE_CLIENT_SECRET`, `COOKIE_KEY` (32 bytes as base64, `openssl rand -base64 32`) and `VITE_GOOGLE_CLIENT_ID`, which the `build` task also passes to the bundle (`env`). Without all three the relay answers 503 JSON, except `token` without a cookie, which stays 401, and `logout`, which always answers 200 and clears the cookie, so an unconfigured relay still drops a stale one. A new `COOKIE_KEY` leaves every refresh cookie unreadable, so everyone gets 401 and signs in once more. Locally they come from the environment or `packages/app/.env.local` (git-ignored). Signing in with the real Google needs `pnpm --filter @dineug/erd-editor-app exec vp dev --port 5175 --strictPort`: the registered redirect URI is `http://localhost:5175/api/auth/callback`, and plain `dev` takes 5173. `ERD_EDITOR_E2E_GOOGLE_OAUTH_URL` points the dev relay's token and revoke calls at a fake; the Pages Function never reads it.
- **Vite's `cors` middleware runs ahead of every plugin's**, so the dev adapter drops the headers it set and a relay answer carries the handler's alone. An `OPTIONS` preflight still gets Vite's 204 under `vp dev`, where Pages answers 405.
- **The `/gdrive` client judges the relay by its JSON contract alone** (`authMode.ts`): a 200 with `access_token` and `expires_in` is a token, a 401 with `error` means sign in, and anything else, the app's HTML, a 429 or 1027 page, a network error or ten seconds of silence, is an unavailable relay, remembered in `localStorage` (`@dineug/erd-editor-app/gdrive-relay-unavailable-until`) until the next UTC midnight, when Workers' free quota resets. Offline decides nothing. Until then no tab sends `/api/auth/*` anything, so the refresh cookie survives the fallback, until the person signs out: sign-out asks the relay too, so a shared computer keeps no cookie. Sign in, Reconnect Google, a tab shown again and a click in an expired fallback read the flag again, so a tab follows another into the fallback and tries the relay first past midnight.
- **`signOut()` resolves whether the relay confirmed it cleared the cookie**, for the screen to say so. In the fallback the token client's token is always revoked (GIS `revoke`), whatever the relay answers. A form POST to `oauth2.googleapis.com/revoke`, which ends the grant, revokes a live token only when the relay did not confirm (offline, 1027, ten seconds of silence) and no GIS revoke ran. Unconfirmed, `@dineug/erd-editor-app/gdrive-relay-logout-pending` in `localStorage` sends `POST /api/auth/logout` ahead of the next `/api/auth/token` of any tab or visit; while that logout fails no token is asked for and the relay counts as unavailable. A sign-in whose callback reported success clears the flag without a logout, since its cookie replaced the old one. Relay logouts run one after another, so the last one sent sets the flag.
- **A sign-out ends the sign-ins still open in every tab** (`signed-out` with `fromSignOut`): the relay's popup closes (`abandon`) and a token client request settles as cancelled. COOP can keep that popup open and a callback may already be under way, so each tab keeps listening for the attempt's `oauth-done` until its five minutes are up, and a success there logs out at the relay again. The `signed-out` of a renewal that met a 401 ends no sign-in, since the one still open brings the cookie back.
- **The access token lives in memory and on one channel** (`tokenManager.ts`). Tabs share it over `BroadcastChannel('@dineug/erd-editor-app/gdrive-token')` (`request`, `token`, `signed-out`) and renew under the lock `@dineug/erd-editor-app/gdrive-token-refresh`, five minutes before expiry and no sooner than five seconds after issue. A tab that needs a token first asks the others and waits 200 ms, also inside the lock, since channel messages and lock grants have no order between them; that is what keeps two tabs at one relay call. A hidden tab's timers are throttled, so `visibilitychange` reschedules them. A 401 for a token already renewed gets the new one, never a second renewal. The account comes from userinfo (`sub`, `email`), which gives up after ten seconds so a stall cannot hold the lock; a token of another `sub` from the channel or a renewal stops the tab as `account-changed`, except the sign-in that asked for it. A sign-out wins over what is in flight: a tab drops a relay, token client or userinfo answer asked for before a sign-out it saw, and adopts no token issued before the latest one (`issuedAt` in the shared session, when the relay or the token client was asked, `at` in `signed-out`). A tab's own sign-in wins the same way over a renewal asked for before it finished, so an account switch cannot stop its own tab as `account-changed`, and a tab that turns `account-changed` while it waits for the others asks the relay nothing. `/token`'s `scope`, the token client's and Drive's 403 `insufficientPermissions` each mean `scope-missing`; a grant that names no scope says nothing.
- **The fallback is the GIS token client alone** (`gis.ts`, loaded only on entering it, ten seconds before it counts as blocked), for sign-in, Try again and Reconnect Google. Past the recorded midnight Reconnect Google opens no popup: the fallback kept the cookie, so one `POST /api/auth/token` decides, a token signing in, a 401 leaving Sign in, an unavailable relay leaving Reconnect Google on the token client. It renews on the next click or keyup capture outside anything editable, checked on `composedPath()`; `<erd-editor>` counts as editable whole, since its closed shadow root hides its inputs from a listener on the window (happy-dom shows them, Chrome does not). A renewal nobody asked for that fails waits for Reconnect Google or any new token. **Mark every sign-in and sign-out control with `AUTH_CONTROL_ATTRIBUTE` (`data-gdrive-auth-control`)**: Sign in, Continue with Google, Try again, Reconnect Google, Sign out, Cancel. The window's capture listener runs before a button's handler, so an unmarked control's click would first open a renewal; one that then asks for a sign-in takes that renewal over, so its failure still shows.
- **The sign-in popup never trusts the DOM for its result** (`oauthPopup.ts`). It is opened inside the click with a fresh attempt id and takes only that attempt's `oauth-done`; when it closes, shows a same-origin page without the callback's marker (the SPA of a missing `_routes.json`, a 1027 page), runs five minutes or is cancelled, one `POST /api/auth/token` decides, a pending logout going first: 200 signed in, 401 cancelled, an offline answer an error that records nothing, anything else unavailable. With a logout pending, a close first waits up to `CALLBACK_GRACE_MS` (a second) for the attempt's `oauth-done`, so that logout cannot clear the cookie the callback just set. It keeps listening after a cancel until the five minutes are up, since COOP can close it early while the person finishes; a late `scope_missing` still stops as `scope-missing`. The callback page posts and closes at once, so its `oauth-done` can cross that token request: it wins, its failure over any answer (an older cookie included), its success over a 401 by asking once more.
- **Every Drive call names its `fields`** (`driveClient.ts`, `FILE_FIELDS` and friends): Drive answers `kind,id,name,mimeType` without them, and a save answer without `modifiedTime` turns every later save into a conflict. A content PATCH is `uploadType=media` with the file's own mimeType as `Content-Type`, which Drive otherwise takes as the new mimeType; a create is one multipart POST. The client retries nothing but one 401 with a renewed token; `withRetry` reruns a whole cycle after a network error, 5xx, 429 or 403 rate limit, three times at 1, 2 and 4 seconds plus jitter, and never a POST, which could create a file twice. Error messages carry the kind and Google's reason, never a file id or name.
- **One tab saves a Drive file: the holder of its lock** (`fileLeader.ts`). The lock and the file's channel share the name `@dineug/erd-editor-app/gdrive-file/<sub>/<fileId>`, so another account's tabs never meet. Opening reads the metadata and turns away a trashed file, a Google Doc, one over 64 MB and, after the download, anything `isEditorDocument` refuses (which lets the lock go and never saves); then an `ifAvailable` probe decides. The first tab loads from Drive; a later one queues for the lock and says hello (again at 0.5, 1.5 and 3.5 s). The leader acks every hello, `save-request`, `check-request`, `reload-request` and `rename-request` with a `status` first and does the work a task later, and answers hellos only once its editor holds the document and its baseline. While a tab holds the lock a follower never reads Drive itself: after 7.5 s without a snapshot it shows `waiting-snapshot`, whose "Open from Drive and take over" steals the lock, loads from Drive and sends `reloaded` to every tab. A leader still loading (a large download, an editor not yet mounted) answers the hellos it held once it can, and a `waiting-snapshot` follower still takes that snapshot. A load a steal or another tab's document overtook installs nothing: a tab checks after the download that it still leads and that its epoch has not changed. A follower whose `save-request` gets no ack in three seconds shows `waiting-leader` and "Take over saving", a steal that keeps its document. Without Web Locks every tab leads and a new tab waits half a second for a snapshot, so tabs share edits, but two PATCHes can overlap (Firefox 93–95; not addressed). A rename the sidebar asks for there goes to one tab: each open tab answers the `rename-request` with a `rename-claim`, and the asking tab sends it again with `to` naming the first claimant, the only tab that renames. Firefox holds a background tab's timers to a second, so the answer often comes late: a tab that loaded Drive alone meanwhile still takes it until it edits, saves or hands its load to another tab, and otherwise stays on its own load.
- **Edits cross tabs on the file's channel, one document load at a time** (`fileChannel.ts`, `documentController.ts`). Every message carries its sender's epoch, a new id for each load from Drive; `actions`, `saving` and `saved` of another epoch are dropped, since another load's save is another document, and only `snapshot` and `reloaded` set it. The element's four presence trackers (`editor.sharedMouseTracker`, `sharedFocusTracker`, `sharedSelectionTracker`, `sharedDragSelectTracker`) never go on the channel: one person's tabs do not show each other as peers. The editor attaches in the order the shared store needs, the value, then the subscription whose first handshake settles the LWW state, then the batches that came before it, and the screen makes the editor anew and attaches again whenever the epoch changes. An editor detached leaves its document behind, so one attached again within the same load starts from it, edits included, rather than from the load. Reload from Drive, from any tab, reloads in the leader and hands every tab the new document. `conflict` and `unconfirmed` travel as the leader's `status`, and the Drive list's news (a rename, a new file) on `@dineug/erd-editor-app/gdrive-files/<sub>`.
- **Every tab runs the save debounce, two seconds after the last change and ten at most** (`saveQueue.ts`); a follower's then asks the leader, whose cycle is one at a time: metadata, `modifiedTime` against the base, the lock asked again, `saving`, the PATCH, `saved`. Edits are told by `toDriveFingerprint`, so a zoom never saves, and the leader alone computes it: when it saves, when it is elected and for `beforeunload`. A `modifiedTime` that moved stops as `conflict`, or as `unconfirmed` while an attempt announced by `saving` is unaccounted for, since that PATCH may be what moved it. A retry reruns the whole cycle; a PATCH whose answer was lost or a 5xx keeps its attempt pending, so a retry that finds the file moved reads unconfirmed rather than PATCHing over it, one that finds it unmoved PATCHes again, and one Drive refused posts `failed`. A cycle that ends after its tab lost the lock leaves no stop behind, and a new leader takes its predecessor's view, including that a stop its own queue kept from an earlier term has since been resolved. `conflict`, `unconfirmed`, `deleted`, `readonly`, `account-changed` and `scope-missing` stop saving until the person acts; a token the fallback let expire pauses it until the token manager has one again, which also resumes `scope-missing` once the grant is back, and a leader that goes hidden saves at once. A `saved` older than the base never moves it back.
- **A steal is fenced three ways**: the old leader asks the lock again right before its PATCH (the flag a steal's rejection clears is the fence; `navigator.locks.query()` lists the thief's lock under the same name, so the query only lets a rejection already on its way land first); a PATCH that went out still posts `saved`, whoever leads by then, and any tab's `saved` moves the base, a leader whose content differs saving over it at once, which puts back what a stale PATCH overwrote; and the tab that stole holds every save of its own up to five seconds for the attempt the old leader announced, then checks the metadata and stops as `unconfirmed` if the file moved. A `saved` that reaches a leader stopped on `conflict` or `unconfirmed` moves the base but lifts the stop only after one metadata GET finds Drive at that base; a file past it stays stopped, as a conflict once no attempt is left to account for it. Check Drive (`checkUnconfirmed`, the user's call on 2026-09-25) downloads the file and compares its Drive fingerprint with the attempt's: the same moves the base and resumes saving, anything else is a conflict, and so is an `unconfirmed` whose attempt has since failed or settled, since the file moved without it. Nothing ever overwrites a change made outside the tabs.
- **A rename goes through the leader, after any save under way**: metadata `m0`, the rename, and the base moves to the rename's `modifiedTime` only when it was at `m0`, which `renamed { from, to }` lets every follower's base do too; otherwise the rename would turn the next save into a conflict. `renameDriveFile` renames a file this tab does not have open: the leader of a tab that has it (a held lock, or without Web Locks a `status` within two seconds), else Drive at once.
- **A follower warns on `beforeunload`** (`followerHasUnsavedChanges`) for a change in the last 500 ms, which its shared store may still hold, a change no leader `status` has followed, or a leader whose last status is `saving`, `failed`, `paused`, `waiting-leader`, `conflict` or `unconfirmed`; the leader compares fingerprints. `flush()` saves before a switch or a sign-out and says whether anything is left. A follower's flush sends a `save-request` with a `requestId` and waits for the leader's `flushed { requestId, saved }`, posted once the cycle it asked for ends, never for the ack alone, which comes before any save; no ack in three seconds or no answer in 30 is false, and a tab elected meanwhile saves itself.
- **fetch is bound where the client is assembled**, as for the relay: every `services/gdrive` module calls the fetch it is given without a receiver, and `window.open` likewise.
- **Limited Use keeps Google data out of analytics**: the gtag snippet adds its script only when the path is not `/gdrive`, and Sentry (`sentryScrub.ts`) traces no request to Google or `/api/auth/`, drops `ui.*` breadcrumbs and navigations with a query on `/gdrive` and fetch breadcrumbs to Google anywhere, and turns `/files/<id>` into `/files/[id]` and drops the query of every Drive, `/gdrive` and `/api/auth` URL it sends, the `Referer` included.
- **Hex `[hash:8]` output names are a contract with `sw.ts`**, repeated under `worker` because workers inherit no `build` output options; base64 hashes silently stop matching `CacheFirst`.
- Take `RouterProvider` from `react-router/dom`; the root export of the same name lacks the `flushSync` wiring and still typechecks.
- `run.tasks` is bespoke: its inputs name `packages/erd-editor/dist/**/*.d.ts` by hand, so a newly typechecked sibling goes into that list.

### Common Patterns

- `Component.tsx` beside `Component.styles.ts`; Emotion `css` prop, Radix Themes for widgets, `lucide-react` for icons.
- **Buttons are gray-first, size 2** (size 1 inside the compact update-prompt card). The one primary action of a screen or dialog is `solid` `color="gray"` `highContrast` (New schema in the empty viewer, Start session, Reload, Refresh); a destructive one is `outline` red (Empty trash, a confirmation's Delete, Stop session), or ghost red in a row, never solid: red-9 under a white label reads 3.9:1. Secondaries are `outline` gray, a dialog's Close / Cancel `soft` gray. The sidebar's New schema and Trash are ghost gray rows (`rowButton` in `SidebarItemView.styles.ts`) with their icon on the list's text edge. Solid jade is avoided: its white label reads 3.15:1.
- jotai modules export their state atoms but keep write-only `atom(null, …)` action atoms private behind `use*` hooks.
- Dates and relative times go through luxon, in the `en` locale like the rest of the UI copy.

## Dependencies

### Internal

`@dineug/erd-editor` — the element, plus the `engine.js` subpath whose `createReplicationStore()` the IndexedDB service runs headless and `emptyDocument` reads a new Drive file from. The Drive sync tests run `peer.js`'s `createPeerStore`, the same engine without a screen.

### External

- `dexie` stays at `^3` on purpose: it owns users' stored documents, so a major upgrade is its own verified change.
- `@trystero-p2p/nostr` / `mqtt` load dynamically; `ERD_EDITOR_NOSTR_RELAY_URLS` at build time points nostr at private relays.
- `luxon` does all date work: the list's date groups, the "Edited …" and "Deleted …" times, the trash's 30 days, the backup file name.
