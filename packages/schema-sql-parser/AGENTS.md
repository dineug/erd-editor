# schema-sql-parser

## Purpose

`@dineug/schema-sql-parser` (private) is a hand-written, permissive DDL parser: `schemaSQLParser(source, { database })` tokenizes SQL of any dialect into a flat `Statement[]` of nine kinds — `create.table`, `create.index`, `alter.table.add.{primaryKey,unique,foreignKey,default}`, `alter.table.alter.column.autoIncrement` and `comment.on.{table,column}`, which SQL Server's `EXEC sp_addextendedproperty` of an `MS_Description` yields too. Unrecognised input is skipped, so a real dump imports partially instead of failing; `CREATE TYPE`, `CREATE DOMAIN`, `CREATE EXTENSION` and `CREATE SEQUENCE` are among it. Its only consumer is `packages/erd-editor/src/utils/schema-sql-parser/`, which folds the statements into an `ERDEditorSchemaV3` document and names the document's database, the one option; only Databricks reads differently.

## For AI Agents

### Working In This Directory

- **Never throw on unrecognised SQL** — the loop advances `$pos` and continues; bailing turns a partial import into a failed one.
- **`$pos` (`RefPos = { value: number }`) is a shared mutable cursor.** Each parser leaves it just past what it consumed; off by one either loops forever or swallows a statement.
- Adding a statement kind is four edits: the parser file, the `Statement` union and `StatementType`, a matcher in `parser/helper.ts`, a branch in `parser/index.ts`.
- **One `ALTER TABLE name ADD` is dispatched once, whatever it adds** (`isAlterTableAdd`): the primary key, foreign key or default parser reads the statement when its first clause is one, then `alterTableAddUniqueParser` reads the same tokens again and returns one `alter.table.add.unique` per UNIQUE clause, so phpMyAdmin's `ADD PRIMARY KEY (...), ADD UNIQUE KEY ...` keeps every key. A CONSTRAINT symbol names only the clause it opens: a comma or ADD drops it. A UNIQUE after a word no branch claims belongs to the column the clause adds (`ADD [COLUMN] c INT UNIQUE CHECK (...)`) and keys nothing. A foreign key or a default after a first clause of another kind is still dropped, and so is `ADD KEY` / `ADD INDEX`; when the first clause is a foreign key, `alterTableAddForeignKeyParser` reads every one and keeps only the last, and when it is a default, `alterTableAddDefaultParser` reads that one alone. A group the parser skips (a CHECK, a foreign key's lists) also ends at a `;`, and so does a key list `indexColumnsParser` reads, the ALTER's or `CREATE INDEX`'s, which then keys nothing: one the source leaves open never swallows the statements after it. A `CREATE TABLE` whose parentheses do not balance still runs to the end of the source.
- **SQL Server's comments are `EXEC [[db.]sys.]sp_addextendedproperty` calls** (`add.extended.property.ts`), which SSMS writes with named arguments (`@name=N'MS_Description', @value=N'...', @level0type=N'SCHEMA', ...`) and the editor's MSSQL export (`packages/erd-editor/src/utils/schema-sql/MSSQL.ts`) by position. Only `MS_Description` is read (the owner's decision): on level 1 `TABLE` it is a `comment.on.table`, on level 2 `COLUMN` a `comment.on.column`, and anything else (another property, a view, an index, no name) yields no statement; the level 0 schema is dropped, as every qualified name keeps its last segment. The level 1 name is kept whole, though, since it names one table: the export writes a double-quoted table named `dbo.users` there as `'dbo.users'`, the name its `CREATE TABLE "dbo.users"` reads back as, and splits an unquoted one, its schema at level 0 and `'users'` at level 1; a file an older export wrote, naming an unquoted `dbo.users` whole there (`'user', dbo, 'table', 'dbo.users'`, which SQL Server refuses) beside a `CREATE TABLE dbo.users` read back as `users`, is matched by its last part (`findCommentTable` in `packages/erd-editor/src/utils/schema-sql-parser/index.ts`). Each argument is one token: the comment (`@value`) must be a string literal (`N'...'` or `'...'`; a number, `NULL` or `DEFAULT` there gives no statement), the property name and a level's type or name may be any name token (`dbo`, `[Orders]`, `N'Orders'`), and a `NULL` or `DEFAULT` (the parameter's own default, `NULL`) leaves its parameter unset, so one at level 2 still gives a table comment; an `@variable` for any argument but level 0's gives no statement, since a column's description read as its table's would replace that comment, and the list ends at the first argument no comma follows, an unquoted `GO` or the next statement; an operator after a value (`N'a' + N'b'`) drops the whole call rather than keep part of the text. The call needs `EXEC` or `EXECUTE`, and `isNewStatement` counts it, not any other `EXEC`: the editor's export writes it right after a unique key's `ALTER TABLE`, which would otherwise read on through it. `sp_updateextendedproperty` is not read.
- **pg_dump writes a serial column's default and an identity column's identity apart from its table**, after `CREATE SEQUENCE ... ; ALTER SEQUENCE ... OWNED BY t.c` for a serial one: `ALTER TABLE ONLY t ALTER COLUMN c SET DEFAULT nextval('s'::regclass)` and `ALTER TABLE t ALTER COLUMN c ADD GENERATED {ALWAYS | BY DEFAULT} AS IDENTITY (SEQUENCE NAME s ...)`. `matchAlterTableAlter` measures `ALTER TABLE [ONLY] name` before an `ALTER` that no `TABLE` follows, trying both readings of `ONLY` as for ADD, and `alterTableAlterColumnParser` reads every action of the list, each opened by `ALTER [COLUMN] c` right after the head or a comma at depth 0, where an `ALTER TABLE` is the next statement instead: one that sets a default `isNextvalDefault` reads as PostgreSQL's call of `nextval`, or adds an identity, yields `alter.table.alter.column.autoIncrement` with the table's last segment and the column; any other action (`SET DEFAULT 0`, MariaDB's `SET DEFAULT (nextval(db.seq))`, `DROP DEFAULT`, `SET NOT NULL`, `TYPE`, `ADD GENERATED ALWAYS AS (expr) STORED`) yields none, so the column keeps the default its `CREATE TABLE` gave it, and for one that yields the importer sets that column's `autoIncrement` and clears its default. The `CREATE SEQUENCE` and its `OWNED BY` are skipped, since the default alone makes the column auto increment. A `DROP` right after the column's name is stepped over, so the one of `DROP DEFAULT` ends no statement; any other statement word `isNewStatement` counts, there or later, ends it where no `;` comes first, so an `ALTER` the source cuts off before its action never swallows the next statement, and the `nextval(...)` is read only up to there. A statement word in the column's place is its name only before a word a PostgreSQL column action opens with (`ColumnActionWords`: `ADD`, `DROP`, `OPTIONS`, `RESET`, `RESTART`, `SET`, `TYPE`), as pg_dump leaves one PostgreSQL does not reserve unquoted (`ALTER COLUMN delete SET DEFAULT ...`); before anything else it opens the next statement, so an `ALTER [COLUMN]` cut off before its column's name ends there too, but for a `CREATE TYPE`, `ALTER TYPE` or `DROP TYPE` after it, which reads as a column and its `TYPE` action and yields no statement either way.
- **Keywords are unquoted `string` tokens compared case-insensitively**; every `is*Value` matcher refuses a `quoted` token, so `` `key` `` is a column and `KEY` an index. `--` and `/* */` comments never become tokens.
- **`column.default` is the whole `DEFAULT` expression as raw SQL**, which every exporter writes after `DEFAULT` (`statement/default.expression.ts`). It runs to the next column keyword (`isColumnKeywordValue`, a constraint state, `CHARACTER SET`, and the vendor options `ColumnKeywords` leaves out: `ROWGUIDCOL`, `SPARSE`, `MASK`, `STORAGE`, `COLUMN_FORMAT`, SQL Server's inline `INDEX`, a `TAG` before its list), comma, `)` or an unpaired `]` at depth 0, or to a `;` at any depth, and its first token is the value whatever it is (`DEFAULT NULL`); a `CASE` opens a level its `END` closes, as a paren does, so the keywords inside a bare `CASE ... END` end nothing. The `FOR` of `NEXT VALUE FOR` ends nothing, nor do the `WITH` and `WITHOUT` of a cast to a type `WITH [LOCAL] TIME ZONE` or `WITHOUT TIME ZONE`, while any other `WITH` or `WITHOUT` ends the default (T-SQL's `WITH VALUES`, MariaDB's `WITHOUT SYSTEM VERSIONING`). Oracle's `ON NULL [FOR INSERT ONLY | FOR INSERT AND UPDATE]` before the expression is skipped (`onNullSpan` in `create.table.ts`). The lexer drops whitespace, leaves a cast glued to its neighbours (`0::int`) and cuts `>=`, `<=`, `!=` and `=>` at their `=`, so the tokens are joined by rule: no space inside parentheses, around `.` and `::`, before a comma, inside an operator the lexer cut, or before an opening paren or an array subscript unless an operator stands before it (`now()`, `IN(1, 2)`, `ARRAY[1, 2]`, `- (1)`); one after a comma, before a T-SQL name in brackets (`NEXT VALUE FOR [dbo].[seq]`) and anywhere else (`now() AT TIME ZONE 'utc'`). The owner's decision takes off the parentheses around the whole of it (`((0))` gives `0`, `(getdate())` gives `getdate()`) and its outermost cast (`'draft'::character varying` gives `'draft'`). The parser takes that cast off a literal only, a prefixed one too (`NULL::character varying` gives `NULL`, `B'0'::"bit"` gives `B'0'`), since off anything else it changes or breaks what the default means (`ARRAY[]::text[]`, `('now'::text)::date`), and a cast inside stays (`lower('A'::text)`). A quoted token inside it goes back into its delimiters (`requote`), and a lone quoted value goes back into a string literal whatever its quotes (`toStringLiteral`: `'...'`, inner quotes doubled, or for Databricks a quote and a backslash escaped with a backslash, which Spark 4.0 and earlier read), since the lexer has stripped them and `PENDING` would read back as a name. `GENERATED BY DEFAULT AS IDENTITY` reads no default, its `IDENTITY` setting `autoIncrement`, and so does a default that is one call of `nextval('...')` (`isNextvalDefault`: a bare, unqualified `nextval`, unquoted in any case or in double quotes in lowercase, as `pg_dump --quote-all-identifiers` writes it, in parentheses or not, with nothing after its argument list, whose one argument is the sequence's name in a single-quoted literal, plain or with PostgreSQL's `E` or `U&` prefix, under any casts to a type name and parentheses: `'s'`, `'s'::regclass`, `'s'::"regclass"`, or the late-bound `('s'::text)::regclass` PostgreSQL writes back for a `nextval('s'::text)` default), a serial column's, whether inline or set apart from its table as pg_dump does (the owner's decision): every exporter writes its own auto increment for the flag and leaves the default out, and the sequence the call names has no place in the document. `nextval('s') + 1`, `nextval('s')::integer`, `nextval(N's')` and SQL Server's `NEXT VALUE FOR s` stay defaults, and so does MariaDB's `nextval(db.seq)`, which names its sequence bare (the owner's decision). MySQL's `ON UPDATE CURRENT_TIMESTAMP` ends the default and is dropped, since a column has no field for it. SQL Server's `ALTER TABLE ... ADD [CONSTRAINT n] DEFAULT expression FOR column`, the form SSMS scripts every default in, apart from its table, is written back the same way (`alter.table.add.default`, through `writeDefaultExpression`) but for a call of `nextval(...)`, which stays its default, since SQL Server has no such function; no column keyword ends it there, since no column option can follow it: only the `FOR` that names the column does (not that of `NEXT VALUE FOR`), a comma or a `)` nothing opened at depth 0, or a `;` or the next statement at any depth (a `GO` script), so `DEFAULT 'a' COLLATE Latin1_General_CI_AS FOR c` keeps its `COLLATE` and `c`; the importer sets that column's default from it, and the constraint name is dropped (the owner's decision). The editor's exporters put the parentheses back where a database reads the expression only inside them (`formatDefault` in `packages/erd-editor/src/utils/schema-sql/utils.ts`).
- **So does a quoted data type argument, in the delimiter it came in** (`requote`, a single quote by the same rule): `ENUM('a','b')`, `OBJECT("city" VARCHAR)`; `column.dataType` is raw SQL too. A user type's quoted name keeps its quotes, T-SQL brackets too whether the name needs them or not (`"MyType"`, `[sysname]`, `[dbo].[Order]`, where ORDER is reserved), a listed type's does not (`[int]` → `int`) but for PostgreSQL's `"char"` and `"bit"`, other types than `char` and `bit` (`unquoteTypeName`). A nested type's quoted tokens keep theirs too: `STRUCT<name: STRING COMMENT 'x'>`, `'it\'s'` for Databricks.
- **A type no list carries is read only where the type stands**, the token right after the column name (`typePos` in `statement/create.table.ts`): `mood`, `public.mood`, `hstore`. A single-quoted literal and the words in `ColumnKeywords` (`helper.ts`) are refused there, since a typeless column (SQLite, a computed `AS`, a `CREATE TABLE AS` column list) puts its first constraint in that place; a column keyword the parser meets there goes into that list, or it becomes the type. The list also ends a `DEFAULT` expression. `TAG` before `(` and `SORT` where the column ends are refused by position, since a PostgreSQL type may carry either name. Anywhere else an unknown word is an attribute (`INT UNSIGNED`).
- **A table constraint or index item yields no column**: `opensConstraintItem` in `statement/create.table.ts` names the tokens that open one; a new opener goes there. An item opened by a word a column may be named too (an unnamed `CHECK (...)` or `CHECK NOT FOR REPLICATION (...)`, `LIKE s`, `EXCLUDE USING`, `FULLTEXT ft (c)` or `SPATIAL (g)`, `PERIOD FOR`, `SUPPLEMENTAL LOG`) goes into `isTableItemWord` (`helper.ts`), told apart by what follows it; a column named `check` is quoted anyway.
- **A UNIQUE over several columns is one unique index** in every spelling (`UNIQUE (a, b)`, `UNIQUE KEY` / `INDEX n`, SQL Server's inline `INDEX n UNIQUE`, `CONSTRAINT [n] UNIQUE`, `ALTER TABLE ... ADD [CONSTRAINT [n]] UNIQUE [KEY | INDEX] [IF NOT EXISTS] [n]`, `CREATE UNIQUE INDEX`), named by its index name, else its CONSTRAINT symbol, else `''`; a flag on each column would be a stricter key. SQL Server's inline `INDEX n UNIQUE (...) [INCLUDE (...)] WHERE ...` reads its filter by the rule `CREATE UNIQUE INDEX ... WHERE` follows (below): unless the filter only drops NULL keys, the key is a plain index that keeps its name and columns, over one column too. One column sets the column's `unique` whatever its name, which is how the editor's own `UQ_<table>_<column>` comes back as the flag it was. `alter.table.add.unique` only reports the key; the editor's importer applies that rule to it. `matchKeyModifier` keeps `NULLS NOT DISTINCT`, `NONCLUSTERED` and `USING BTREE` from being read as the name. A column's own UNIQUE reads no name and no key list, since Oracle follows it with `USING INDEX (...)`. An ALTER's unique or primary key reports the index Oracle's `USING INDEX [schema.]index` names as `usingIndexName` (`matchUsingIndexName` refuses the index properties and constraint states that may stand there instead), and the primary key its CONSTRAINT symbol too. The importer reads the table's index of that name, else of the key's own name (SQL Developer exports `CREATE UNIQUE INDEX "UQ"` before `ADD CONSTRAINT "UQ" UNIQUE`), over the same columns as part of the key: a composite unique key is that index made unique, a one-column key and a primary key take it into their flags, since Oracle refuses to index one column list twice. A key with neither name (Oracle's system-named `ADD PRIMARY KEY` / `ADD UNIQUE`, whose index SQL Developer exports as `SYS_C...`) takes over, the same way, the index of the table, inline or from a `CREATE INDEX`, that covers its columns in the same order, unique or not and whatever its name, none included: Oracle enforces a primary or unique key through an index over its columns, a non-unique one too, rather than build another, so `CREATE INDEX ix_id ON t (id); ALTER TABLE t ADD PRIMARY KEY (id);` imports as the primary key flag on `id` and no index, and a second index a MySQL or PostgreSQL script keeps over those columns is taken over as well. Where the `CREATE INDEX` stands plays no part: the importer merges every `CREATE INDEX` before any ALTER key, so `ALTER TABLE t ADD PRIMARY KEY (id); CREATE INDEX ix_id ON t (id);` imports the same, since DBMS_METADATA's `CONSTRAINTS_AS_ALTER` output, followed by the table's dependent index DDL, writes each ALTER before the `SYS_C...` index of its key. An index over the key's columns in another column order stays one of its own. `create.table` reports in `keys` each primary key and one-column unique key the source names (by CONSTRAINT, or a one-column `UNIQUE KEY n` / `INDEX n UNIQUE`), and every key with no name that Oracle's `USING INDEX` follows, a composite unique key too, which stays in `indexes` as well; a key with no name that PostgreSQL's `USING INDEX TABLESPACE ts` follows is not reported, since DBMS_METADATA never writes `TABLESPACE` right after `USING INDEX` and Oracle refuses a second index over a key's columns (ORA-01408): a `CREATE INDEX` over the columns of that key is an index of its own; a column's CONSTRAINT names a key only when the key follows it at once. The importer reads a later `CREATE [UNIQUE] INDEX`, such as the one DBMS_METADATA writes for each key a table declares inline, as a key or index the table already has in two cases only: it carries the name of a key or of an index of the table over the same columns, in any order; or it covers, in their order, the columns of a key with no name that `keys` reports, one Oracle's `USING INDEX` followed (`PRIMARY KEY ("ID") USING INDEX ...` or `UNIQUE ("A", "B") USING INDEX ...`, then `CREATE UNIQUE INDEX "HR"."SYS_C..."`). Read so, it adds no index: an index takes its name when it had none, and its UNIQUE. It never folds into any other index with no name, an earlier `CREATE INDEX` without one or an inline `UNIQUE` without `USING INDEX`: `UNIQUE (a, b)` then `CREATE INDEX ix_ab ON t (a, b)` keeps both, and so do `CREATE INDEX ON t (a, b)` then `CREATE UNIQUE INDEX uq ON t (a, b)`. The editor's own exports write no `USING INDEX`, so an index over the columns of an unnamed key they write comes back as the index it was.
- **`CREATE [UNIQUE] [NONCLUSTERED] INDEX` reads what dump tools write**: `matchCreateIndex` measures the header through INDEX, `CONCURRENTLY` / `IF NOT EXISTS` and a missing name are skipped, the index and table names keep their last segment (pg_dump's `ON [ONLY] public.t`, Oracle's `"HR"."T"`), `USING btree` before the key list is skipped, and only the first ON names the table, never SSMS's `ON [PRIMARY]` filegroup. A `WHERE` makes a unique index a plain one that keeps its name and columns, since a partial key unconditioned is a stricter one, unless `isNullFilter` reads it as `key IS NOT NULL` over key columns, AND-joined, in parentheses that pair up: those rows are the ones the SQL standard's UNIQUE already lets repeat, SQL Server's usual filter for a unique nullable column.
- **A foreign key keeps its referential actions** in their SQL spelling (`ReferentialAction`), `''` where the clause is absent. `referencesParser` (`statement/create.table.ts`) reads the reference and the `ON DELETE` / `ON UPDATE` / `MATCH` clauses right after it, for a table-level `FOREIGN KEY`, an `ALTER TABLE ... ADD FOREIGN KEY` and an inline column `REFERENCES` (SQL Server and Snowflake may spell it `FOREIGN KEY REFERENCES`); a missing referenced column list leaves `refColumnNames` empty in all three: the referenced table's primary key, which the importer resolves only when it has one column, since `CreateTable` keeps no declared key order to pair a composite key by. `matchReferentialClause` spans the column list PostgreSQL lets `SET NULL` / `SET DEFAULT` name (`ON DELETE SET NULL (a_id)`), so a clause after it is still read, and still skips a clause nothing claimed, MySQL's `ON UPDATE CURRENT_TIMESTAMP` included.
- `helper.ts` merges all eight `dataType/` lists into one deduplicated uppercase set, so a type added to one vendor widens every dialect.
- **Type names match word by word, longest first**: write multi-word names in full (`TIMESTAMP WITHOUT TIME ZONE`); `matchDataType` returns the token span, argument lists and an array suffix (`[]`, `[3]`, `ARRAY`) included. Unlisted words in front of a listed type join it in the type's place, since SQLite takes any words as a type (`UNSIGNED BIG INTEGER`); with no listed type after them, only the first is the type (`hstore COMPRESSION pglz`). Each name is mirrored with a `primitiveType` in `packages/erd-editor/src/constants/sql/dataType/`; no test pins the parity, so change both lists together.
- **The `CREATE ... TABLE` header is measured, not counted**: `matchCreateTable` returns its span over a whitelist of modifiers (`OR REPLACE`, `TRANSIENT`, …), since scanning to the next `TABLE` would claim `CREATE VIEW ... FROM TABLE(...)`. `matchQualifiedName` does the same for an `ALTER TABLE db.schema.t` target.
- **The `ALTER TABLE ... ADD` head is measured too** (`matchAlterTableAddHead`): `ONLY`, a qualified name, SQL Server's `WITH CHECK` / `WITH NOCHECK` (every foreign key SSMS scripts) and `CONSTRAINT name`; the four `alter.table.add.*` parsers step over the words it allows.
- **Angle-bracket generics are rebalanced in the parser**: `<` / `>` are not break characters, so `matchNestedDataType` rejoins `ARRAY` / `MAP` / `STRUCT` spans and keeps their inner commas from ending the column.

### Testing Requirements

- `pnpm exec vp run --filter @dineug/schema-sql-parser --fail-if-no-match test` — `node` environment.
- A new end-to-end case is a `### ` section in `src/schema_sql_test_case.md` with a fenced `sql` block and a fenced `json` block; `index.test.ts` deep-equals `{ statements }`.
- `index.test.ts` also parses the root `data/sakila.sql` and pins its column, foreign key and index shape; the other `data/*.sql` dumps are manual only.

### Common Patterns

- AST nodes are fully populated with `''` and `[]` rather than optional fields.
- A qualified table name (`db.schema.t`) keeps its last segment in every statement parser.
