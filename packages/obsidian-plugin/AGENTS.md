# obsidian-plugin

## Purpose

The Obsidian plugin: a `TextFileView` that puts `<erd-editor>` in a tab for `.erd` / `.vuerd` files, and for `.erd.json` / `.vuerd.json` through a wrapped `WorkspaceLeaf.openFile`. Each vault window also serves the document hub `agent-hub` specifies, over `agent-hub-host`, so a coding agent running `@dineug/erd-editor-mcp` edits the diagrams open in that window live, as it does in VS Code; the Coding agents setting turns it off. The theme (appearance, gray and accent color) is a per-vault setting the editor's own theme builder changes too, as in VS Code. `dist/` (`main.js`, `manifest.json`, `styles.css`) is the whole plugin folder. It is released from `dineug/erd-editor-obsidian-plugin`, which carries this repository as a submodule, keeps a copy of `manifest.json` at its root for Obsidian's version check, and attaches `dist/` to a GitHub release tagged with the manifest version.

## For AI Agents

### Working In This Directory

- **Every worker is inlined.** Obsidian loads `main.js` alone, with no file beside it to spawn a worker from. `inlineUrlWorkers` rewrites each `new SharedWorker(new URL(…, import.meta.url))` / `new Worker(…)` in `erd-editor`'s and `replication-store-worker`'s `dist/` (the spelling `tools/vite/worker-url.ts` writes) into Vite's `?sharedworker&inline` / `?worker&inline`, and fails the build when one survives. A shared worker becomes a data URL, which `base64InlineWorkers` (`tools/vite/inline-worker.ts`, as in `erd-editor`'s UMD build) re-encodes under Chromium's URL cap; the replica starts from a blob. `worker.format` is `es` with `codeSplitting: false`: every one is a module worker, and none can load a chunk from a data or blob URL.
- **Node builtins stay external, with and without the `node:` prefix.** The renderer runs Node (`nodeIntegration`), and the hub and `@effect/platform-node` import `node:net`, `node:fs`, `node:fs/promises`, `node:os`, `node:crypto` and `node:path`. `builtinModules` holds almost no `node:` names, and a builtin left out resolves to Vite's empty browser stub with only a warning, which leaves the hub a `net` without `createServer` at runtime. `noBrowserExternal` fails the build when a chunk's `moduleIds` still name `__vite-browser-external`; it reads the module ids because the minified code keeps no trace of the stub.
- **`<erd-editor>` is defined once per window.** Importing the package defines it, and `customElements.define` cannot repeat, so `loadErdEditor` reaches it through `require()` (Rolldown then initializes it lazily) and keeps the module on a global symbol; a disabled-then-enabled plugin reuses it, and a new build takes effect after restarting Obsidian. The lazy form splits each inline worker's source from its declaration, which is why `readStringLiteral` also reads a bare assignment.
- **`.erd.json` / `.vuerd.json`**: Obsidian types a file by its last extension, and `registerExtensions(['erd.json'])` registers without effect. Registering `json` would claim every JSON file in the vault, so `main.ts` wraps `WorkspaceLeaf.prototype.openFile` with `monkey-around` and mirrors the core method (the `file` guard, `active` defaulting to the active leaf, `group`, `eState`). The suffix is matched without regard to case (`a.ERD.json` too), as the hub and the MCP server match a diagram file. The file explorer and the quick switcher still leave these files out unless Detect all file extensions is on.
- **Saving goes through the replica worker only**, as in the IDE hosts, so the tab never stringifies the document on the main thread, not even when it closes: the shared store's `subscribe` relays every action (`webviewReplicationCommand`), the replica posts `hostSaveValueCommand` 200 ms after the last change, and that value is what `requestSave` writes. A value with `changed` false, a scroll or zoom the file keeps nothing of, is neither kept as `replicaValue` nor saved, and `registry.valueSaved` counts it for the quiet wait without taking it as the content: kept, `getViewData` would hand it back, and the core save on close would rewrite a file an older release or another machine wrote, whose bytes the replica's value never has. Never serialize with `editor.value` in the plugin. The core `save` writes only when `getViewData()` differs from the text it last loaded or saved, and `getViewData` hands back the loaded text until the replica sends a value, so opening a file never rewrites it (a `.vuerd` would migrate, any file would reformat). **Every load starts a new replica**: `setInitialValue` does not cancel the replica's debounce, so a replica kept across a file switch or an outside reload could post the previous document after the next one loaded, and that value would be saved over it. A replica error shows a Notice.
- **Closing, switching files, reloading and quitting save the replica's last value.** An edit made within the replica's 200 ms before that is lost, as it is when an IDE webview closes. The core close saves through `getViewData` (`save(true)` from `onUnloadFile`). A quit or a reload does not wait out the 2 s `requestSave`, and a write started then as a quit task never lands on Windows, where the page unloads within milliseconds (see Obsidian versions differ here); a 1.13 reload fires no `quit` at all. So `main.ts`'s one `quit` handler and one `pagehide` handler call `saveBeforeExit` on every ERD tab, and the writer writes its unsaved value with `writeFileSync` to `adapter.getFullPath(file.path)` before the handler returns. The smoke's reload step and last step fail without it on Windows; the last step reads the files inside the quit event too, since on macOS, where Obsidian awaits a quit task, the end state alone would pass with the write left to a quit task.
  - `exitSave` (`tabSave.ts`) decides. No unsaved value (`hasUnsavedValue`: the writer only, never a waiting or unreadable tab, never before Obsidian loaded the file) writes nothing, so tabs of one file never both write. The tab's own write under way (`saving`) leaves the value to a quit task, `saveDocument`, which waits that write out and saves again: a sync write over an async one left the file mixed in 80 of 80 scratch runs. Otherwise it writes only when the file holds exactly `lastSavedData`, which the core save sets before its write starts, so a half-written file reads different too; anything else is an outside change the watcher has not delivered, which wins, as `isPlaintext` false makes it win. The file is read without one leading byte order mark, which `Vault.read` drops before `lastSavedData` holds the text: compared with it, a file opened with the mark read as an outside change, and a quit before the timed save lost the edit. An unreadable file, a failed write (`console.error`) or an adapter with no disk path falls back to the quit task.
  - After the write the tab sets `data`, `lastSavedData` and `dirty` as `TextFileView.save` does, so the pending `requestSave`, the core `quit` handler and the `pagehide` after a `quit` find nothing to write. It writes in place, as the adapter does (through a symlink, keeping the file's identity and permissions), and cannot tear, since the page's thread is blocked while it runs. The vault hears nothing of it (`TFile.stat` and the metadata lag it): the page is going, and should it stay, the watcher's `modify` finds `lastSavedData` equal.
  - The tabs write before the hub's `releaseSync`, in the same handler, so an agent never finds the lock gone while a tab is about to write the file in place and goes headless on it. A quit task left for a write under way runs after the lock is gone and may not land on Windows, and a tab closed a few ms before the quit is not covered: its closing `save(true)` cleared `lastSavedData` and is async.
  - Only a `quit` task turns 1.12's Reload app into closing the window, as Obsidian core does for its own unsaved views, and the plugin queues one only while a write is under way or the synchronous write falls back (an unreadable file, a failed write, no disk path).
  - `onUnloadFile` first calls the shared store's `flushStreamBuffers()`, which sends a stream group (a color, a memo resize) still held for its quiet period to the other tabs, which keep it. Keep `await super.onClose()` before `destroy()`, since the core close saves through `getViewData` and `destroy()` would empty the document first, and do not name a method `load` or `unload` — those are `Component`'s lifecycle.
- **Tabs of one file stay in step as edits happen**, the way `vscode-extension` broadcasts between webviews of one document. The registry groups the tabs by `TFile`; a tab's shared-store actions go to its own replica and to every other tab's shared store and replica at once. The first tab alone writes the file: another hands back `lastSavedData` from `getViewData` (`viewData` in `tabSave.ts`), so two tabs never write together. The writer's save coming back as a modify event is recognised (`handedByFile`, or the tab's own replica value) and not reloaded, which keeps undo; an outside change reloads every tab and drops `handedByFile`, which the file no longer holds.
- **A tab opened beside another starts from that tab's replica value once it holds every edit made there.** A value read right after an edit lags it by the replica's 200 ms, and the new tab would miss that edit for good and, once it became the writer, write the file without it. So `seed` waits on `registry.seedWhenQuiet`: while the document's quiet state is pending it waits for the replicas' saves, `JOIN_QUIET_CAP_MS` (500 ms) at most in all, as a join does, checks again on the turn it resumes, then loads the peer's value. With no other tab holding the document (the first tab closed during the wait, or every other one shows an unreadable file) it loads what the file's last writer handed Obsidian (`handedByFile`), else the text Obsidian last gave the tab: the modify event of that writer's close write can reach this tab after its wait ended, and would then be skipped as the writer's own save. That is why an outside change drops `handedByFile`: kept, a tab opened beside one an outside change made unreadable (a merge conflict) loaded the writer's earlier value editable and, once the writer, wrote it over the conflict; the smoke's step fails on a build that keeps it.
  - Meanwhile the tab has no replica and is not live, so neither the hub nor another tab injects into it, and its editor is read-only, since nothing would relay an edit made there (it shows `onOpen`'s empty canvas, or the previous file's diagram after a file switch); `loadDocument` restores the read-only state the file calls for.
  - A waiting tab hands back `lastSavedData` from `getViewData`, which Obsidian moves to every write of the file, never the text it opened with. So one that became the writer when the first tab closed during the wait writes nothing over what that tab wrote on close, adds no quit task, and `erd_save` finds nothing to write. Handing back its open-time text instead would write it over the first tab's close write and lose the edits in it, as the smoke's step showed with the wait hidden from `tabState` in a scratch copy. `tabSave.ts` holds these rules and `tabSave.test.ts` pins them.
  - A tab letting go of its file is no peer: `hasDocument` is false while its `onUnloadFile` runs. Obsidian's closing save (`save(true)`) calls `clear()` before it writes, which empties the tab's loaded and replica values, and the tab stays the file's first tab, shared store open, until the write returns; a tab seeding in that window took the empty text for the peer's value, loaded an empty diagram and, once the writer, wrote it over the file. It takes `handedByFile` instead, what the closing save is writing. The smoke's slow-close step, with the write held back 3 s, loads an empty diagram without the flag.
  - Leaving the file cancels the wait, and an outside change loads the file's version at once. Edits that go on in the other tab past the cap, with no replica save between them, can still be missed, as a join can miss them, and an edit the first tab made within its replica's 200 ms before it closed is lost, as on any close. A stream group still held in the other tab reaches the new one once it subscribes.
- **The theme is a per-vault setting, saved as `vscode-extension` saves its own.** `data.json` holds `appearance` (`auto`, `light` or `dark`, default `auto`), `grayColor` (default `slate`) and `accentColor` (default `indigo`) beside `agentHub`; `readSettings` takes only the three appearances and webview-bridge's `GrayColor` / `AccentColor` values, and falls back to the default for anything else.
  - Every tab sets `enableThemeBuilder` and listens for `changePresetTheme`; `ThemeHost.picked` saves the pick, and `applyTheme` re-themes every ERD leaf of the vault at once (`getLeavesOfType`, popouts included). `onload` applies the loaded settings once more, for tabs restored with the layout before they loaded.
  - `auto` is the editor's `system`, the theme builder's System: `setPresetTheme` gets `system` for it, and `setSystemAppearance` the light or dark Obsidian's `theme-dark` body class names, which the `css-change` handler sends again whatever the setting, since the builder can pick System at any time.
  - `themeFromBuilder` takes the builder's pick as it comes, its `system` saved as `auto`, so a color picked under System keeps `auto` and Light or Dark replaces it, the one Obsidian shows now included. `vscode-extension` and the IntelliJ plugin save the pick the same way.
  - The settings tab changes the same three values and re-themes at once; `onExternalSettingsChange` (a sync changing `data.json`) re-reads the settings, re-themes and sets the hub switch.
- **The shared store belongs to the file, not the tab.** It is created after the document loads and destroyed when the tab leaves the file: its first `subscribe` sends `getLWW`, and the other tabs answer with `mergeLWW`, so the new tab's clock and last-writer-wins state match theirs and its first edit is not taken for an older one. Subscribing before joining (in `onOpen`) sent that request to no one.
- **Unreadable files** (not JSON, or neither `doc` nor `canvas` at the top) open read-only and `getViewData` returns the file text, so a merge conflict or a cut-off sync is never replaced by an empty diagram. `readonly` still lets viewport actions through, which is why the text, not `editor.value`, is handed back.
- **`isPlaintext` is false**: with the default, an outside change during an unsaved edit is merged into the JSON as text. False takes the file's version and drops the unsaved edit.
- **The schema GC runs after a load**, so a document that is inconsistent (FK flags with no relationship, for one) can change without an edit. The smoke fixture is kept consistent for that reason.
- **`styles.css` overrides `contain: strict !important`** on diagram leaves only. Layout or paint containment makes the leaf the box `position: fixed` resolves against, and the editor places its menus with viewport coordinates, so they landed offset by the leaf's position.
- **The editor's shortcuts reach it while its tab is active.** Obsidian's keymap listens for `keydown` on the window in the capture phase, and a key that matches a command's hotkey goes to that command and is prevented and stopped before the page sees it, whether or not the command applies there. `Alt+Enter` (add column) is Follow link under cursor, `$mod+K` (search) Insert Markdown link and `$mod+F` (Find and Replace) Search current file, and a hotkey the user sets can take any other shortcut. The workspace asks the active leaf's `view.scope` first (Obsidian's own canvas view keeps its keys the same way), `Scope.handleKey` answers with the first matching registration's result, and the keymap prevents the key only when that is `false`.
  - So `ErdView` sets `this.scope = new Scope(this.app.scope)` and registers every press of the loaded module's `createKeyBindingMap()`, the element's defaults, never a copy, with a handler returning `true`: Obsidian runs none of its commands for the key and lets it through to the editor. `scopeKeysOf` (`keys.ts`) spells them as the keymap matches them, the event's key code read as a letter, digit or name: `$mod` is `Mod`, `Control` is `Ctrl`, `KeyK` is `K`, `Digit1` is `1`, `Space` is `' '`, `Equal` is `=` and `Minus` is `-`.
  - Every other hotkey (the command palette, the quick switcher, closing a tab, settings) falls through to `app.scope` and works in the ERD tab. The scope holds only while the ERD leaf is the active one, wherever focus is in it; a modal or a menu pushes a scope of its own, which the view's never reaches.
  - `Mod+S` is not the editor's, so it reaches Obsidian's Save current file (`editor:save-file`), which saves whichever `TextFileView` is active, the ERD tab included: the writer writes its replica's last value at once, and another tab of the file writes nothing, since its `getViewData` is what the file holds. Nothing in the plugin registers it. A save pressed within the replica's 200 ms of an edit writes the value before it, and the autosave writes the edit 2 s later.
  - A module an earlier plugin version loaded into the window, which `loadErdEditor` keeps until a restart, has no `createKeyBindingMap`; its tabs then register nothing and Obsidian's hotkeys win.
  - The smoke's `Alt+Enter` and `Mod+K` steps fail on a build without the scope, on 1.12.7 and 1.13.7, and its `Mod+S` step passes on both builds.
- **The icon is the logo's two tables and their link in lines** (`icon.ts`), the IntelliJ plugin's file icon on Lucide's 24 grid, added with `addIcon` on load and removed on unload. `addIcon` wraps the content in `<svg viewBox="0 0 100 100">` and nothing more, so the content sets `fill`, `stroke` (`currentColor`) and the joins itself and scales the grid up; it names no `stroke-width` and inherits Obsidian's `--icon-stroke` (2 in a tab header, 1.75 in the ribbon) in the grid's units, as the Lucide icons beside it do. The page outline of Lucide's `file` left no room at a tab's 14 px for the link, and a filled page with the tables cut out was the heaviest icon in the tab bar.
- Export goes through `setExportFileCallback` into `fileManager.getAvailablePathForAttachment`, with the characters Obsidian refuses in a name replaced.
- `isDesktopOnly` is true: nothing has been checked on mobile, Chrome on Android has no SharedWorker, and the hub needs Node. Popout windows are unsupported: `<erd-editor>` is defined in the main window's registry only, and on 1.12.7 a tab opened in a popout got an element with the editor's API whose rendering threw `Sharing constructed stylesheets in multiple documents is not allowed`; nothing past that was checked. `applyTheme` still reaches such a tab.

### The coding-agent hub

- **One hub per vault window**, in the plugin instance of that window. Vault windows run in renderers of their own, so the lock and socket are `~/.erd-editor/ide/<renderer pid>.json` / `.sock`; a popout shares its window's pid and plugin instance. `createObsidianHost` names the ide `obsidian`, its one folder the native real path of `FileSystemAdapter.getBasePath()`, and has no folder event (a window has one vault). The lock's `version` is `this.manifest.version`, never a constant. Every agent-visible message is `vscode-extension`'s where the situation is the same, both hosts building it with the same constructor from `agent-hub-host`'s `documentRules.ts`; the one that names the host says Obsidian (`Obsidian could not open <path> in the ERD editor: …`). The read-only view refusals name no editor and differ from VS Code's because the situation does: here the read-only case is a file the editor cannot read, there a git or merge view.
- **`src/hub/` imports nothing from `obsidian` at runtime**, only its types: the `obsidian` package ships no runtime, so everything the hub needs of Obsidian comes in through `HubTab` (which `ErdView` implements) and `HubVault` (which `main.ts` builds). That is what lets its specs run in Node. `imports.test.ts` reads `require` and dynamic `import` calls as imports too.
- **The registry lives from plugin load**, before any tab can open and whether or not the hub listens, so `observedVersion` covers every emission. A document is one `TFile` with the tabs showing it, keyed by the file's native real path once `realpath` resolved (a rename bumps a generation, so a late step of the old path lands nowhere). A tab is ready once loaded with its shared store open on a readable document and its path resolved; only ready tabs count for `openDocument`, `applyActions` and waiters. Tabs showing a file the editor cannot read make it a read-only view: `join` answers its text with `readonly`, edits and `save` answer `readonly`, and `openDocument` answers at once instead of waiting 5 s.
- **Content and quiet waits.** The registry mirrors each document as its first load and then every replica save, which is what a `join` hands a peer. A change notes the live tabs it reached; a join waits for their saves (500 ms cap) and captures content and `observedVersion` in one step, the window ending on a timer after the response, and `save` waits 2 s at most, answering `saved: false` and writing nothing if no replica saved the edit. An outside change that reloads the tabs is a new document: its peers hear `documentClosed`, the quiet state starts over, `observedVersion` stays monotonic. A rename tells the peers `documentClosed` for the old path and lists the new one.
- **`listDocuments`** lists the open documents first, then every ERD file of the vault (`erdFileProblem` filters `vault.getFiles()`), each by real path, once. `dirty` is the writer's content against what the file last took, or a quiet wait still pending; `active` is the file of the ERD tab that took focus last.
- **`openDocument`** answers at once for a ready tab; otherwise it registers its waiter before any IO, creates through `vault.create` when asked (an existing file is left as it is, a missing folder answers `notFound`), loads a deferred leaf already showing the file, or opens a background tab (`getLeaf('tab').openFile(file, { active: false })`). Obsidian's default Always focus new tabs still focuses it, and the tab's load takes it for the active document, so `main.ts` hands focus back to the leaf that had it and puts the active document back (`registry.keepActive`): from a note, which no ERD tab hears take focus, the agent's background tab would otherwise stay `active`. A real path maps back to a `TFile` relative to the vault folder's real path, else by scanning the ERD files' real paths.
- **Saving an agent edit.** The writer tab keeps saving every replica value about 2 s later, agent edits included, as Obsidian saves the user's: in one document the two cannot be told apart. `erd_save` writes at once through the writer's `TextFileView.save` and answers whether the file then holds the tab's value; the MCP server's wording states the difference from VS Code, which keeps agent edits unsaved until `erd_save`.
- **The Coding agents setting** is the last row of the settings tab (`PluginSettingTab.display()`, since the manifest's `minAppVersion` predates 1.13, where `getSettingDefinitions` arrived), after the three theme dropdowns: one toggle, on by default like the extension's setting, kept per vault in `data.json` through `loadData` / `saveData`, re-read on `onExternalSettingsChange`. Off, the hub writes a `hub: false` lock with no pipe, which refuses agent writes naming the setting; on, it listens again.
- **Lifecycle.** `onunload` (disable, update) runs `HubLifecycle.stop`: every peer hears `documentClosed` for every path it joined or read, those frames drain (1 s at most), then the runtime disposes, for 5 s at most (`DISPOSE_TIMEOUT`, which `runtime.test.ts` pins on a listen that never returns), so a close a stalled hub task holds never keeps the next instance from starting. The timeout gives up only while `createHubRuntime` keeps the hub layer off `Layer.merge`, `Layer.mergeAll` and array provides, whose forked close it never reaches (`Layer.tap` and `Layer.provide` today; the `Layer.mergeAll`s of the documents and of `main.ts`'s machine build beside the hub, not around it; `agent-hub-host`'s AGENTS.md, `close` and `releaseSync`). `onunload` is not awaited and the next instance's `onload` can run in the same millisecond on the same pid, so the closing promise sits under a `Symbol.for` key and a new instance starts its hub only once it settled. Each close is chained onto the one before it: an instance stopped while it still waited for an earlier close has no hub and closes at once, and a third starting after it would otherwise bind the pipe and write the lock that the first one's close then deletes. Both hold only up to that give-up, past which the old close runs beside the next instance and can delete that instance's lock and, on POSIX, its socket file (`agent-hub-host`'s AGENTS.md, An earlier hub of the same pid, has what and for how long); on Windows the next instance cannot listen while the old one holds the pipe, and serves no agent until the Coding agents setting is turned off and on. A window closing, reloading or quitting never runs `onunload`: `main.ts`'s one `workspace.on('quit')` and one `pagehide` handler write every tab's unsaved value first, then call `releaseSync`, which deletes the lock and the socket before it returns. Never add a quit task for the hub.
- **Obsidian versions differ here** (measured on macOS unless a bullet names Windows). The `/Applications` bundle is 1.12.7, but Obsidian loads a newer `obsidian-<version>.asar` from its user data folder over it (1.13.7 on this machine), and an instance on a fresh `--user-data-dir` starts on the bundle and fetches the update for its next launch.
  - 1.12.7: `quit` fires on a window close, a reload and an app quit, and any quit task turns a reload into a window close, which the plugin queues only while a tab's write is under way or its exit write falls back (an unreadable file, a failed write, an adapter with no disk path). The synchronous exit write has not been run on 1.12.7: its `quit` is taken to fire inside `beforeunload` as 1.13.7's does, which the smoke on the macOS bundle checks.
  - 1.13.7: `quit` fires only when the window is closing (`sendSync('is-closing')`), synchronously inside `window.onbeforeunload`; a reload fires none, which is why `pagehide` also writes the tabs and releases (the smoke sees the lock go before the new one is written, and the file keep an edit made 400 ms before the reload).
  - Windows, 1.13.7 from the installer (2026-09-27): the page unloads 2 to 24 ms after `beforeunload` although Obsidian prevented it for its quit tasks, so no async quit task lands, Obsidian's own for notes included, and a quit ends the process. On every platform Obsidian's main process destroys a closing window 3 s after `close`, whether or not its quit tasks finished.
  - 1.13.7: a second `app.changeTheme` within about a second of the first, before Obsidian wrote the first to `.obsidian/appearance.json`, was undone in some tries (the body class and the config back on the first theme). The smoke waits for the file to hold each switch before the next.
  - Both: a quit that runs a quit task ends in `window.close()`, so on macOS the app process stays up without a window; the plugin adds one only while a tab's write is under way or its exit write falls back, and the smoke stops the pid it spawned. `TFile.saving` is a flag in 1.12, which overlapping writes can leave set, and a count of writes under way in 1.13.
  - 1.13.7 opens Settings in a popout window. A hub restarted from there (the Coding agents toggle, or enabling or updating the plugin in Community plugins) can leave uncaught `illegal access` errors, and in some tries the first agent call after it waits for its `hello` until the MCP server's 30 s timeout; the next call recovers, and nothing is lost. The cause is not found. Turned on through `setAgentHub` with no popout open, the hub answered every hello in ten tries, which is why the smoke toggles it that way and looks at the settings tab only before any restart. A theme dropdown restarts nothing, and the smoke picks those in the popout. Yet one smoke run on 1.13.7 in about ten also caught three `illegal access` page errors with no hub restarted from the popout, and the runs after it none. The source is unknown, so the no page errors step can still fail this way on 1.13.7: rerun it before taking it for a regression, and read the `(after: …)` step each error names. Known limitation.
- **Files outside the vault**: the hub writes its lock and socket under `~/.erd-editor/ide` and deletes the ones dead windows left there; it listens on a local socket only and makes no network request. The plugin repository's README discloses this, as Obsidian's developer policies ask.
- **No hub in a Flatpak.** Flathub's Obsidian runs in a pid namespace of its own with the home folder shared, so no pid outside is alive in it and its own pid means nothing outside: its startup sweep would delete every live window's lock and socket, and an MCP server outside would delete its lock as dead and write its open files behind it. `pidSandbox` (Linux, `FLATPAK_ID` or `/.flatpak-info`) stops `startHub` before any runtime is built: no lock, no sweep, no socket, and agents edit the files on disk as with the plugin off. While Coding agents is on, a Notice says so on load and the setting's description says why; turning it off stops the Notice. Not checked in a real Flatpak.

### Testing Requirements

The `test` task (`tsc --noEmit`, then Vitest) and `test:coverage` cover `src/hub/`, `src/keys.ts`, `src/settings.ts` and `src/tabSave.ts` (perFile 80% on all four metrics): `main.ts`, `ErdView.ts` and `loadErdEditor.ts` run only inside Obsidian (the `obsidian` package ships types and no runtime, and the editor needs a window), and the smoke covers them, so whatever they decide that can be pure goes into a measured module. `settings.test.ts` pins the defaults, the fallback of unknown values, `editorTheme` and `themeFromBuilder`; `tabSave.test.ts` what a tab hands Obsidian to save, a tab waiting to load among them, and what `exitSave` does as the window goes; `keys.test.ts` how each spelling the editor's shortcuts use becomes a scope key. The specs run the registry and the handler over `createHubHarness`: `registry.test.ts` (tabs, relays, quiet waits, seeding, content, the lock's documents, shutdown), `join.test.ts` (the join window, and over a real socket, a named pipe on Windows, the response ahead of queued actions), `handlers.test.ts`, `host.test.ts`, `lifecycle.test.ts`, `runtime.test.ts` (over its own memory doubles of `agent-hub-host`'s `HubEnvironment`, `HubListener` and `LockFile` services, never the node layers, which would write a lock under the real home) and `imports.test.ts`. CI runs both, and the build, `tsc --noEmit` first; `smoke` is the check that the plugin works, run by hand on macOS or Windows with Obsidian installed.

```
pnpm exec vp run --filter @dineug/erd-editor-obsidian-plugin --fail-if-no-match build
pnpm exec vp run --filter @dineug/erd-editor-obsidian-plugin --fail-if-no-match test
pnpm --filter @dineug/erd-editor-obsidian-plugin test:coverage
pnpm exec vp run --filter @dineug/erd-editor-mcp --fail-if-no-match build   # the smoke's agent
pnpm --filter @dineug/erd-editor-obsidian-plugin smoke
OBSIDIAN_ASAR="$HOME/Library/Application Support/obsidian/obsidian-1.13.7.asar" pnpm --filter @dineug/erd-editor-obsidian-plugin smoke
SMOKE_KEEP=1 pnpm --filter @dineug/erd-editor-obsidian-plugin smoke   # leaves the app on CDP port 9333
```

`smoke` copies `dist/` into a throwaway vault and starts Obsidian with its own `--user-data-dir` (your vaults are untouched), attaching over CDP only once that instance's `DevToolsActivePort` and vault folder are its own. It prints the Obsidian version it ran, then checks:

- opening every extension, saving through `Alt+N`, two tabs of one file editing in step, a tab split within 100 ms of an unsaved edit waiting read-only, starting with it and writing it once the first tab closed, the same wait with the first tab closing during it and the waiting tab, now the writer, closing without writing (the sequence that loses an edit on a build whose waiting tab hands back its open-time text; the step first waits until the tab's saved text is the first tab's close write, without which such a build passes too), closing without an edit, closing before the timed save, closing two tabs of one file (the file's `modify` events counted: exactly one write), a tab opened 200 ms after the writer closed with an unsaved edit while that close write is held back 3 s (it starts from the edit, and the file ends with it), the unreadable-file fallback, a tab opened beside one an outside change made unreadable after the writer saved (read-only, not live, and closing both leaves the text), an outside change during an edit, `openFile(null)`, the create command and the containment override;
- the keys Obsidian binds to its own commands, pressed through Playwright's keyboard, whose events pass through Obsidian's window listener: in an active ERD tab `Alt+Enter` adds a column to the table `Alt+N` focused (in the editor, then in the file), `Mod+K` opens the editor's quick search (read off its shadow root) and `Escape` closes it, `Mod+F`, Obsidian's Search current file, does the same with its Find and Replace, `Mod+S` writes an edit before the 2 s autosave would, and `Mod+P` still opens Obsidian's command palette;
- the theme, on what two open diagrams paint: by default they follow Obsidian's light or dark (`app.changeTheme`) and switch with it; the settings tab's dropdowns re-theme both at once and save to `data.json`, a named appearance stays when Obsidian switches and `auto` follows again; one diagram's theme builder saves its pick and re-themes the other (a color keeps `auto`, the other appearance replaces it, System brings `auto` back); `data.json` written on disk, as a sync writes it, re-themes both. The element's shadow root is closed, so the smoke reads the `:host` custom properties off the element (`--gray-color-1`, `--accent-color-9` through `getComputedStyle`) and compares them with `@radix-ui/colors`, resolved from `erd-editor`'s package, the palette the editor builds its theme from; it clicks the builder through the DevTools protocol (`DOM.getDocument` with `pierce`, then a function run on the shadow root);
- the hub through the real `packages/mcp-server/dist/erd-editor-mcp.js`, spawned over stdio in the vault folder with your `HOME`: the lock (`ide` `obsidian`, the socket beside it, `0600` in `0700`, the vault's real path, the open documents), the settings tab's Coding agents toggle, `erd_list_documents`, `erd_open_document` on a closed file (a background tab, focus kept), the same from a note (focus back on the note, the diagram last in focus still the one `erd_list_documents` names active), `erd_add_table` shown live before the file has it, `erd_save` writing at once, the 2 s autosave of an agent edit, a user edit reaching the agent, the last tab closing (the closed note, then a write that reseeds and reopens the tab), the setting off (a `hub: false` lock, a write refused naming the setting) and on, the plugin disabled (the lock and the socket gone, the agent editing the file with the `no longer serves it` note) and enabled again, and `app:reload` 400 ms after an edit in an ERD tab (the window reloads under the same pid, the file holds the edit the 2 s autosave had not written yet, the lock goes before the new one is written, the agent edits live again), with Playwright detached around the reload;
- a file written the way releases before the origin and the locks wrote it, so it opens locked: two clicks on the zoom-in button (the readout read off the shadow root) and three wheel scrolls leave its bytes as they were through the 2 s autosave and the tab closing (without the replica's `changed` flag, both write the replica's value over them);
- no page errors (each names the step reported before it), then, last, quitting 400 ms after an edit in each of two new tabs: a `quit` listener the smoke adds after the plugin's reads both files inside the event and must find each edit there, each file keeps it once the window is gone, and the lock and the socket are gone.

A run with a failed step prints what the MCP server wrote to stderr, its log, at the end.

Options: `OBSIDIAN_BIN` points it at another install than `/Applications/Obsidian.app` on macOS (Windows below); `OBSIDIAN_ASAR` copies an `obsidian-<version>.asar` into the run's user data, where it loads over the bundled version (it only reads the file you name); `SMOKE_PORT` (9333); `SMOKE_OUT` keeps `smoke.png` in another folder; `SMOKE_KEEP=1` leaves the app running and skips the quit. The run deletes its `mkdtemp` folder at the end unless kept, and at start every `erd-obsidian-smoke-*` folder earlier runs left in the temp folder, except one a running Obsidian still uses. Its instance writes a real lock and socket under `~/.erd-editor/ide` while it runs; the run checks they are gone and deletes only files of its own renderer pid. Never run it with another `HOME`: macOS then asks for a keychain on every launch. It stops only the Obsidian it spawned, through that instance's CDP or its pid. To try a build in a vault of your own, link `dist/` in as `<vault>/.obsidian/plugins/erd-editor`.

On Windows `OBSIDIAN_BIN` defaults to `%LOCALAPPDATA%\Programs\Obsidian\Obsidian.exe`, where the installer puts it, and an `OBSIDIAN_ASAR` comes from `%APPDATA%\obsidian\`. The lock names the named pipe `\\.\pipe\erd-editor-ide-<renderer pid>`, which the run looks up in the `\\.\pipe\` listing and never stats, since a stat of a live pipe connects to it as a peer; the lock step checks no modes, which Windows does not keep. Earlier runs' command lines come from CIM, Windows having no `ps`. A quit ends the process and its debugging port with it, where macOS keeps the app up without a window, and the work folder is deleted with retries, since Electron's helper processes let go of its files after the main pid exits. Measured on Windows 11 with the Obsidian 1.13.7 installer (2026-09-27): 55 steps pass, and the no page errors step fails on a product finding, reported rather than gated: `illegal access` page errors after the theme step, in each of the runs measured. A build without the exit write fails the reload step (the file without the edit) and the quit step (neither file holding its table, in the quit event or after it).

## Dependencies

### Internal

All devDependencies, bundled: `@dineug/erd-editor` (the element), `@dineug/erd-editor-replication-store-worker` (the replica), `@dineug/erd-editor-webview-bridge` (the replica's commands, and the `GrayColor` / `AccentColor` values the theme settings allow), `@dineug/erd-editor-agent-hub-host` and `@dineug/erd-editor-agent-hub` (the coding-agent hub). `obsidian` (types only; external at runtime), `monkey-around`, `effect` and `@effect/platform-node` (bundled; node builtins stay external), `@types/node` (`types: ["node"]`), `@playwright/test` for `smoke`'s `connectOverCDP`.
