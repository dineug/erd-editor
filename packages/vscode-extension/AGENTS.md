# vscode-extension

## Purpose

The published VSCode extension (`vuerd-vscode`, publisher `dineug`) — the Node-side host. It registers the `editor.erd` custom editor for `*.erd`, `*.erd.json`, `*.vuerd` and `*.vuerd.json`, owns the document bytes, serves the bundle `vscode-webview` builds into `public/`, and answers the `webview-bridge` commands. `private: true`; published through `vsce`.

## For AI Agents

### Working In This Directory

- `package.json` is the manifest. Its src ↔ manifest invariants are unit-asserted: `src/constants/viewType.test.ts`, the defaults check in `src/configuration.test.ts`, the commands and menu entries in `src/extension.test.ts`, the `agentHub.enabled` key and default in `src/hub/config.test.ts`, and in `src/hub/autoOpen.test.ts` `ERD_FILE_EXTENSIONS` against `customEditors[].selector` and `ERD_FILE_GLOB` against `activationEvents`.
- `engines.vscode` (`^1.101.0`, the first release running on Node 22) is the floor. `.vscode-test.mjs` derives its `minimum-supported` run from it; `build.target: 'node22'`, `@types/node` `^22` and `@types/vscode` `^1.101` are raised by hand with it, and nothing gates them.
- **`dist/extension.js` is a contract**: `main` is `./dist/extension`, so a `.cjs` emit never activates. Everything but `vscode` and builtins inlines because the VSIX ships no `node_modules` (`--no-dependencies`); a bare `require` left in the bundle fails activation.
- **Minified, and the VSIX carries no map.** Vite writes no map unless asked and leaves an `ssr` build unminified, so `build.minify: true` is what strips this bundle and `build.sourcemap` is now `false`; `rolldownOptions.output.minify` on top emits the same bytes (sha256 equal, measured 2026-09-23), so only the one option is set. The reason is Effect. Measured 2026-09-23 when that was decided, while `@dineug/erd-editor-agent-hub` was the only thing pulling effect in: the bundle had gone 72,473 B → 424,302 B unminified, minification brought it to 116,599 B (38,494 B by the `gzip -9` command line, 38,495 B at the `zlib` level 9 used below), and a map of that would have been 2,082,178 B; the VSIX went 1,851,779 → 1,378,150 B, 18 files → 17. The hub has run on effect since, so the Build bullet under Testing Requirements holds today's size. `.vscodeignore` holds `dist/**/*.map` so that stays true structurally: the build task's `tsc` step snapshots `dist/**` before `vp build` empties it, so an entry recorded while maps were on restores one beside the minified bundle on every later cache hit, and `vsce` packs whatever sits in `dist/` (measured 2026-09-23: 17 files with such a map present). A stack trace from the Extension Host therefore names `dist/extension.js` and a column on one of its few lines: reproduce with such a local build rather than reading the shipped trace.
- File support lives in two manifest places — `activationEvents` (`workspaceContains:**/*.{erd,vuerd,erd.json,vuerd.json}`) and `customEditors[].selector` — and their extension sets must stay equal: the hub's lock exists only once the extension is active. A glob of `**/*.{erd,vuerd}` alone leaves a folder holding only `.erd.json` / `.vuerd.json` files with the extension inactive and no lock; the `erd-json-only` Extension Host run asserts such a folder activates it.
- The hub serves only while `isHubEnabled()` (`src/hub/config.ts`): the window is trusted and `dineug.erd-editor.agentHub.enabled` (default `true`) is not off. It re-applies on `onDidGrantWorkspaceTrust` and on a change to that setting; off or untrusted, it still writes a `hub: false` lock.
- The hub never throws at the editor: every failure goes to `console.warn` under `[erd-editor hub]`. `activate` makes the `DocumentRegistry` itself, with no IO, and registers the provider and the commands synchronously, so a document can open the moment it returns; then it starts one `ManagedRuntime`. Its registry layer builds first, cannot fail, and hands the registry its IO; the hub's layer builds on it under `Layer.catchCause`, which logs `could not start the document hub` and leaves the registry serving every editor (`extension.test.ts` pins it). One runtime of two layers, not one layer, since a hub that failed would take the registry's IO down with it, and not two runtimes, which `deactivate` would have to order and time out apart. Once built, the hub's state changes run on one promise queue whose `.catch` logs, the registry logs a publish that rejects, and `deactivate` catches every cause of the runtime's disposal and then closes the registry, which settles whatever it still queues when the dispose interrupted its layer mid-build. It listens before its lock names the pipe and rewrites the lock to `hub: false` before closing the pipe. A hub that cannot listen still writes a `hub: false` lock (empty `pipe`), because a window with no lock invites headless writes over its open editors. A window disposed before its startup task ran binds nothing and writes no lock at all: the layer's acquire hands the registry its publisher without awaiting the first publish, which queues behind that task.
- **Registration is a queue the registry's layer drains.** `register` and `unregister` change what the editor side reads (`docToWebviewMap`, the entries) at once and queue only their IO step, the native realpath of a new document, run on the `FileSystem` of `DocumentRegistry.layer` through a `FiberSet` of its scope. Steps queued before that layer built wait for it and then run one at a time in arrival order, each after the IO of the one before it and never after its publish, so the lock takes that backlog in the order it came; a step that comes later runs at once, on its own, so a realpath that hangs on a stalled mount holds up only its own document, whose editor does not open until it returns and so takes no edit its lock entry would guard. Each step is followed by a publish, and the lock lists only paths a step resolved. Closing the layer interrupts the steps in flight and settles the rest without IO. A realpath that fails or dies keys the document by the path given, the key a path that is not absolute, an untitled document's, always gets. The platform, which decides how keys compare from the first call on, goes to `makeUnsafe`; only the realpath is IO.
- `openCustomDocument` awaits `register`, which never rejects. The publisher the hub hands the registry queues every lock write in order but resolves at once while its startup or an `apply` is queued ahead, the tasks that may listen: an editor opening never waits on a hub coming up, a listen that does not return or a hub that failed. Once the hub is up it waits for the rewrite that lists the document, so an agent resolving the file finds this window's lock before the editor takes an edit, but for one second at most (`PUBLISH_WAIT` in `src/hub/services/DocumentHub.ts`), after which it logs and lets the editor open: a task ahead of that rewrite can stall for good — the realpath of a workspace folder just added or of a listed document on a stalled mount, or a lock write — and every later rewrite queues behind it, so without the cap every later editor opening would wait with it (`extension.test.ts` pins the second). A stalled task or a listen that never returns also holds the hub's close, which `deactivate` abandons at its 5 second timeout, leaving the lock for the stale sweep of a window that starts after this process is gone.
- **One way to a peer, one way into webviews.** Everything bound for a peer goes through `DocumentRegistry.deliverToPeer` (join queue, then the two filters: version at or below `snapshotVersion`, or no version at all); everything an agent sends webviews goes through `injectToWebviews` (ready webviews only, no exclusion). A webview that has not sent `hostInitialCommand` would wipe an injected batch with its initial value. Only batches queued before the snapshot is captured go through the filters; one queued between the capture and the timer that ends the window is not in the snapshot and goes out whole.
- A peer's batch is `applyActions`, refused unless the document has a ready webview and the peer joined that very `ErdDocument`; a webview never relays it back (it arrives tagged shared), so `injectToPeers` is the only way the other peers hear of it. `join` (500 ms cap) and `save` (2 s cap) first wait for the replica saves a change is owed, since `document.content` lags an edit by the replica's 200 ms debounce. The webviews owing one are the ready set copied when the change is noted, and the wait ends once that set is empty and at least one save has come: a webview that reports ready afterwards never holds the wait open and its own save settles nothing by itself, while a change that reached no ready webview still waits for one save. `onValueSaved` therefore carries the webview whose replica saved, and a panel closing takes it out of the set. A save reaching the hub sooner than 200 ms after a peer batch was sent cannot hold it and is not counted; a relay bounds nothing, since it can arrive after its replica saved. `join` captures at its cap regardless; `save` answers `saved: false` at its cap and writes nothing, as the bytes may lack the edit.
- `readonly` is the two schemes of `src/hub/readonlyUri.ts`, `git` and `conflictResolution`; `vscode.workspace.fs.isWritableFileSystem` was considered and not used. A git or merge view shares its file's path: the registry prefers the file, and with only the view open `join` says `readonly: true` and writes are refused, but `openDocument` neither answers from the view nor waits on it — it opens the file itself.
- Path authorization (`src/hub/authz.ts`) resolves the real path, then leaves the folder and document rule to agent-hub's `authorize` Effect. It climbs past a path's missing tail only when `realPath` fails `NotFound` and `HubEnvironment.lstat` fails `NotFound` too. A dangling symlink, any other `realPath` error, or a `..` behind a missing directory is refused as `outsideWorkspace`: `realpath` cannot see where a write through it would land. `lstat` stays on `HubEnvironment` with its raw errno rather than move to `FileSystem.readLink`, whose `PlatformError` folds EINVAL, EPERM, EIO and ENAMETOOLONG all into `Unknown` and would read a file the hub cannot examine as one that exists.
- **Every real path the hub takes is the native realpath's**: the lock's `workspaceFolders` and `documents`, authorization, the registry's keys (`registryLive` provides the registry layer with it) and `listDocuments` all resolve through `src/hub/services/nativeFileSystem.ts`, `NodeFileSystem` with `realPath` on `node:fs/promises`' `realpath`, as `mcp-server` resolves an agent's path (its `io/fileSystem.ts`). `NodeFileSystem`'s own is the JS `fs.realpath`, which keeps the spelling it is given: on macOS a differently cased path, and a folder VS Code hands over in NFC whose name the disk holds in NFD (as Finder writes Korean names), came back as given while the MCP server's came back as on disk, so `selectHub` found no lock covering a document open in the window, answered headless where a `hub: false` lock should have blocked, and a write landed under the editor. When the native realpath fails, `NodeFileSystem`'s runs for the reason tag. `nodeHub.test.ts` holds both spellings to the disk's, through the hub's `realpathOrSelf` and through the registry's keys.
- Unit specs must not provide the node layers (`HubEnvironment.layer`, `HubListener.layer`, `NodeFileSystem.layer`, `nativeFileSystem.ts`' `layer` over it, or `registryLive` and `documentHubLive`, which carry them) — build the memory layers of `test/mocks/hubLayers.ts` instead, or they bind a socket and write a lock under the real home directory. The exceptions are `src/hub/services/nodeHub.test.ts` and `src/hub/services/netSocket.test.ts`, which run the node layers (and `authorizePath` and the registry over `registryLive` on them) against a `mkdtemp` directory.
- `serveConnection` reads in a fiber of its own and serves from a queue, so a peer hanging up marks the connection closed at once rather than behind the request in flight; that request is forked detached, so a save or an open already writing runs to its end and only its response is dropped. A peer's id is taken when its `hello` passes, so a refused peer consumes none. Closing the serving scope destroys every accepted connection, including one accepted in that very tick, which is also what lets `server.close` settle.
- Its two halves are apart — `Socket.readerString` for the frames it reads, a fiber of its own draining the outbound queue through `socket.writer` — rather than one duplex `Socket.toChannelString` channel, which couples them: a write failure there fails the read side too, and a `CloseEvent` offered after it can no longer reach the socket. Apart, a write that cannot reach a peer is logged and leaves the connection serving, and `hangUp` still destroys the socket of a peer whose frame could not be read, where `endWith` (a refused `hello`) only ends the write side. The connection waits on that writer fiber before its scope closes, so the last frames still go out.
- `fromNetSocket` attaches its no-op `error` listener where the connection is accepted, not inside the reader: a reset peer emits `error` right before `close`, and a socket nothing has read yet would throw it in the extension host instead.
- A panel's `onDidDispose` listener must not read `panel.webview`: VS Code marks the panel disposed before firing the event and the getter throws `Webview is disposed` (seen on 1.138.0, and on 1.90.0 when it was the floor; history now), which once left a closed split-view panel counted ready, so `save` waited on a replica that no longer existed. `removeWebview` finds the webview by its panel, and the stub's panel throws the same way. It then calls `dropRecipient` (`src/hub/joinWindow.ts`) for that webview: the closed replica's save never comes, so a pending change whose remaining replicas already saved settles right then, not at the next edit.
- State-changing commands must go through `dispatchBroadcast` over `docToWebviewMap` in `src/erd-editor.ts`, or one document open in two groups desynchronizes. The one exception is the hub: an agent's batch goes through `DocumentRegistry.injectToWebviews` to every ready webview, since no webview sent it, while `dispatchBroadcast` skips the webview a command came from.
- New host behaviour goes on `ErdEditor`, not the provider, which only wires documents and panels into the registry; `bootstrapWebview` returns one `Disposable` releasing both the `mergeRegister` handle and the raw listeners.
- No new `vuerd.*` command: `extension.test.ts` and the Extension Host suite pin the registered set to the manifest's four.
- The four `vuerd.*` handlers are arrows, never bare references: `editor/title` passes more than the uri, and the second argument would land as `viewColumn`.
- `IMPORT_FILE_TYPES` is keyed by the bridge's import `type` union and feeds both the dialog filter and the extension check; the check is an alternation because `graphql` has three extensions.
- `capabilities.untrustedWorkspaces.supported` is `true` — never eval or execute document content.
- `build:vsce` / `publish:vsce` run a `vsce` no package.json declares; it must be on `PATH`.

### Testing Requirements

- Unit: `pnpm exec vp run --filter vuerd-vscode --fail-if-no-match test`. Call `resetVscodeMock()` in `beforeEach`; the stub is shared per file. `pnpm --filter vuerd-vscode typecheck` is the gate alone.
- Integration: `pnpm --filter vuerd-vscode e2e` builds, compiles `tsconfig.integration.json` to `out/`, then runs `stable` and `minimum-supported` over `test/fixtures/workspace/` and `erd-json-only` (stable only) over a folder whose one file is `sample.erd.json`, with its own specs (`xvfb-run -a` on Linux; `VSCODE_TEST_USER_DATA_DIR` shortens the IPC socket path). Those specs import only `vscode` and node builtins, the fake peers of `agent-hub.test.ts` included — the host runs the emitted JS unbundled, so `@/` does not resolve; `agent-hub.test.ts` speaks the hub's JSON lines by hand over `net` and restores the `sample.erd.json` it saves.
- `vscode.workspace.save(uri)` saves a custom editor document and clears its dirty flag: measured 2026-09-22 on VS Code 1.138.0, two tabs of one document went from dirty to clean within 1 ms of one call and the disk held the new table; a later probe got the same from that call alone on 1.90.0 (8 ms) and 1.138.0 (8 ms), so the hub's save ladder ends at its first rung on stable, and did on 1.90.0 (measured on 1.90.0 when it was the floor; history now).
- `agent-hub.test.ts` prints one `[agent-hub e2e] vscode <version>` line per timed spec (join, applyActions, applyToDirty, save, applyToOtherPeer); applyToDirty is the replica round trip that `join` and `save` wait on, about 210–225 ms on 1.90.0 and 1.138.0 (measured on 1.90.0 when it was the floor; history now), against their 500 ms and 2 s caps.
- The replica round trip runs in a real Extension Host: measured 2026-09-22, each of two webviews answered an injected batch with `hostSaveValueCommand` 209–239 ms later, `document.content` grew 900 → 1936 B, the tab turned dirty at 256 ms, and the `Tag.shared` batch never came back through `hostSaveReplicationCommand`.
- Build: `pnpm exec vp run --filter vuerd-vscode --fail-if-no-match build`; `dependsOn` builds `vscode-webview` first, which fills `public/`. Nothing gates the bundle's size, so it is recorded here: `dist/extension.js` is 166,640 B (gzip-9 55,386 B, the `zlib.gzipSync` level the size scripts use, measured 2026-09-23) with the hub on effect layers, the registry's IO on a layer of its own, an editor opening's wait on the lock capped, effect imported from its named entries, peer frames decoded by `PeerToHubMessage` and notifications encoded by `HubNotification` (166,474 B and 55,332 B before the cap, 164,212 B and 54,507 B before the registry's layer, 163,664 B and 54,300 B before the notification encoder, 163,668 B and 54,496 B with effect's module paths), up from 116,599 B (gzip-9 38,495 B) when only `agent-hub` pulled effect in. Two minified spikes set what to expect of it, measured 2026-09-23: a minimal `Layer.effect` + `ManagedRuntime` + one `Schema.Struct` extension came to 129,231 B, and one shaped like this hub (Stream, Queue, Deferred, a Socket adapter, Ndjson, a tagged error, a Logger) to 154,361 B, so the bundle sits above the shape it ships and inside 1.5× either one. It carries no `ws`, no `undici` and no dynamic `import(`, and requires only `vscode` and node builtins.
- Manual: F5 `Launch Extension` from this folder builds the dependencies once (`build:deps`), then watches the extension only — rebuild the webview after changing it. The watch build is the shipping one, so it is minified and mapless too: `launch.json`'s `outFiles` still finds `dist/extension.js`, but a breakpoint belongs in it and not in `src/`. Flip `build.sourcemap` to `true` for a debugging session, and do not commit that.

## Dependencies

### Internal

`@dineug/erd-editor-webview-bridge` and `@dineug/erd-editor-agent-hub` (both inlined into `dist/`) and `@dineug/erd-editor-vscode-webview` (fills `public/`) — `devDependencies`, which the build's `dependsOn` still follows.
