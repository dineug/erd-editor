# agent-hub

## Purpose

`@dineug/erd-editor-agent-hub` is the one specification of the document hub that lets a coding agent's MCP server join an IDE window's collaboration stream: the protocol version and message types, the lock file schema and where it lives, JSON lines framing, path authorization and hub discovery. Every message and the lock file is an effect `Schema`, and the types of the same names, the frame decoders and the request encoder are derived from them. Path authorization and hub selection return Effects, frames stream through `Stream` steps, and the one service any of them requires is effect's `FileSystem` (`readLockDirectory`); the path rules underneath stay pure functions over strings. Each side provides the layers and its own net adapter. `private: true`; `effect` is its one peer dependency.

## For AI Agents

### Working In This Directory

- **No `node:*` — a choice, not a constraint.** `defineLibraryConfig` builds for `BROWSER_TARGET` and `createExternal` does not externalize builtins, but a bespoke Node-target config would be allowed (`check-task-inputs.mjs`'s `sharedTaskCount` would go 1 → 2). Pure functions with injected `isAlive` / `homeDir` / `platform`, and Effect functions that name effect's `FileSystem` tag in their requirements instead of calling `node:fs`, were chosen because three runtimes read the same spec — the extension's CJS bundle, the MCP server's ESM bundle and the Extension Host e2e's unbundled fake peer — and because the suite then reaches perFile 80% without fs (`readLockDirectory` runs over `FileSystem.layerNoop`). `node-free.test.ts` enforces it; byte counts use `TextEncoder`, never `Buffer`.
- **`effect` is a peer, imported from its named entries.** `createExternal` reads `peerDependencies`, so every `effect` import stays bare in `dist/*.js` and `dist/*.d.ts`, and each consumer inlines the one copy its own `effect` devDependency resolves (same `catalog:` pin). Import `{ Schema, Stream } from 'effect'` and the like, from the entries effect's `package.json` exports by name and its own docs import from, never a module path such as `effect/Schema`, which resolves only through its `./*` wildcard: the root lint rule and `node-free.test.ts` both refuse one. A consumer program that reaches these `.d.ts` files type-checks effect's declarations too, so it needs `skipLibCheck` or a lib with the DOM names (`TextDecoderOptions` in `Channel.d.ts`); `tsconfig.app.json` and the extension's `tsconfig.json` (lib ES2022) have `skipLibCheck`.
- **`engines.node` (`>=22.12.0`, the root's floor) is a declaration only.** This package builds for `BROWSER_TARGET` and imports nothing from `node:`, so the floor binds only the consumer bundles it is inlined into: the MCP server's `node22` build and the extension's, on the VS Code 1.101 host (Node 22.15).
- **The protocol is a wire format.** A new method is a `request(...)` member of `HubRequest` plus a `response(...)` pair in `HubResponse` (or a `notification(...)` member of `HubNotification`); `HubRequestParams`, `HubResultMap` and the `HUB_*_METHODS` lists are read off those members, and `protocol.test.ts` pins the names and fails `tsc` when a request has no response. Its round-trip cases decode and re-encode the frames today's peers write and expect the same bytes back. A field the schema does not know never fails a decode: a struct drops it, and `listDocuments` params and the `leave` result, which nothing reads, are open records that take any object. The one exception is an `id` on a notification: every `notification(...)` member refuses the key, so a frame with an id never reads as a notification and a peer still takes it for an answer, as it did before it decoded by schema. A missing field does fail, `hello`'s `client` included, which the hub still reads by hand and defaults to `''`: the direction readers hand such a frame over as a `RefusedFrame` holding the parsed value, and a reader that keeps fallbacks reads that value itself (see Framing). Any change that an older peer cannot read bumps `HUB_PROTOCOL_VERSION`; it stayed 1 through the `applyActions` change below, made before the protocol first shipped. There is no `rejoin` message: reseeding after an auto open is a session step of the MCP server.
- **A peer sends requests only; notifications flow hub → peer.** A peer hands over its own actions with the `applyActions` request (`{ path, actions }` → `{ webviews }`), so a refusal (`notOpen`, `readonly`) reaches it and the session can rejoin; the `actions` notification carries the actions of webviews and of other peers to a joined peer, and `documentClosed` tells it the editor went away. The hub answers a frame without an `id` with nothing.
- **Error codes say whose fault it is.** `badRequest` is a malformed request, an unknown method or a missing `path`; `internal` is the hub failing (a handler threw something other than `HubRequestError`, or its result could not be framed). `notFound` means only that the named document does not exist, so an MCP server never reads a hub bug as a missing file.
- **Lock location is computed here only.** Locks are `<home>/.erd-editor/ide/<pid>.json` (dir `0o700`, file `0o600`); the socket is `<pid>.sock` beside it, or `\\.\pipe\erd-editor-ide-<pid>` on win32. `lockFilePid` is the inverse of `lockFilePath` and ignores anything else in the directory, temp files of an atomic rewrite included.
- **`MAX_PIPE_PATH_BYTES` is 100** — under the kernel's `sun_path` field of 104 bytes on macOS and 108 on Linux. `pipePathFits` measures UTF-8 bytes and always passes win32 named pipes; a path that does not fit is the adapter's cue to bind under the temp directory and write that path into the lock's `pipe`. The lock itself never moves.
- **Socket path, measured 2026-09-22** on macOS 26 (Darwin 25.6, arm64), Node 22.23.2, libuv 1.51.0: `<home>/.erd-editor/ide/<pid>.sock` came to 40 bytes for a 13-byte home, and `net.createServer().listen` bound it and accepted a connection. Paths up to 104 bytes bind as given; a longer one is not rejected — `listen` succeeds on its first 104 bytes and a client given the same long path still connects — so `pipePathFits` is the only guard and the adapter checks it before `listen`. The path is home + 22 + pid digits bytes, so the longest home that fits is 73 bytes on macOS (5-digit pids) and 71 on Linux (`pid_max` up to 4194304). Not measured yet: Linux `listen` and the win32 named pipe ACL.
- **`parseLock` is lenient forward, strict on types.** Unknown fields are dropped so a newer writer still parses; a missing field or a wrong type returns `null` (`protocolVersion` is `Schema.Int`, a safe integer; the hand-written check before it took any integer). `serializeLock` encodes through the same codec: the eight fields in declaration order, two-space indent, a final newline, nothing else, so no extra property leaks to disk. The bytes are those of the pre-schema writer; `lock.test.ts` pins them.
- **Paths are compared, never resolved.** Inputs are absolute and normalized by the caller, with symlinks resolved by `realpath` on both sides (`FileSystem.realPath` in the extension's `src/hub/authz.ts`, the MCP server's `realPath` in `src/paths.ts`), each a native realpath over `NodeFileSystem`: nothing here folds more than case, so the two sides must spell a path alike, and the JS realpath `NodeFileSystem` brings keeps a spelling the disk does not hold (a case, or NFC for a name stored in NFD on macOS); nothing here resolves a path, and the only file system access is `readLockDirectory`'s listing and reads. Rules: segment-wise (`/a/bc` is not inside `/a/b`), case-insensitive on `win32` and `darwin` only, backslashes folded and the drive letter lowercased on `win32` only (on POSIX a backslash is part of a file name), a `..` segment or a relative path matches nothing, a folder counts as inside itself.
- **Authorization and discovery use one rule**: inside a workspace folder, or exactly equal to one of the lock's `documents`. A window with no folder therefore admits only the documents it has open.
- **`readLockDirectory` is the one lock reader**: the MCP server's discovery and the extension's stale-lock cleanup both read locks through it. A missing or unreadable directory is no locks, a name `lockFilePid` refuses is skipped, and so is a lock whose read or stat fails between listing and reading; listing order is kept. `mtimeMs` comes from `FileSystem`'s `mtime`, a `Date`, so it is whole milliseconds (Node's `mtimeMs` carries a fraction), and a file system with no mtime reads as 0.
- **`selectHub` takes lock files unparsed** (`{ pid, raw, mtimeMs }`) so it can report both stale kinds, and returns an Effect that asks `isAlive` each time it runs, so it chains onto the read: `readLockDirectory(home).pipe(Effect.flatMap(locks => selectHub(locks, target, platform, isAlive)))`. The two stay apart rather than one `discoverHub`: the extension's stale cleanup filters out its own pid between them and wants only `stale`. A dead pid is `stale: 'dead'` whatever its content — the only kind that is safe to delete with its socket. A live pid whose lock does not parse is `stale: 'malformed'` and is skipped but must be left alone: it may be mid-write or from a newer schema. Among live parsed locks, a `documents` match outranks any folder, a deeper folder outranks a shallower one, then the newest `mtimeMs`, then the higher pid. A `hub: false` winner is `blocked`; no match is `headless`.
- **Framing**: one JSON value per `\n`-terminated line, compact `JSON.stringify` output. `decodeFrameResults(schema)` takes strings (the adapter decodes bytes with a streaming UTF-8 decoder: `Stream.decodeText`, or `setEncoding('utf8')` on the `node:net` socket, which both consumers' `fromNetSocket` call so that `Socket.readerString` only passes strings through; `readerString` over byte chunks decodes each chunk on its own and turns a character split between two reads into U+FFFD), skips blank and whitespace-only lines, leaves a `\r` before the `\n` to `JSON.parse`, never parses an unterminated tail, and stops at a non-JSON line or a frame over `MAX_FRAME_BYTES` — measured in UTF-8 bytes, on both encode and decode, and checked before a partial line is buffered. Each JSON value comes out as a `Result`: the message `schema` decoded, or a `RefusedFrame` (`{ value, issue }`, the parsed value and the schema's reason) for JSON that fits no message, and reading goes on. It fails the stream with `FrameError` (`reason` `tooLarge` or `notJson`) and passes the text stream's own failures through; `decodeFrames(schema)` also fails at the first refused value, with `reason` `invalid`. After a `FrameError` the stream is out of step: close the connection. The consumers read through `decodePeerToHubFrames` (`PeerToHubMessage`) and `decodeHubToPeerFrames` (`HubToPeerMessage`) and each decide what a refused frame gets: the hub reads it by hand as it read every frame before the schema, so it keeps its old answer (hang-up, `badRequest` with its id, or the handler with the params it can read); the MCP server reads it by hand too, as its client did before the schema: a numeric `id` settles the pending request it names, a string `method` with object `params` goes to the session as a notification (an unknown method among them), and anything else is logged and skipped. `encodePeerToHubFrame` writes a request through `PeerToHubMessage` then `encodeFrame`: fields in schema order, unknown ones dropped, the bytes `protocol.test.ts` pins for today's requests; `openDocument`'s `create` and `initialValue` are `Schema.optional`, so one given as `undefined` is left out as `encodeFrame` leaves it out, where `optionalKey` would throw. `encodeHubNotificationFrame` writes the hub's notifications the same way through `HubNotification`, the bytes `encodeFrame` wrote of the objects the hub builds. The hub's responses stay `encodeFrame` of what its handlers return, because a result JSON cannot frame must answer `internal` with JSON's own message. `encodeFrame` throws a `RangeError` over the limit. `decodeFrameResults` splits lines itself rather than through `Ndjson.decodeString`: that filter drops only zero-length lines, so a whitespace-only line would fail `JSON.parse` instead of being skipped, and its `splitLines` also ends a line at a lone `\r` and flushes the unterminated tail at the end.
- `authorize(folders, documents, target, platform)` checks `isAuthorized` when it runs and fails with `HubRequestError` of code `outsideWorkspace` (`<target> is neither inside a workspace folder nor an open document`); an adapter turns any `HubRequestError` into a `HubError` response carrying the same code. `HubRequestError` is a `Schema.TaggedError` (`_tag` `HubRequestError`, yieldable, `Effect.catchTag`) built as `new HubRequestError({ code, message })`, and a code outside `HubErrorCode` throws at construction.

### Testing Requirements

- `pnpm exec vp run --filter @dineug/erd-editor-agent-hub --fail-if-no-match test` (node environment); `pnpm --filter @dineug/erd-editor-agent-hub test:coverage` for the perFile 80% gate.
- `framing.test.ts` builds strings of `MAX_FRAME_BYTES` to test the real limit for `encodeFrame`, `decodeFrames` and `decodeFrameResults`, which takes about a second; its assertions compare lengths and identity, not the strings, so a failure does not print 64 MiB.
- Effect specs use `itEffect` / `runTest` from `src/__test-utils__/effect.ts` (`@effect/vitest` needs Vitest 5); services are layers, e.g. an in-memory `FileSystem.layerNoop({ readDirectory, readFileString, stat })` in `discovery.test.ts`.
- This suite cannot see consumer breakage: after a protocol or lock change run `pnpm build`, and update the hand-written frames of the Extension Host e2e peer (`packages/vscode-extension/test/integration/agent-hub.test.ts`), which imports nothing from this package.

### Common Patterns

- `HubErrorCode` is an `as const` map paired with a same-named type; `HubErrorCodeSchema` is `Schema.Literals` of its values.
- A schema and its type share a name (`LockRecord`, `HubError`, `HubRequest`, ...), the type being `typeof X.Type`: struct properties come out `readonly`, arrays are `Schema.mutable` so they still pass to the `string[]` / `unknown[]` parameters of `paths.ts` and the consumers.
- Message types are `Extract` over the union schema's type on `method`, so narrowing on `method` narrows `params` and `result` too.
