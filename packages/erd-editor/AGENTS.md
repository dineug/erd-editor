# erd-editor

## Purpose

The editor core, published on npm as `@dineug/erd-editor`: the framework-free `<erd-editor>` custom element on `@dineug/r-html`, whose Redux-like store's actions carry a Lamport clock version and merge through the LWW registers in `@dineug/erd-editor-schema`. Beside the package root, which exports both element classes and their define functions and defines neither tag, it ships `erd-editor.js` and `erd-viewer.js`, which each define one tag when imported, `<erd-editor>` or the read-only `<erd-viewer>`, and two DOM-free entries, `engine.js`, the headless replica, and `peer.js`, a headless collaboration peer that edits by dispatching actions instead of by a pointer; seven workspace packages consume the root, `engine.js` and `peer.js` (Rules § Entries and Consumers). The ERD scene is a Konva `<canvas>` rendered through a second r-html host, `@dineug/r-html-konva`, over the scene geometry in `src/konva/`, and the toolbar, panels, menus and the editing overlay stay DOM. The same scene components also draw the one view, the Visualization tab's Flow mode, and a `GeometrySource` tells them which they draw; a view is the reader's own placement, zoom and rows, never in the file, the history or a peer. A change here keeps the peer graph free of the DOM, and a change to an entry's surface updates the spec that pins it (`src/index.test.ts`, `src/erd-editor.test.ts`, `src/erd-viewer.test.ts`, `src/engine/index.test.ts`, `src/peer/index.test.ts`).

## Making a Change

1. **Read the nested `AGENTS.md` files first.** Open the one in each `src/` directory the change touches and in each directory above it, up to this file; Subdirectories lists all nineteen. Root step 1 says which reads load them on their own, so open each one yourself. For a change another package sees, read that package's file too (root step 1): `mcp-server`'s for `peer.js`, `replication-store-worker`'s and `app`'s for `engine.js`, `webview-client`'s, `obsidian-plugin`'s and `app`'s for the element's API, and `erd-editor-yjs`'s for the store port and the action lists it mirrors (`src/engine/AGENTS.md`, The store port).
2. **Write the change with its specs** (root step 2). A spec's file name picks its project and its extension follows how it mounts (Testing Requirements). A string a user sees follows `src/i18n/AGENTS.md`: a dictionary key, or a literal where it stays as written.
3. **Run the package's `test` task** (root step 3), which runs `tsc --noEmit`, then the `unit` and `browser` projects:

   ```
   pnpm exec vp run --filter @dineug/erd-editor --fail-if-no-match test
   ```

   The `browser` project needs Chromium; when it fails to start, install it with `pnpm --filter @dineug/erd-editor exec playwright install chromium` and run the task again. A change to an entry's exports, the element's API or a type a sibling reads runs `pnpm test` instead, since the consumers type-check against `dist/**/*.d.ts`.
4. **Run the coverage gate** (root step 4), both projects at 80% per file, since CI fails a file under it:

   ```
   pnpm --filter @dineug/erd-editor test:coverage
   ```

   Testing Requirements gives the form for one file.
5. **Run root step 5**, `pnpm check` then `pnpm build`; the build also writes the two UMD bundles. After the build, run `pnpm peer-graph`, `pnpm dist-shape`, `pnpm consumer-bundles` and `pnpm size` when this package's output or a library it inlines changed (root step 5). The peer graph's rules are in `src/peer/AGENTS.md`. A record past its `budgetGzip` is reported with the measured bytes and what added them, and the budget stays for the owner to re-pin (root § Making a Change).
6. **Run the e2e for behaviour a user sees** (root step 6): `pnpm --filter @dineug/erd-editor e2e`, which builds first. Read `e2e/README.md` before writing an e2e spec. A change to the peer store (`src/engine/peer-store.ts`, `presence.ts`, `stream-flush.ts`, `to-width.ts`) also runs two checks in other packages: `mcp-server`'s `test` task (`pnpm exec vp run --filter @dineug/erd-editor-mcp --fail-if-no-match test`) and `pnpm --filter vuerd-vscode e2e`. Their `scenarios.test.ts` and `agent-hub.test.ts` are the other two completion gates of the peer work (Testing Requirements). A change to the store port's five methods, to `clearSharedTrackers` or to the presence, handshake or following lists runs `erd-editor-yjs`'s `test` task too (`pnpm exec vp run --filter @dineug/erd-editor-yjs --fail-if-no-match test`), and its e2e for one a room's clients would see.
7. **Update the READMEs a user-visible change reaches**, the ones root § Common Patterns lists; this package's `README.md` is the npm page.
8. **Report as root step 7 says.** When the `browser` project or the e2e fails to start, install Chromium as step 3 says and run it again. A missing Chromium is no reason to leave either check out (root § Making a Change). Name each check you leave out and the platform it needs: `vuerd-vscode`'s e2e needs the VS Code that `@vscode/test-cli` downloads, and a display (`xvfb-run -a` on Linux).

## Rules

### Entries and Consumers

- **Seven packages depend on this one.** `app`, `webview-client`, `replication-store-worker`, `obsidian-plugin`, which bundles it into its `main.js`, and `mcp-server` depend on it, `erd-editor-yjs` names it as a peer and binds the element and the peer store through the store port, its shipping code taking types alone, and `vuerd-vscode` lists it as a devDependency for one spec. A change to an entry reaches each of them, so read their `AGENTS.md` (Making a Change, step 1).
- **`engine.js` is DOM-free.** `app` imports it beside the element, and `replication-store-worker` imports that entry alone.
- **`peer.js` is DOM-free too.** `mcp-server` inlines it into its one file as a headless collaboration peer. `app`'s Drive, fingerprint, collaboration host and IndexedDB schema specs, `obsidian-plugin`'s `src/__test-utils__/diagram.ts` and `vuerd-vscode`'s `src/runtime-value.test.ts` import that entry too, and so does `erd-editor-yjs`: its shipping code for the `PeerStore` type, its specs, bench and e2e compactor for `createPeerStore`, the action barrels and the type lists. Peer graph rules: `src/peer/AGENTS.md`.

### The Element and Its Hosts

- **Keep host integrations on `ErdEditorElement`.** `webview-client`'s `mountWebview` sets the import callback only when a host passes `importFile` (VSCode does, IntelliJ does not), so the built-in `<input type=file>` is IntelliJ's only import path. The Dictionary tab's Import CSV opens a built-in input in every host, since the callback's types name no CSV, and its export goes through the export callback (`src/components/dictionary/AGENTS.md`).
- **The theme's `system` appearance** (`SYSTEM_APPEARANCE`, `themes/radix-ui-theme.ts`) is a third `ThemeOptions.appearance` beside light and dark. The theme builder lists it first and `changePresetTheme` reports it unchanged. `resolveAppearance()` in `src/components/element-host/themeHost.ts` resolves it to the light or dark a host named with `setSystemAppearance`, or to the OS colour scheme `useDarkMode` reads once that is `null`. So `createTheme` takes `ResolvedThemeOptions`, `hasDarkMode()` asks the resolved appearance, and `systemDarkMode` picks `system` when turned on and keeps what `system` shows when turned off. An IDE host names its own light or dark because its page cannot see it, and the hosts keep storing `auto` (`packages/webview-client/AGENTS.md`). `<erd-viewer>` starts on `system` (`useThemeHost`'s first argument), so an embed follows its page from the first frame.

### Packaging and Externals

- **A file-level `dist/`.** `vite.config.ts` builds with `preserveModules` and `minify: false`, so `dist/` holds each module at its `src/` path beside its `.d.ts`, and a consumer's bundler prunes by file and minifies once, as with the private libraries (root § Working In This Directory, Library builds). `output.comments` drops the JSDoc from the JavaScript, which the `.d.ts` keep, and keeps `/* @__PURE__ */` and licence comments, since `pnpm peer-graph` reads the emitted text (root § Testing Requirements). The worker pass inherits `minify: false` but not `output.comments`, so `dist/workers/*.shared-worker.js` ship unminified with their JSDoc, for the host's bundler to minify.
- **`sideEffects` names four modules in six patterns.** `./dist/erd-editor.js` and `./dist/erd-viewer.js` are what a consumer imports for their effect alone. `**/erd-editor.ts`, `**/erd-viewer.ts`, `**/workerDomStubs.*` and `**/elkWorkerRealm.*` serve the package's own builds (the lib, umd and worker passes, and Storybook), which read the field against `src/` ids, where a `./dist/…` path matches nothing: without them the umd entries and the stories, which import an entry bare, define no tag, and the worker passes drop the two stubs. In a consumer's bundle the stubs sit inside `dist/workers/*.shared-worker.js`, which each bundler takes as an entry. `pnpm consumer-bundles` or `pnpm dist-shape` fails on a field that leaves a pattern out (root § Testing Requirements).
- **Every other module is pure.** Its top level runs nothing its exports do not need, and every bundler drops a module that a pure file reaches only through a bare import. So an entry that defines a tag imports its define function by name and calls it, and a bare-import hop put between the two needs a pattern of its own. `GlobalStyles`, `icons.ts`, `globalEventObservable.ts` and the `@dineug/r-html-konva` draw gate need none, since the exports that use them keep them; that package's own `sideEffects: false` holds because every host export reaches the gate's top-level writes (`packages/r-html-konva/AGENTS.md`).
- **A module that runs something at load is listed with its reason.** `src/sideEffects.test.ts` parses every shipped module of this package and of the six workspace libraries it inlines (tests, stories, `__*__` directories and the three dev pages left out) and pins the ones whose top level runs something: a bare import, a statement, an `if`, or a write or registering call in an initializer. Each sits in its list with why a bundler keeps it: a tag or worker stub module needs a `sideEffects` entry, a bundle's own entry is never pruned, and an initializer runs for the exports that keep it. A new one joins the list, and one that loses its effect leaves it.
- **Put a shipped `src/` third-party import in `dependencies`.** The lib and worker builds externalize exactly that list, so a `devDependencies` entry inlines and its types stop resolving for consumers (root § Working In This Directory, Externals).
- **The private `@dineug/*` libraries inline**, each under `dist/<folder>/dist/` at the path its own `dist/` gives a module, with no `.d.ts`: `r-html`, `r-html-konva`, `grid`, `erd-editor-schema`, `schema-sql-parser` and `uuid`. Rolldown's helpers go to `dist/_virtual/`, and to the `_virtual/` of each library whose own build carried some. The public `.d.ts` still name `@dineug/r-html` and `@dineug/erd-editor-schema`. `pnpm dist-shape` holds every other script of `dist/` but `_virtual/`, `workers/*.shared-worker.js` and the two `*.umd.js` files to a module of `src/` at the same path with its `.d.ts` (root § Testing Requirements), and reads these folders from `INLINED_LIBRARIES` in `scripts/viewer-boundary.mjs`, so a library this package starts inlining joins that list.

### Path Alias

- **Declare `@/*` → `src/*` in five places.** They are `tsconfig.json`, `e2e/tsconfig.json`, `vite.config.ts`, `vitest.config.ts` and `vite.umd.config.ts`, where it goes after the `@/workers/<worker>.spawn` entry because aliases match in order. A new alias needs all five (root § Working In This Directory has the rule for every package).

## Testing Requirements

- **The `test` task runs both projects.** `pnpm exec vp run --filter @dineug/erd-editor --fail-if-no-match test` runs `tsc --noEmit`, then `unit` and `browser`. `unit` runs in happy-dom, where `vitest.setup.ts` stubs observers, `matchMedia`, `requestIdleCallback` and a 2D context that draws nothing. `browser` runs in headless Chromium.
- **The `.browser.` infix alone picks the project.** A Konva spec without it runs on the stub context and fails for unrelated reasons.
- **`test:coverage` and `test:dev` skip the type gate.** `pnpm --filter @dineug/erd-editor test:coverage` / `test:dev` run the built-in `vp test`. CI runs `test:coverage` over both projects at `perFile` 80%.
- **Cover a gap with a test.** The three `if (import.meta.hot)` blocks (`Canvas.tsx`, `Minimap.tsx`, `VisualizationGraph.tsx`) carry `/* v8 ignore next -- @preserve */`, since no test runner defines `import.meta.hot`. `@preserve` keeps the hint through the TypeScript transform. Any other gap takes a test.
- **Measure one file within one project.** Pass `--project unit` or `--project browser` with `--coverage.include`; without a project the filter matches nothing.
- **Dev server and Storybook.** `pnpm --filter @dineug/erd-editor dev` builds the workspace dependencies, then serves `vp dev` (`index.html` → `src/index.dev.ts`, r-html HMR), whose page holds an editor and, beside it, a viewer drawing the editor's document again on each `change`. `dev:storybook` / `build:storybook` run Storybook 10, whose `ErdViewer` stories draw a sample document.
- **The e2e builds first.** `pnpm --filter @dineug/erd-editor e2e` builds, then runs Playwright; `e2e:dev`, `e2e:headed`, `e2e:report`, `e2e:typecheck` and `e2e:bench` are the other scripts. Read `e2e/README.md` first, because the fixture reopens the closed shadow root and `E2E_PORT` picks the port.
- **A spec's extension follows how it mounts.** A DOM spec that mounts through tagged templates stays `.ts` (proving JSX changed nothing); one that mounts components in JSX is `.tsx` without the pragma (`Toolbar.browser.test.tsx`, `MapColumnsDialog.test.tsx`); a scene spec is `.tsx` under the konva pragma.
- **Test output is never review evidence.** `.vitest/` (`.vitest-attachments/` before Vitest 5) and `__screenshots__/` are gitignored.
- **A view spec provides the source before rendering.** It sets the source on its container first, because `useContext` subscribes at setup and `onBeforeMount` only.
- **Destroy the store a unit spec dispatched into.** A unit spec that dispatches into `createTestAppContext()`'s store calls `app.store.destroy()` once it has read what it needs (`src/__test-utils__/diffSeed.ts`'s `diffStateOf`). The relationship hooks' throttled sort outlives the spec and can fire after the file's happy-dom environment is gone. The `Node is not defined` it then throws lands in a later file's run and fails `ci` with every test passed.
- **The surface on top is `__erdStages.canvas`.** Everything mounting `canvas/Canvas.tsx` registers as `canvas`, and `konva/testHandle.ts` publishes the newest live claim there and every live claim in `__erdStageClaims`, where a page with two viewers finds each one's stage by its host.
- **Scene code counts twice in `pnpm size`.** The export-png worker builds its own app context, so its scene code is a second copy in every record whose bundle names that worker, `./erd-editor.js` and the root among them. `components/localeContext.ts`, `i18n/{source,translate,locales}.ts` and the English dictionary (`i18n/messages/en/**`) count twice as well, because the scene's placeholders read them. Only removing a live reference moves bytes. Report a number rather than re-pinning the budget.
- **The viewer's source graph keeps to the boundary file.** `src/viewer/imports.test.ts` (`// @vitest-environment node`) walks `src/erd-viewer.ts`, which reaches the element, the read-only view and all they compose, with `__test-utils__/importGraph.ts`, whose `walk` also names the files only an `import()` reaches (`dynamic`), and reads `scripts/viewer-boundary.json` with the match rule `scripts/viewer-boundary.mjs` keeps, a bare import folded to its package. The graph reaches no entry, so its `PENDING` list is empty. It fails on a boundary entry the graph reaches that the list leaves out, on a listed entry it no longer reaches, which a change that cuts one off takes out of the list, and on a package the file neither allows nor forbids, the inlined workspace libraries allowed but `@dineug/grid`. Every file of `i18n/messages/en/` must be in the static graph and each of the 24 other dictionaries in the dynamic set alone. It also holds every forbidden path to the graph of `src/erd-editor.ts`, so no entry guards nothing.
- **Peer specs run without a DOM.** `src/peer/` specs, and in `src/engine/` those of `peer-store.*`, `presence`, `stream-flush` and `to-width`, open with `// @vitest-environment node`, since the peer's real realm has no DOM. `engine/peer-store.node.test.ts` runs one with `window`, `document` and `Node` undefined.
- **`engine/peer-store.converge.test.ts` is a completion gate.** It wires a peer store and a user store the way `e2e/specs/shared-presence.spec.ts` wires two elements, and runs every `SEED_SCENARIOS` edit through them. Its mapping races wire two to five peer stores through `__test-utils__/peerMesh.ts`, its name view races three, each with a replica, its races at one counter four, each with a replica, two of them editors built before the slot in the mixed session, its geometry races two to four, each with a replica, one an editor built before the registers in the mixed session, three a user store's drag beside two peer stores, one with a peer's write landing inside its 200 ms window and one with a third peer's answer to a join landing ahead of that write, and one two user stores, each with a replica, the second closing with its drag held once both answered a join, and its dictionary races two or three, a replica beside each peer where a word edit crosses a schema import, with the hooks run on fake timers after every batch delivered. It is one of the three completion gates of the peer work, with `mcp-server`'s `scenarios.test.ts` and `vuerd-vscode`'s `agent-hub.test.ts`.
- **Two measurements only this package can make.** `engine/peer-store.undoable.test.ts` replays each `SEED_SCENARIOS` edit through a bare `createRxStore` and compares the cursor it moves with the entries `dispatch` reported. `peer-store.dispatch-count.test.ts` mocks `@/engine/rx-store` to count the calls into `dispatchSync`. Run against `mcp-server`'s own peer, they would check a report against itself.
- **Each entry has its own record in `pnpm size`.** `./peer.js` and `./engine.js` are bundled apart from `./erd-editor.js`, so code only they reach counts in their records and never in the editor's; a budget note says what the measurement was when it was re-pinned.

## Common Patterns

- **JSX compiles to r-html tagged templates** through `@dineug/vite-plugin-r-html`. The spellings:
  - `class` / `style` keep array and object values.
  - On a DOM element, `?x` → `bool:x`, `@x` → `on:x` and `.x` → `prop:x`.
  - `${ref(r)}` → `use:ref={ref(r)}`; `...${o}` → `{...o}`.
  - Component props take no dot, because the transform adds it, so `onFoo` is never an event.
  - `<C>{t}</C>` compiles to `` .children=${html`${t}`} ``.
- **Konva scene files open with `/** @jsxHost konva */`**, which compiles against `@dineug/r-html-konva`. The pragma, its intrinsics and what fails its compile: `src/konva/AGENTS.md`.
- **Component conventions live in `src/components/AGENTS.md`.** That covers one directory per component, a second binding of one event, icon colour and the lucide table icon.
- The native list in `primitives/select/Select.tsx`: `src/components/primitives/AGENTS.md`.
- **Name actions by kind.** `somethingAction$` generators live in `generator.actions.ts`, `somethingAction` creators in `atom.actions.ts`. Bitmask flags go through `src/utils/bit.ts`.
- **Restyle the floating bars in one file.** `VisualizationToolbar` reuses `FloatingToolbar.styles.ts`, which re-exports the bar, as its `root`, and its tools from `src/components/erd/view-controls/viewControls.styles.ts`: the bar, the pill, the divider, the zoom readout and the compass, which the view controls in both bars and the read-only view's controls bar draw too. So a change there reaches all three.
- **Restyle both dictionary lists in one file.** The domain picker (`ColumnDomain.tsx`) reuses `ColumnLogicalName.styles.ts`, the term list's, and searches through `column-domain/domainOptions.ts`, which the Dictionary tab's picker of a term's domain shares (`src/components/dictionary/AGENTS.md`). Both take their focus, press, wheel and scroll handling from `table-view/column/useHintList.ts`, which the data type list still writes out on its own.
- **Give each part its own theme token.** A color is added per part (`toastError`, `findReplaceError`, `schemaSqlWarningBackground`) in `src/themes/tokens.ts` and `radix-ui-theme.config.ts`, never borrowed from another part's token (an owner decision, 2026-10-11). The diff tokens are the diff viewer's alone. `tokens.test.ts` and `radix-ui-theme.config.test.ts` pin the count.
- **Vendor data types live in `constants/sql/dataType/`.** It lists each vendor's types with their `primitiveType`, the column cell's data type hints and the category the code generators fall back to. `generator-code/columnTypes.ts` reads a type by name first, so a type a list adds reaches the generators through its category unless the classifier or a generator has a rule for its name (`src/utils/generator-code/AGENTS.md`).
- **Keep the parser's type lists in step.** `schema-sql-parser`'s `src/parser/dataType/` keeps a list per vendor, which its `helper.ts` merges into the one set its parser matches type names against, word by word. No test pins the two, so a type added or renamed in one goes into the other (`packages/schema-sql-parser/AGENTS.md`).
