# erd-editor

## Purpose

The editor core: a framework-free `<erd-editor>` custom element built on `@dineug/r-html`, with a Redux-like
store whose actions carry a Lamport clock version and merge through the LWW registers in
`@dineug/erd-editor-schema`. Published to npm and depended on by `app`, `vscode-webview`, `intellij-webview` and `replication-store-worker`; three of those import the second entry for a headless replica. No React here.

The ERD scene is drawn on a `<canvas>` by Konva rather than in the DOM. `src/konva/` is a second r-html render host, and everything under `src/components/erd/canvas/`, plus `erd/minimap/MinimapScene.tsx`, `visualization/VisualizationScene.tsx` and `services/export-png/`, is a shape tree instead of markup. The scene builds only what a culling rect three screens wide holds, and a table that scrolls out of it stays built but hidden for a while (`erd/canvas/sceneRetention.ts`), bounded because konva's per-scroll cache walk visits hidden nodes too. No shape exists only to be hit: a cell's text and an icon's first shape put the box they answer for on the hit canvas through a hit function (`erd/canvas/sceneHit.ts`), and a node that only paints does not listen. The rest of the editor — toolbar, panels, context menus, the editing overlay — is still DOM.

## For AI Agents

### Working In This Directory

- Adding an action is a four-file change: the module's `actions.ts`, `atom.actions.ts` and `history.ts`, **plus** the classification lists in `src/engine/actions.ts` — skipping the last compiles and then silently breaks undo, autosave or collaboration. `readonly` is enforced there too, by `readonlyIgnoreFilter` over `ReadonlyIgnoreActionTypes` and the `hasReadonlyIgnore` exemption list, never in components.
- Reducers must write through the LWW operators from `@dineug/erd-editor-schema` using `action.version`; a direct state write wins every merge and corrupts collaborative sessions.
- `ErdEditorElement` exposes `value`, focus/blur/clear/destroy, initial value and theme/keybinding setters, SQL/GraphQL/DBML/AML import setters, `getSchemaSQL`, `getSharedStore`, and `setDiffValue`; keep host integrations on that public surface.
- The DOM-free `createReplicationStore` accepts initial JSON, forwards only `ChangeActionTypes`, strips action tags before reduction, defers `dispatch` to a microtask while `dispatchSync` is immediate, and emits `change` after a 200 ms debounce. `setInitialValue` also runs schema GC.
- File IO and highlighting go through the three injected callbacks. `vscode-webview` sets all three, so the built-in `<input type=file>` never runs there; `intellij-webview` leaves `setImportFileCallback` unset — `ErdEditor.kt` no-ops `ImportFile` — so that input is the only import path inside JCEF, and dropping it would take IntelliJ's import with it.
- **A whole-table duplicate carries the graph its tables span; a column copy carries none.** Alt+drag and the `PayloadKind.tables` clipboard path both gather through `toClipboardRelationships` / `toClipboardIndexes` in `utils/table-clipboard/copy.ts`, so the rule is stated once: a relationship rides along only when **both** end tables are in the copied set, and an index of a copied table rides whole — its name, its unique flag, and its columns in `indexColumnIds` order with each `orderType`. `toCreateEntityActions` builds a source-to-new id map for tables and columns as it emits them, then points the copies at those ids alone; a `relationship.add` follows the tables and columns it names, and an `index.add` precedes its `indexColumn.add`s because it is the only one of them that registers the id in `doc.indexIds`. What it drops, it drops whole rather than in part: half a relationship would be a line `relationshipSort` refuses to route while the scene still drew it at the source's anchors, and a composite `UNIQUE (a, b)` narrowed to `(a)` is a stricter constraint than the one that was copied — the same reason `removeColumnAction$` removes a whole index when one of its columns goes. Atom actions in the one batch, never `attachChangeOnlyTag$` and never a second `dispatch`, so one undo takes the whole copy back. The two payload arrays are optional at `CLIPBOARD_VERSION` 1 on purpose: a bump would make every copy this build writes an `unsupported` hard stop in a shipped editor rather than a paste that drops the graph, so `isSupportedStructure` keeps requiring only `tables`, `columns` and `memos`. `PayloadKind.columns` gathers neither array and must keep it that way.
- `draw-relationship/sort.ts` runs the whole geometry pass: it picks each end's side, orders that side's anchors by the angle of the opposite table (walking the boundary clockwise, so anchors sharing a table cannot cross), then routes every connector orthogonally around the tables (`route.ts`) and pulls apart the routes that share a channel (`nudge.ts`). `pathFinding.ts` only draws, cutting each corner to 45 degrees on the way out (`chamfer.ts`) — the routed polyline itself stays orthogonal. Routing has to live there because it needs every table and every other route; `pathFinding` sees one relationship. Anchors land in schema fields and therefore serialise, so a rendering-only value — the routed polyline, the stub slot — belongs in the `WeakMap` side channels in `draw-relationship/index.ts`, never a new field.
- **No `sideEffects` field, and no `preserveModules`.** Importing the entry registers the element and with it the whole editor, so nothing a consumer's bundler could prune exists; the engine entry loads the chunk it shares with the element entry, which holds the modules both reach and nothing element-only, so there is no headless file to prune either. The field would also cost something: Vite reads a package's own `sideEffects` against its own `src/` files during the build, so a `./dist/…` list marks `customElementRegistry.ts` pure and rolldown drops the bare import chain that registers the element — measured once, as a `dist/index.js` that still resolved and no `components/` at all. Should a subpath export ever want it, every listed path has to be a `**/` glob matching `src/` and `dist/` alike, and the modules whose top-level statement reaches outside them are the entry, `customElementRegistry`, `ErdEditor` (`defineCustomElement`), `GlobalStyles` (`setGlobalStyleOrder`), `konva/batchDraw` (the Konva globals), `konva/host` (`onBeforeFlush`) and `konva/workerDomStubs`, which exports nothing and is imported bare by the export worker for the `document` it installs — the worker pass reads the same field, and so does the umd build.
- **One coordinate canon, four functions, and the view is a document field.** Where a scene layer sits is `settings.originX` / `settings.originY`, the screen point scene `(0, 0)` lands on, read through `getSceneOrigin` in `src/konva/scene/viewport.ts`; `toScreenPoint` and `toScenePoint` are that placement forwards and inverted, and `getOriginToPlace(zoomLevel, scene, screen)` solves it for the origin that puts a scene point at a screen point, which is what a jump to a table asks for. How far the origin may travel is the document's own content: `getContentRect(state)` (`konva/scene/contentBounds.ts`) is the union of every table and memo rect, and `contentScrollRange(near, far, viewportLength, zoomLevel)` in `engine/modules/settings/scrollRange.ts` turns one axis of it into the pure range — at its minimum the content's far edge meets the screen's near edge, at its maximum its near edge meets the screen's far edge — a leaf, so `e2e/bench/harness.ts`, built in node, clamps its seed with the same travel rather than a copy. `getContentScrollRanges(state)` is that pure range on both axes and `getScrollRanges(state)` is it widened to hold the origin where it stands, both in `src/engine/modules/settings/atom.actions.ts`; the minimap's own boxes are `src/components/erd/minimap/minimapGeometry.ts`, itself derived from `getSceneOrigin`. Call them, never restate the algebra: `konva/scene/coordinateAuthority.test.ts` scans every source file for origin arithmetic combined with the zoom outside those four files, following the origin into a renamed binding or a local built from it, and fails the run on the line.
- **A pan goes anywhere; the scrollbars and the minimap are navigation aids drawn over the content and the current view, and they never stop a pan. A load is pulled onto the content.** Nothing in the engine bounds the view: `streamScrollTo` — the wheel, the grab and touch pans, and the re-centre of a ctrl+wheel zoom, which `streamZoomLevelAction$` rides so the history regroups the burst as one entry — writes the origin unclamped, exactly as `scrollTo` does, where a scrollbar track press, a quick-search jump, the re-centre of a toolbar or shortcut zoom (`changeZoomLevelAction$`), a minimap press and a replayed history entry each name the origin they mean, so undo of a scroll restores exactly what was recorded. `changeViewport` moves nothing: a frame that grows or shrinks keeps what was under its corner. The ranges are for the aids. `getContentScrollRanges` is the pure content travel — from the content's far edge on the screen's near edge to its near edge on the screen's far edge — and `getScrollRanges` is `hull(pure, current origin[, frozen origin])`: what both scrollbar tracks, the minimap's map and handle and whether a bar is drawn at all are read from, and what a thumb or handle drag alone is gated by. That gate is the drag's own, not the reducer's: `useVirtualScroll` and `useMinimapScroll` refuse a step with no room on the origin's side of the hull (`hasRoom`) and cut the last one to its end through `clampScrollMovement` (`settings/atom.actions.ts`, the identity on an unmeasured screen), inside the geometry frozen at the press, so the thumb never leaves its track nor the handle its map. A pan past the content widens the hull — the thumbs shrink toward `SCROLLBAR_THUMB_MIN` and the map grows behind the reader — and a pan back lets both collapse to the content again; `coordinateAuthority.test.ts` keeps `current origin ∈ hull ⊇ pure` as a property. Only the load path reads the pure range, and its two ends are exactly the origins where nothing is drawn, so a load is not clamped onto them — pulling a saved far-away view onto the content when a file opens is not a movement limit: `openingOrigin` (`settings/scrollRange.ts`, through `getOpeningOrigin`) keeps an origin the pure range holds strictly, where some of the content is drawn, and pulls one on or past either end the shortest way to where the whole content is on screen, or a screen's worth of it when it is bigger than the screen. `pullScrollIntoRange` (`editor/atom.actions.ts`) applies that when the viewport is positive and otherwise raises `editor.scrollPullPending`, which the first measured frame spends. The stores that are loaded before anyone has measured them say so: `createReplicationStore` dispatches `changeViewportAction({ width: 0, height: 0 })` at construction, `ErdEditor.tsx` does the same for the element's store because a host calls `setInitialValue` before the `ResizeObserver` has reported a frame, and the diff viewer and time travel measure their pane before loading into it — a store left at the default 1200 × 675 would pull the opening view against a screen nobody is looking through, and the later real frame cannot undo it. A document holding anything has at least a screen's worth of travel on each axis — the pure range spans the content plus one screen — so a two-table diagram draws both scrollbars on any screen, and `VirtualScroll.test.ts` pins that. An empty document has zero pure travel, so both scrollbars hide; the wheel and the grab pan it freely all the same.
- **A drag freezes the geometry it is watched against, per store.** `konva/scene/viewFreeze.ts` holds the content rect and the origin as they stood when a drag took hold, keyed on the store's `editor.id`, and `getViewContentRect(state)` / `getFrozenOrigin(state)` hand the frozen values back for that store alone — a diff viewer mounts two stores side by side and a page may host two `<erd-editor>` elements, and a drag in one must not size the other's scrollbars or minimap against the first's content. Entity drags (`canvas/entityDrag.ts`, armed from `useMoveEntity.ts`), both scrollbar drags (`useVirtualScroll.ts`) and the minimap drag (`useMinimapScroll.ts`) all take it, each releasing it from the drag subscription's finalizer and unsubscribing on unmount, so an unmount mid-gesture thaws too. Without it a drag that grows the content grows its own travel under the pointer: the thumb would shrink as it was pulled and the map would rescale under the press. Everything the reader watches therefore stands still for the gesture and updates together on the drop — everything but the screen, which is never frozen: a wheel, a ctrl+wheel zoom or a quick-search jump mid-drag moves it, the hull holds the current origin too, and the aids follow it out, which is how a table is carried far while it is held, since the editor has no edge auto-scroll. A press on the minimap thumbnail lands its unclamped centring `scrollTo` synchronously before it takes the freeze, so the map the drag then holds has already grown to hold the post-press screen, and the handle is never trimmed by its own gesture.
- **The minimap is a map of the content and the current view.** An empty document draws no minimap, exactly as it draws no scrollbar: `Erd.tsx` and `ErdViewer.tsx` render it only while `getContentRect` finds something. `getMinimapLayout(state)` (`minimap/minimapGeometry.ts`) hulls the content rect with the screen at both ends of the travel — `getReachRect` over `getScrollRanges`, the pure travel widened to hold the origin where it stands and, while a drag holds the view, the one it began from — inflates by `MINIMAP_MAP_MARGIN` (100 scene units) and snaps outward to `MINIMAP_MAP_STEP` (500). Inside the pure travel a pan neither rescales the thumbnail nor moves a mark on it, only the handle moves; a pan past it grows the map a grid line at a time, the content shrinking toward a corner while the handle stays on the map, as Figma's does, and a pan back shrinks it again. A press centres the pressed point, unclamped — a press at the map's edge asks for a screen half outside the travel and gets it — and `Minimap.tsx` dispatches that `scrollTo` synchronously before `onScrollStart` freezes the view, so the map the drag then holds is one that has grown to hold the post-press screen, with the handle whole on it. The handle drag is the one gesture the hull gates: it moves within the map frozen at its start (`useMinimapScroll` through `clampScrollMovement`), so it can never take the handle off the map, and a drag to the end of the travel leaves the handle whole against the edge; a drag that began outside the pure travel may see the map shrink on release, which is accepted. A wheel or a jump during an entity drag is gated by nothing, and the map grows to keep the handle on it rather than trimming it away — the content it holds stays the frozen one until the drop, so what grows is the reach alone — and `getMinimapHandleRect`'s trim only reaches a rectangle drawn against another view's map. A table nudged a few pixels leaves the map where it is; `ratio` folds the map's longer side into `MINIMAP_SIZE`, `box` is the map at that ratio, and `offset` centres the box in the square. Two floors keep a far-flung document legible: the box's shorter side never draws under `MINIMAP_BOX_MIN_SIDE` (30 px) — the map is widened about its middle along that axis, snapped again, and the longer side still sets the ratio — and nothing drawn on it is smaller than `MINIMAP_MARK_MIN` (3 px): `getMinimapMarkRect(ratio, rect)` grows a table or memo box about its middle to the mark, and `getMinimapHandleRect` grows the handle the same way before trimming it, so two tables fifty thousand units apart are two marks on a strip rather than an empty hairline. The layer is placed by `toMinimapPoint(layout, { x: 0, y: 0 })` at `scaleX/Y = ratio` and nothing centres inside it — the centring is CSS, on the thumbnail and on the handle alike — and the Stage is resized from the layout the render just took, because a table moved far away changes the box with no setting changing at all. The content rect is tables and memos only, so remote presence cursors and shared drag-select rectangles are neither reachable by scrolling nor shown on the map. `components/erd/hide-sign/` and its off-canvas markers went with the document box: they pointed at entities culling had dropped, and the minimap, always on screen and now a map of everything, is what shows where those are. It does not say which — a mark carries no name — so quick search (`$mod+K`, `components/quick-search/`) is the by-name way to reach an entity that is off screen.
- **A screen holding none of the document says which way the rest of it is.** `components/erd/content-compass/` draws one pill over the middle of the bottom edge for as long as no table and no memo reaches the screen: an arrow at the nearest of them, the gap to it, and a press that centres it. `getContentCompass(state)` (`compassGeometry.ts`) reads the screen through `getVisibleCanvasRect` and the entities through `getContentRects` — the boxes `getContentRect` folds, in `konva/scene/contentBounds.ts` — and takes the nearest by the gap between the two rects, a box touching the screen counting as on it exactly as culling reads one, so the pill is drawn only where the reader has nothing at all. The arrow is turned at that entity's middle, which is also the point a press centres through `getScrollToCenter`, and the press reads the state again rather than the compass the render drew, because a wheel between the two moves the screen. `formatDistance` folds the gap into four characters at most and the label is set in tabular figures, which is what keeps it from jittering as the last digit turns under a pan. It is not the per-entity marker `hide-sign/` was: it says nothing about what culling dropped, only that nothing is left, and one arrow at the nearest entity is the whole of it. `Erd.tsx` and `ErdViewer.tsx` both draw it, unconditionally — an empty document has no nearest entity, so the compass hides itself where the minimap has to be held back — and both name `.content-compass` in the guard list that keeps a press on an overlay from starting a pan.
- **A selection is kept by what it already holds, and `$mod+A` is a caret's before it is the canvas's.** The press that starts an entity drag (`canvas/useMoveEntity.ts`) collapses the selection onto the pressed entity only where the selection does not already hold it — the rule `canvas/altDragDuplicate.ts` reads too — so a group moves as one under a plain drag and `$mod` is left meaning "add this one as well". Nothing collapses a selection on the release, so a click on one of several selected entities leaves all of them selected; empty canvas and Escape are what clear it. `selectAllTable` — the `Select All Table, Memo` command, which selects memos as well — carries two chords now, `$mod+A` and the older `$mod+Alt+A`, and both stand down inside a text field: `hooks/useKeyBindingMap.ts` names it in `YIELDS_TO_A_CARET` and returns before the `preventDefault`, since tinykeys is bound on the editor root and every keydown from an input bubbles through it. The guard is per binding name on purpose, because `Enter` and `Escape` reach `handleShortcut` from inside the cell editor, which is where an edit ends.
- **`settings.width` / `height` are a compatibility field, and so are `scrollLeft` / `scrollTop`.** Nothing in the scene, the scroll ranges, the culling rect, the minimap or the export reads the box after this stage. What still writes it is the four importers (`utils/schema-{sql,graphql,dbml,aml}-parser/index.ts`, through `canvasSizeInRange`); what still reads it is `sortTableAction` (`table/atom.actions.ts`), which wraps its rows at `settings.width`; and a released editor draws it as its document box. No action changes it any more — the toolbar's canvas-size control and the `resize` action went with the box, so a document's box is whatever the file or an import last set. `scrollLeft` / `scrollTop` are the frozen legacy pair a released editor stored its view in, measured from that box centred in the viewport; the schema parser migrates them into the origin pair once, when a document carries no origin, and nothing here reads or writes them otherwise — the importers' `omit` lists in `editor/generator.actions.ts` name both pairs so an import takes its whole view from the document the importer builds, leaving the previous document's origin and its frozen legacy pair behind while every other setting carries over. The `width * (1 - zoom) / 2` term that used to ride along with every scroll, and that a hand-written `-scrollLeft / zoom` quietly dropped, now exists in exactly one place, the migration, so the two regressions it caused cannot be written again.
- **konva enters only through `konva/lib/*`.** The package root barrel drags in every shape, filter and DOM binding, and `konva/lib/Core` alone measured 3.3 kB gzipped, so `src/konva/imports.test.ts` allowlists the thirteen deep modules that ship and lets a spec name two more. The price of skipping the barrel is that nothing assigns `Konva.DD`, which `Konva.isDragging` reads on every stage pointer dispatch; `src/konva/batchDraw.ts` registers it with `Reflect.set(Konva, 'DD', DD)`. Delete that one line and `Stage._pointermove` throws `Cannot read properties of undefined (reading 'isDragging')` before any listener is reached, which takes the whole mouse surface of the editor with it. It broke this branch once, and `konva/scene/renderScene.browser.test.tsx` exists to make that loud: measured with the line removed, the `unit` project over `src/konva` stays green (7 files, 102 tests) and that browser spec turns red (2 failed of 8).
- **A scene root is exported in lower case on purpose.** `renderCanvasScene` (`CanvasScene.tsx`) and `renderMinimapScene` (`MinimapScene.tsx`) are rendered imperatively into a Stage rather than returned as a template value, so `Canvas.tsx` and `Minimap.tsx` hand-roll `import.meta.hot.accept` for them. Rename either to an initial capital — or drop it, leaving the module's export list all component-shaped — and `vite-plugin-r-html`'s `isBoundary` classes the module as a component boundary, injects a self-accept, and the parent's `accept` silently stops running.
- **The PNG export draws its own scene at the zoom the reader is on, and is still not a screenshot.** `services/export-png/` builds a fresh app context from the document JSON, renders `ExportScene` onto a detached Stage (one layer: no scroll, no culling) and rasterises that; the viewport is never read, so the image holds the whole document however far it was scrolled away. The zoom is the one thing the screen lends it: `createDocumentPng` takes a `zoomLevel`, which `renderDocumentScene` writes into its own store with `changeZoomLevelAction` before reading anything, because the layer's scale and the spelling a table is drawn in are the same field — `getExportScale(box, zoomLevel)` is that zoom cut to the two canvas ceilings, and `ExportScene` swaps in `HighLevelTable` under `isHighLevelTable` exactly as the canvas does. The caller names it rather than the document because `toJson` writes `zoomLevel: 1` for an author who asked for the zoom not to be saved. An image the zoom alone made smaller is not a reduction: `renderPng` compares what it drew against `pixelRatio * zoomLevel`, so the toast still means only that a canvas ceiling was hit. What the image holds is `getExportRect(state)` (`exportBox.ts`): every table and memo rect, plus `getRouteBBox` of every relationship when `Show.relationship` is set, inflated by `EXPORT_MARGIN` (80 scene units), with an empty document coming out as the margin alone. `getExportScale(box)` then bounds the Stage itself at `box * min(1, CANVAS_SIDE_MAX / longestSide, sqrt(CANVAS_AREA_MAX / area))`, because a document has no size limit to lean on any more, and `pixelRatio.ts` shrinks the raster ratio of that Stage the same way; a reduction reports the box in scene units, which `erd-context-menu/menus/exportMenus.ts` rounds for the toast, and that file is also where a failure reaches the user rather than the console.
- Everything renders inside a closed shadow root, so `document.querySelector` never finds editor internals; r-html exports `queryShadowSelector` / `closestElement` for the cases that must cross one. Below that shell the scene is a single `<canvas>`, so no DOM query reaches a table, a column or a connector at all: routing asks Konva through `components/erd/hitTest.ts`, which records what konva resolved as each press was dispatched, because the press has already re-rendered the scene by the time `Erd.tsx` asks. A third-party import in shipped `src/` goes in `dependencies`: the lib build externalizes exactly that list, in the worker pass too, so a package left in `devDependencies` inlines into `dist/` and, for an npm consumer, its types stop resolving. The four private workspace libraries are the documented exception: unpublished, so inlined, which is also why the public `.d.ts` still import `@dineug/r-html` and `@dineug/erd-editor-schema` by name — a consumer without `skipLibCheck` sees that, and rolling declarations up would close it.

### Testing Requirements

- `vp run --filter @dineug/erd-editor --fail-if-no-match test` — `tsc --noEmit`, then `vp test run` over **two projects**. `unit` is happy-dom over `src/**/*.test.{ts,tsx}` with the browser glob excluded, and `vitest.setup.ts` polyfills `ResizeObserver`, `IntersectionObserver`, `matchMedia` and `requestIdleCallback` for it alone, and gives every canvas a 2D context that draws nothing and measures ten pixels a character — happy-dom has none, and without one Konva threw while building the Stage of every DOM spec that mounted the element, a throw r-html swallowed and logged. `browser` is a headless Chromium over `src/**/*.browser.test.{ts,tsx}`. **The suffix is the only thing that picks the project**, so a Konva spec named `Foo.test.tsx` runs in happy-dom, where the 2D context is the setup file's stub that paints and hit-tests nothing and every `getBoundingClientRect()` is zero, and it then fails for reasons unrelated to what it asserts. That split is also why `pnpm test` now needs a browser binary: the `ci` job installs Chromium before it. `test:coverage` (v8, per-file 80%, one root block spanning both projects) and `test:dev` (watch) are the built-in `vp test`: no type gate, no dependency builds.
- `pnpm --filter @dineug/erd-editor e2e` — builds this package, then Playwright/Chromium over `e2e/specs/`; also `e2e:dev`, `e2e:headed`, `e2e:report`, `e2e:typecheck`. Read `e2e/README.md` first — the fixture reopens the closed shadow root before the element registers.
- `pnpm --filter @dineug/erd-editor dev` builds the workspace deps then serves `vp dev` with r-html HMR; `dev:storybook` / `build:storybook` drive the Storybook 10 workbench. Colocated specs import from `vite-plus/test`, never `vitest`, and `tsconfig.json` includes all of `src/`, so a type error in a test or in `__test-utils__` turns the run red. A **DOM** spec stays `.ts` with tagged templates on purpose — `mount(template: DOMTemplateLiterals)` is orthogonal to how a component body is written, so those specs are what says the JSX layer changed nothing. A **scene** spec is `.tsx` under the konva pragma instead: what it asserts on is a Konva tree, and there is no earlier spelling of that to hold constant. A failing browser spec writes attachments to `.vitest-attachments/` and `toMatchScreenshot` keeps baselines in `__screenshots__/` beside the spec; both are gitignored and machine-local, so a screenshot baseline is never review evidence.
- `src/engine/index.test.ts` pins the DOM-free entry to exactly `createReplicationStore`; keep that barrel free of browser registration and component exports.

### Common Patterns

- One directory per component: `Foo.tsx` + `Foo.styles.ts` (r-html `css` tag) + `Foo.test.ts`, optionally `Foo.stories.tsx`. Tests mount through `src/__test-utils__` (`mountAndFlush`, `flush`). A **scene** component breaks both halves of that: it has no `.styles.ts`, because a canvas reads no stylesheet — colours come from `@/konva/theme`, geometry from `konva/scene/metrics.ts` and `canvas/sceneTokens.ts` — and its spec is `Foo.browser.test.tsx`, mounting a real Stage.
- **Components are JSX.** `@dineug/vite-plugin-r-html` rewrites every tree into the `html`/`svg` tagged template r-html consumes before oxc sees the file, so the runtime never learns JSX exists. The mapping: `class`/`style` keep their names and array/object values; `?x` → `bool:x`, `@x` → `on:x`, `.x` → `prop:x` on a DOM element, a bare `${ref(r)}` → `use:ref={ref(r)}`, `...${o}` → `{...o}`; a mixed `attr="a ${x}"` becomes a template literal. On a component tag, drop the leading dot — the transform re-adds it to every attribute, which is what stops a prop named `onFoo` being classed as an event. `children` stays an explicit prop where it already was: `<C>{t}</C>` compiles to `` .children=${html`${t}`} ``, a second template around the one you had.
- JSX forbids a repeated attribute, so the second binding of one event is `on:x__2` — three tags need it. Empty templates have no JSX spelling: `GlobalStyles.ts` and two lines of `Icon.tsx` keep theirs. `src/__jsx-parity__/parity.test.tsx` renders each shape twice, JSX and tagged template, and compares the DOM — change the transform or the type layer and that is what says so.
- **A `.tsx` file renders into one host, picked by a file-level `/** @jsxHost konva */` pragma** in the first block comment. With it, every template in the file compiles under `konva` — imported from the `konvaImportSource` both Vite configs set to `@/konva/host` — and the intrinsic tags are `k-circle`, `k-group`, `k-layer`, `k-line`, `k-path`, `k-rect` and `k-text`, typed in `src/konva/jsx.d.ts`. Mixing hosts is a compile error in both directions (a `<div>` in a konva file, a `k-*` tag in a file without the pragma), as are `class`, `style`, `zIndex`, a spread on a `k-*` tag, and a bare string or number child of one. `bool:` and `prop:` are typed `never` because they commit through an `HTMLElement` check a Konva node never passes; `zIndex` and `draggable` are `never` because the host owns sibling order and the scene's own mouse streams own dragging. `src/__jsx-parity__/parity.konva.browser.test.tsx` is the konva half of the parity gate.
- Icons are one flat `IconName` union — lucide's kebab keys for 39 stroked glyphs and seven PascalCase crow's-foot glyphs, `NOTATION_ICON`, hand-drawn as the same `IconNode` shape on lucide's grid and named after the v2 `RelationshipType` members. `@/utils/icon` serializes one of those into an svg data uri for the draw-relationship cursor; a cursor image is a document of its own where no theme reaches, so it takes `isDarkMode` and draws black ink over a white halo on light, the reverse on dark. The `<svg>` is `fill="none"` / `stroke="currentColor"`, so colour a glyph with `color` and never `fill` — a `fill` rule matches, validates and paints nothing, which is what `src/styles/emittedCss.iconPaint.test.ts` stands guard over — for the DOM surfaces. The scene draws the same glyphs from the same `getIcon` data as Konva shapes (`canvas/SceneIcon.template.tsx`), where the stroke colour is an attr on the node rather than something a cascade settles.
- Generator actions are `somethingAction$` in `generator.actions.ts`, plain creators `somethingAction` in `atom.actions.ts`; bitmask flags (`settings.show`, `Tag`) go through `src/utils/bit.ts`.
- `generator-code/sqlalchemy.ts` is the one generator that emits an import header and `class Base(DeclarativeBase)`, in the per-table path as well as the whole-document one — Python has no implicit namespace, so a bare class body is a `NameError`; `typeorm.ts` names its decorators the way `jpa.ts` names its annotations, unimported. Four things `sqlalchemy.ts` renders faithfully rather than repairing, and `typeorm.ts` and `sequelize.ts` share all four: the cross-class reference — a SQLAlchemy forward-reference string, a TypeORM `() => Target` — so a per-table snippet names classes it does not contain, and a table with no primary key becomes a class the mapper rejects — Sequelize instead gives it an `id` the diagram does not have; the other two follow `createSchemaSQL`, which declares the same collision — two tables of one name keep that table name (only their class names are deduplicated), and an unnamed column reaches `mapped_column("")` / `@Column({ name: "" })` / `field: ""`. `typeorm.ts` adds two of its own: an auto-increment primary key whose type is outside `@PrimaryGeneratedColumn`'s numeric union loses that type, and its one-to-one and many-to-one properties are typed `Relation<T>` rather than `T` — every class lands in one module, so an annotation can name a class declared below it, and under `emitDecoratorMetadata` the `design:type` is read eagerly. `sequelize.ts` is unimported too — the eight names in its `SEQUELIZE_NAMES` are free identifiers the receiving file supplies — and emits the `Model.init()` class style whose associations are immediate calls evaluated at module load rather than TypeORM's lazy `() => Target`; each class is followed by its own init and every association call trails them all, so a per-table snippet carries the calls that touch it and names classes it does not contain. Two consequences are its own: a composite foreign key declares its columns and no association at all, because `foreignKey` / `sourceKey` / `targetKey` are each a single string, and a property that would shadow a `Model` instance member or a reserved module name is renamed with `field` carrying the database name, because a `declare` field is still checked against the base class. `drizzle.ts` is the only generator whose shape follows `settings.database`: PostgreSQL, MySQL/MariaDB and SQLite reach `pg-core`, `mysql-core` and `sqlite-core`, while MSSQL, Oracle, Databricks and Snowflake fall back to `pg-core` — drizzle 0.45 publishes no dialect of their own, and `pg-core` is the one that keeps the most of a diagram. It emits an import header the way `sqlalchemy.ts` does, shares those same four collisions, and turns a comment into a `//` line because drizzle has no slot for one. Two are its own: a reference that closes a cycle — a self-reference, or two tables pointing at each other — carries `(): AnyPgColumn =>` on its thunk, or the matching annotation on the extra-config callback, because the table const's type would otherwise depend on itself; and `relationName` is emitted only where one pair of tables carries more than one relationship, which is the only thing that lets drizzle pair a `one` with its `many`. `dbml.ts` is the one generator that repairs rather than renders faithfully, because DBML rejects as a parse error what the others merely render oddly: a duplicated table name is renamed, a typeless column is dropped and the table it empties goes with it, and a `Ref` is dropped unless both ends resolve — a duplicate pair in either direction included. Every identifier is double-quoted, which is what makes an empty or non-ASCII name legal, and a type is quoted whenever the bare form would not round-trip (`decimal(10, 2)`, `enum('a','b')`). A comment becomes `Note:` / `[note:]` and never `//`, which is a trivia token no consumer sees. It reads no setting, so `tableNameCase` / `columnNameCase` are inert — a DBML name is the database identifier — and the per-table path emits the Table block alone, since a `Ref` naming an absent table does not parse. `aml.ts` renames and drops the same way, except that AML admits a typeless attribute, and `LanguageToLangMap` sends both to the `sql` grammar because shiki ships neither. Three things are AML's own: an attribute is NOT NULL unless `nullable` is written, so the generator emits the keyword the importer resolves away; a type is always quoted, since a bare `varchar(100)` reads back as the inline enum `varchar` with the member `100`; and a single-column relation rides its attribute as `-> t(id)` while a composite one becomes a trailing `rel` line, the only spelling that holds more than one attribute. `dbml.test.ts` parses every generated document with `@dbml/parse`, a devDependency the lib build never reaches; AML has no such package, so `aml.test.ts` asserts on the text.
- `schema-sql/Snowflake.ts` is the one generator where `settings.bracketType` picks whether to quote rather than which character: `"` is Snowflake's only delimiter, and a quoted name is case sensitive where a bare one folds to upper case, so `BracketType.none` leaves identifiers bare.
- `@/*` → `src/*` is declared four times — `tsconfig.json`, `vite.config.ts`, `vitest.config.ts`, `e2e/tsconfig.json`. A new alias needs all four.
