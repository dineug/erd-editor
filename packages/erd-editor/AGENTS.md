# erd-editor

## Purpose

The editor core, published on npm as `@dineug/erd-editor`: the framework-free `<erd-editor>` custom element on `@dineug/r-html`, whose Redux-like store's actions carry a Lamport clock version and merge through the LWW registers in `@dineug/erd-editor-schema`. Beside the package root, which exports both element classes and their define functions and defines neither tag, it ships `erd-editor.js` and `erd-viewer.js`, which each define one tag when imported, `<erd-editor>` or the read-only `<erd-viewer>`, and two DOM-free entries, `engine.js`, the headless replica, and `peer.js`, a headless collaboration peer that edits by dispatching actions instead of by a pointer; six workspace packages consume the root, `engine.js` and `peer.js` (Rules § Entries and Consumers). The ERD scene is a Konva `<canvas>` rendered through a second r-html host, `@dineug/r-html-konva`, over the scene geometry in `src/konva/`, and the toolbar, panels, menus and the editing overlay stay DOM. The same scene components also draw the one view, the Visualization tab's Flow mode, and a `GeometrySource` tells them which they draw; a view is the reader's own placement, zoom and rows, never in the file, the history or a peer. A change here keeps the peer graph free of the DOM, and a change to an entry's surface updates the spec that pins it (`src/index.test.ts`, `src/erd-editor.test.ts`, `src/erd-viewer.test.ts`, `src/engine/index.test.ts`, `src/peer/index.test.ts`).

## Making a Change

1. **Read the nested `AGENTS.md` files first.** Open the one in each `src/` directory the change touches and in each directory above it, up to this file; Subdirectories lists all nineteen. Root step 1 says which reads load them on their own, so open each one yourself. For a change another package sees, read that package's file too (root step 1): `mcp-server`'s for `peer.js`, `replication-store-worker`'s and `app`'s for `engine.js`, and `webview-client`'s, `obsidian-plugin`'s and `app`'s for the element's API.
2. **Write the change with its specs** (root step 2). A spec's file name picks its project and its extension follows how it mounts (Testing Requirements). A string a user sees follows `src/i18n/AGENTS.md`: a dictionary key, or a literal where it stays as written.
3. **Run the package's `test` task** (root step 3), which runs `tsc --noEmit`, then the `unit` and `browser` projects:

   ```
   pnpm exec vp run --filter @dineug/erd-editor --fail-if-no-match test
   ```

   The `browser` project needs Chromium; when it fails to start, install it with `pnpm --filter @dineug/erd-editor exec playwright install chromium` and run the task again. A change to an entry's exports, the element's API or a type a sibling reads runs `pnpm test` instead, since the consumers type-check against `dist/**/*.d.ts`.
4. **Run the coverage gate** (root step 4), both projects at 80% per file, since CI fails a file under it:

   ```
   pnpm --filter @dineug/erd-editor test:coverage
   ```

   Testing Requirements gives the form for one file.
5. **Run root step 5**, `pnpm check` then `pnpm build`; the build also writes the two UMD bundles. After the build, run `pnpm peer-graph`, `pnpm dist-shape`, `pnpm consumer-bundles` and `pnpm size` when this package's output or a library it inlines changed (root step 5). The peer graph's rules are in `src/peer/AGENTS.md`. A record past its `budgetGzip` is reported with the measured bytes and what added them, and the budget stays for the owner to re-pin (root § Making a Change).
6. **Run the e2e for behaviour a user sees** (root step 6): `pnpm --filter @dineug/erd-editor e2e`, which builds first. Read `e2e/README.md` before writing an e2e spec. A change to the peer store (`src/engine/peer-store.ts`, `presence.ts`, `stream-flush.ts`, `to-width.ts`) also runs two checks in other packages: `mcp-server`'s `test` task (`pnpm exec vp run --filter @dineug/erd-editor-mcp --fail-if-no-match test`) and `pnpm --filter vuerd-vscode e2e`. Their `scenarios.test.ts` and `agent-hub.test.ts` are the other two completion gates of the peer work (Testing Requirements).
7. **Update the READMEs a user-visible change reaches**, the ones root § Common Patterns lists; this package's `README.md` is the npm page.
8. **Report as root step 7 says.** When the `browser` project or the e2e fails to start, install Chromium as step 3 says and run it again. A missing Chromium is no reason to leave either check out (root § Making a Change). Name each check you leave out and the platform it needs: `vuerd-vscode`'s e2e needs the VS Code that `@vscode/test-cli` downloads, and a display (`xvfb-run -a` on Linux).

## Rules

### Entries and Consumers

- **Six packages depend on this one.** `app`, `webview-client`, `replication-store-worker`, `obsidian-plugin`, which bundles it into its `main.js`, and `mcp-server` depend on it, and `vuerd-vscode` lists it as a devDependency for one spec. A change to an entry reaches each of them, so read their `AGENTS.md` (Making a Change, step 1).
- **`engine.js` is DOM-free.** `app` imports it beside the element, and `replication-store-worker` imports that entry alone.
- **`peer.js` is DOM-free too.** `mcp-server` inlines it into its one file as a headless collaboration peer. `app`'s Drive, fingerprint, collaboration host and IndexedDB schema specs, `obsidian-plugin`'s `src/__test-utils__/diagram.ts` and `vuerd-vscode`'s `src/runtime-value.test.ts` import that entry too. Peer graph rules: `src/peer/AGENTS.md`.

### The Element and Its Hosts

- **Keep host integrations on `ErdEditorElement`.** `webview-client`'s `mountWebview` sets the import callback only when a host passes `importFile` (VSCode does, IntelliJ does not), so the built-in `<input type=file>` is IntelliJ's only import path. The Dictionary tab's Import CSV opens a built-in input in every host, since the callback's types name no CSV, and its export goes through the export callback (`src/components/dictionary/AGENTS.md`).
- **The theme's `system` appearance** (`SYSTEM_APPEARANCE`, `themes/radix-ui-theme.ts`) is a third `ThemeOptions.appearance` beside light and dark. The theme builder lists it first and `changePresetTheme` reports it unchanged. `resolveAppearance()` in `useErdEditorAttachElement.ts` resolves it to the light or dark a host named with `setSystemAppearance`, or to the OS colour scheme `useDarkMode` reads once that is `null`. So `createTheme` takes `ResolvedThemeOptions`, `hasDarkMode()` asks the resolved appearance, and `systemDarkMode` picks `system` when turned on and keeps what `system` shows when turned off. An IDE host names its own light or dark because its page cannot see it, and the hosts keep storing `auto` (`packages/webview-client/AGENTS.md`).

### Packaging and Externals

- **No `sideEffects` field, no `preserveModules`.** Vite reads the package's own field against `src/`, so a `./dist/…` list marks `src/erd-editor.ts` pure and drops element registration. A future list needs `**/` globs covering `erd-editor.ts`, `erd-viewer.ts`, `GlobalStyles`, `konva/workerDomStubs` and `services/elk-layout/elkWorkerRealm`. The draw gate's top-level writes belong to `@dineug/r-html-konva`, whose own `sideEffects: false` holds because every host export reaches them (`packages/r-html-konva/AGENTS.md`).
- **A module that runs something at load is listed with its reason.** `src/sideEffects.test.ts` parses every shipped module of this package and of the six workspace libraries it inlines (tests, stories, `__*__` directories and the three dev pages left out) and pins the ones whose top level runs something: a bare import, a statement, an `if`, or a write or registering call in an initializer. Each sits in its list with why a bundler keeps it: a tag or worker stub module needs a `sideEffects` entry, a bundle's own entry is never pruned, and an initializer runs for the exports that keep it. A new one joins the list, and one that loses its effect leaves it.
- **Put a shipped `src/` third-party import in `dependencies`.** The lib and worker builds externalize exactly that list, so a `devDependencies` entry inlines and its types stop resolving for consumers (root § Working In This Directory, Externals).
- **The private `@dineug/*` libraries inline.** The public `.d.ts` still name `@dineug/r-html` and `@dineug/erd-editor-schema`.

### Path Alias

- **Declare `@/*` → `src/*` in five places.** They are `tsconfig.json`, `e2e/tsconfig.json`, `vite.config.ts`, `vitest.config.ts` and `vite.umd.config.ts`, where it goes after the `@/workers/spawn` entry because aliases match in order. A new alias needs all five (root § Working In This Directory has the rule for every package).

## Testing Requirements

- **The `test` task runs both projects.** `pnpm exec vp run --filter @dineug/erd-editor --fail-if-no-match test` runs `tsc --noEmit`, then `unit` and `browser`. `unit` runs in happy-dom, where `vitest.setup.ts` stubs observers, `matchMedia`, `requestIdleCallback` and a 2D context that draws nothing. `browser` runs in headless Chromium.

Any other gap takes a test.
- **Measure one file within one project.** Pass `--project unit` or `--project browser` with `--coverage.include`; without a project the filter matches nothing.
- **Dev server and Storybook.** `pnpm --filter @dineug/erd-editor dev` builds the workspace dependencies, then serves `vp dev` (`index.html` → `src/index.dev.ts`, r-html HMR). `dev:storybook` / `build:storybook` run Storybook 10.

Read `e2e/README.md` first, because the fixture reopens the closed shadow root and `E2E_PORT` picks the port.
- **A spec's extension follows how it mounts.** A DOM spec that mounts through tagged templates stays `.ts` (proving JSX changed nothing); one that mounts components in JSX is `.tsx` without the pragma (`Toolbar.browser.test.tsx`, `MapColumnsDialog.test.tsx`); a scene spec is `.tsx` under the konva pragma.

- **Destroy the store a unit spec dispatched into.** A unit spec that dispatches into `createTestAppContext()`'s store calls `app.store.destroy()` once it has read what it needs (`src/__test-utils__/diffSeed.ts`'s `diffStateOf`). The `Node is not defined` it then throws lands in a later file's run and fails `ci` with every test passed.

## Common Patterns

- **JSX compiles to r-html tagged templates** through `@dineug/vite-plugin-r-html`. The spellings:
  - `class` / `style` keep array and object values.
  - On a DOM element, `?x` → `bool:x`, `@x` → `on:x` and `.x` → `prop:x`.
  - `${ref(r)}` → `use:ref={ref(r)}`; `...${o}` → `{...o}`.
  - Component props take no dot, because the transform adds it, so `onFoo` is never an event.
  - `<C>{t}</C>` compiles to `` .children=${html`${t}`} ``.
- **Konva scene files open with `/** @jsxHost konva */`**, which compiles against `@dineug/r-html-konva`. The pragma, its intrinsics and what fails its compile: `src/konva/AGENTS.md`.
- **Component conventions live in `src/components/AGENTS.md`.** That covers one directory per component, a second binding of one event, icon colour and the lucide table icon.
- The native list in `primitives/select/Select.tsx`: `src/components/primitives/AGENTS.md`.
- **Name actions by kind.** `somethingAction$` generators live in `generator.actions.ts`, `somethingAction` creators in `atom.actions.ts`. Bitmask flags go through `src/utils/bit.ts`.
- **Restyle both floating bars in one file.** `VisualizationToolbar` reuses `FloatingToolbar.styles.ts`, so a change there reaches both bars.
- **Restyle both dictionary lists in one file.** The domain picker (`ColumnDomain.tsx`) reuses `ColumnLogicalName.styles.ts`, the term list's, and searches through `column-domain/domainOptions.ts`, which the Dictionary tab's picker of a term's domain shares (`src/components/dictionary/AGENTS.md`). Both take their focus, press, wheel and scroll handling from `table-view/column/useHintList.ts`, which the data type list still writes out on its own.
- **Give each part its own theme token.** A color is added per part (`toastError`, `findReplaceError`, `schemaSqlWarningBackground`) in `src/themes/tokens.ts` and `radix-ui-theme.config.ts`, never borrowed from another part's token (an owner decision, 2026-10-11). The diff tokens are the diff viewer's alone. `tokens.test.ts` and `radix-ui-theme.config.test.ts` pin the count.
- **Vendor data types live in `constants/sql/dataType/`.** It lists each vendor's types with their `primitiveType`, the column cell's data type hints and the category the code generators fall back to. `generator-code/columnTypes.ts` reads a type by name first, so a type a list adds reaches the generators through its category unless the classifier or a generator has a rule for its name (`src/utils/generator-code/AGENTS.md`).
- **Keep the parser's type lists in step.** `schema-sql-parser`'s `src/parser/dataType/` keeps a list per vendor, which its `helper.ts` merges into the one set its parser matches type names against, word by word. No test pins the two, so a type added or renamed in one goes into the other (`packages/schema-sql-parser/AGENTS.md`).
