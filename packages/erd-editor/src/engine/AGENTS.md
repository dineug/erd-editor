# engine

## Purpose

`src/engine/` is the editor's store: the action modules under `modules/` with their reducers and undo entries, the action type lists in `actions.ts`, the rx operators and the stores. Reducers merge through the LWW operators of `@dineug/erd-editor-schema`, so peers that hear the same actions in another order hold the same document. A change here keeps three things in step: the action type lists, the file form a host compares for `changed`, and the `actions$` barrels `mcp-server` builds its tools from. The same features have rules in `src/utils/AGENTS.md` (imports, appends, duplicates), `src/services/AGENTS.md` (automatic placement) and `src/peer/AGENTS.md` (the `peer.js` entry and its graph). Others are in `src/components/erd/AGENTS.md` (table groups in the scene), `src/components/schema-sql/AGENTS.md` (the Schema SQL tab) and `src/utils/schema-sql/AGENTS.md` (the constraint names the SQL writers build).

## Making a Change

1. Read the nested file of each other directory the change reaches, listed in Purpose. A change to a change type, an `actions$` barrel or the key set of `peer.js` crosses into `mcp-server`, so read `packages/mcp-server/AGENTS.md` too (root step 1).
2. Carry what each rule below says moves with it: the lists a new action type joins (Actions and lists), the spec the rule names, and `mcp-server`'s `tools/copy.ts` for the foreign key rules.
3. Run `erd-editor`'s `test` task (root step 3). A change to a change type, an `actions$` barrel or the key set of `peer.js` changes an entry's exports, so it runs `pnpm test` instead (package step 3). That run holds the `test` tasks of `mcp-server`, `app`, `vuerd-vscode` and `obsidian-plugin`, which Rules names.
4. For a change to the view seams, run `pnpm --filter @dineug/erd-editor e2e` (root step 6), since `e2e/specs/visualization-flow.spec.ts` asserts what the host hears.

## Rules

### Actions and lists

- **Add an action in four places.** Write it in the module's `actions.ts`, `atom.actions.ts` and `history.ts`, whose undo entry puts it in `HistoryActionTypes`. Then add it to the hand-kept lists in `src/engine/actions.ts`. A type missing from `ChangeActionTypes` compiles, then silently breaks the host `change` (autosave), collaboration and readonly.
- **The action lists enforce readonly.** Readonly is enforced by those lists: while the editor is readonly, `readonlyIgnoreFilter` (`engine/rx-operators/`) drops its own `ReadonlyIgnoreActionTypes` actions (every `ChangeActionTypes` type but the viewport and setting changes `hasReadonlyIgnore` names; a peer's `Tag.shared` actions pass), so a component that hides a control from a reader is not what refuses the edit. A path that does more than dispatch reads `store.getReadonly()` itself before it starts, since the filter drops only its document actions: `undo` / `redo` and `undoSheet` / `redoSheet` in `engine/rx-store.ts`, whose replay passes the filter, and the placed imports and appends (`src/utils/AGENTS.md`).
- **The `actions$` barrels are `mcp-server`'s catalog.** A new change type also needs a tool or an exclusion reason in `mcp-server`'s reachability spec (`src/tools/reachability.test.ts`). Every generator a module's `actions$` barrel exports is part of the catalog `mcp-server` builds its tools from: its `tools/registry.kind.test.ts` holds a census of every key and a reason for each editor generator, so a helper that the barrel's generators call (`loadSchemaAction$`, `toSchemaImportJson`, `withGridPoints`) is exported by name and stays out of the barrel.
- **Reducers write through the LWW operators.** Use the operators from `@dineug/erd-editor-schema` with `action.version`. A direct write wins every merge and corrupts collaborative sessions.
- **A flag undoes to the value it held.** The undo of `table.changeNameDerived` and `column.changeNameDerived` records the flag the entity held before the batch, where the other option bits record the negation of the value sent. So an undo of a write that changed nothing leaves the flag as it was.
- **Reader-only state stays out of every list.** `editor.views`, `visualizationMode`, `handTool`, `zenMode`, `openMap` and `lastCanvasType` are in no list. So they are never saved, undone or sent to a peer. `engine/actions.test.ts` pins the eleven `editor.view*` types and `editor.changeVisualizationMode` out of all of them.

### Settings that travel as changes

- **The Schema SQL scripts are document content** (`settings.ddlScripts`, owner decisions of 2026-10-07). There is one `before` and one `after` string for the whole document. Each is written as is into the DDL of every database.
  - `settings.changeDDLScript` writes each script through a register of its own (`replaceOperator`, `settings.ddlScripts` with the position as the path). So a peer's edit of one script never overwrites the other.
  - The action ignores a position or a value no editor sends. It makes an undo entry (`settings/history.ts`) and is dropped under readonly like every change. `mcp-server`'s `erd_set_ddl_script` sends it too.
  - How the DDL is generated (create, `IF NOT EXISTS`, or drop and re-create) and its header are the window's own choices, no setting: `src/components/schema-sql/AGENTS.md`.
  - An editor built before the scripts ignores the action, and saving a document there drops them.
- **A scroll or zoom is still a change**, unlike one in a Flow view (View seams, below).
  - Scroll and zoom (`settings.scrollTo`, `streamScrollTo`, `changeZoomLevel`, `streamZoomLevel`) stay in `ChangeActionTypes`, which following and shared views need.
  - The replica reports each as a `change`. Every hub (`agent-hub-host`'s `joinWindow.ts`, its Kotlin port) waits for one replica save per change before `join` or `save` answers. A missing save holds them to their caps and has `save` answer `saved: false`.
  - A zoom moves the origin too, keeping the point it zooms around in place (`changeZoomLevelAction$`, `streamZoomLevelAction$`, `pinchZoomAction$`).

### Locks

- **The locks cover the view and code settings** (owner decisions of 2026-10-06). `settings.lockSettings` (`LockSettingType`) locks the viewport, the tab, the language, both name cases, the bracket type and the name view. The viewport lock takes the origin and the zoom as one, since one saved without the other opens elsewhere. Every lock is on in a new document.
- **The name view's lock reads the other way round** (owner decisions of 2026-10-19). `LockSettingType.unlockNameViewMode` (64) unlocks `settings.nameViewMode` while set, so a new document keeps 63 and every file, with `lockSettings` or without, opens with the name view locked. Whether a setting is locked is read through `erd-editor-schema`'s `isSettingLocked`, and a lock is turned on or off through `setSettingLock`, which take one bit and throw a `RangeError` on a mask; a mask is read bit by bit over `LockSettingTypeList`. A copy of the bits as they stand needs neither, as `landLoadedSettings` takes each lock's bit from a load, and nor does a read of bits that are not inverted alone (`packages/erd-editor-schema/AGENTS.md`, Settings and locks).
  - `settings.changeNameViewMode` carries `shared` and `editorId`, which `toNameViewModeAction(state, value, readonly)` sets: `shared` while the lock is off and the store is not readonly. The caller passes `store.getReadonly()`, which no state holds.
  - A shared switch writes the name view's register (`replaceNameViewMode`, `settings.nameViewMode`) on every peer and replica, so it is saved and followed.
  - Any other switch shows on the store whose `editor.id` the payload names alone, outside the register, and every other store drops it, whatever its tags. A replica strips the tags before its reducers and its `editor.id` names no window, so it drops every one: a window's own switch and the one a host relays from another view alike. A switch without `shared` reads as not shared, one without `editorId` as another store's.
  - The `editorId` rides in the payload, since the shared store adds `meta.editorId` only to what it sends, so the sender's own dispatch has none.
  - It is in `SharedFollowingActionTypes`, readonly lets it through (`hasReadonlyIgnore`), as the reader's own screen, and it makes no undo entry.
- **A locked setting saves its locked value.** `toDocumentJson`, the file form every `value` getter returns, writes a locked setting at `settings.lockedValues`, as `toJson` does. So a change to it comes out `changed` false, and the hosts write nothing and mark nothing modified. Those hosts are `vscode-extension`'s `erd-editor.ts`, `obsidian-plugin`'s `ErdView.ts` and `intellij-plugin`'s `ErdEditor.kt`.
  - `app`'s Drive save leaves a view no lock holds out of its fingerprint.
  - The element's `change` event leaves such a change out. `lockIgnoreFilter` on `rx-store.ts`'s `change$` filters it by `LockSettingActionTypes`, reading the lock as the batch passes. The replica still reports it for the hubs.
- **Locking and unlocking carry values.**
  - `changeLockSettingsAction$` locks at what the store holds and carries the values, so every peer and the replica hold one lock.
  - An unlock carries what the store shows of the settings it names in `UnlockCarriedSettings`: `CodeLockSettings` (the language, both name cases and the bracket type, whose setters every peer applies) and the name view, which each reader held as its own while locked. Every peer and replica then show those values, so all save one value.
  - A reader that opened the file while the lock was on still shows the value it held (`replication-store.test.ts`, an unlock after a reader joined from the file).
  - An unlock of the viewport or the tab carries nothing, since each reader's screen is its own.
  - Taken on the Settings tab, a tab lock locks `editor.lastCanvasType`: the last tab other than Settings the reader stood on. `changeCanvasType` and both load reducers record it before and after they move the tab.
  - Locking a setting is a change of its own, readonly-ignored like the rest.
- **Each lock bit is a register.** The reducer writes each bit through `replaceOperator` (`settings.lockSettings`, the bit as the path), setting it with `setSettingLock`. So the latest lock or unlock of a setting wins on every peer.
  - The reducer refuses a lock whose values the setting's own setter would refuse, the Settings tab included.
  - An unlock sets what it carries whether it wins the bit or not, skipping a value the setter would refuse.
  - The four code setters and an unlock's values write through one register per setting, outside the bit's (`replaceCodeSetting`, `settings.code`, the field as the path). The shared name view switch and an unlock's name view share `replaceNameViewMode`'s. So a setter and an unlock that cross land one value on every peer.
  - An unlock and a newer relock that cross show one value on every screen while the relock holds the file (`replication-store.test.ts`, an unlock crossing a newer relock). A version tie is the exception, as everywhere.
- **The replaced switch stays for older agents.** `settings.changeIgnoreSaveSettings`, the switch the locks replaced, has a reducer that changes nothing. It is in the replica's lists alone (`ReplicaChangeActionTypes`, which `ReplicaActionTypes` takes in), not `ChangeActionTypes`. So the replica reports a batch an agent written before the locks sends (`changed` false), and the hub waiting on it confirms the save. The element fires no `change`, and no peer is sent it.
- **The Lock rows show each lock's value.** The Settings tab's Lock rows (`components/settings/lockSettingRows.ts`) show the value each lock holds, or the live value dimmed while the lock is off. Each value reads by the name the menu that sets it gives, and the name view's as Physical Names, Logical Names or Both Names. The viewport shows as its zoom and its origin, the origin shortened with the unit the content compass prints (`formatDistance`: `12k`, `-2.4k`).

### Loads and new documents

- **A new document starts with every lock on**, so looking around a new diagram never changes its file. The store's initial state is `erd-editor-schema`'s `createSchema()` (`lockSettings` 63, whose clear 64 bit is the name view's lock).
  - That document is what an element given no value shows. A replica's or a peer's `value` shows it before a load (`app`'s new Drive file, `mcp-server`'s `createEmptyDocument`), and so does every empty value a load takes.
  - `utils/loadValue.ts`'s `toLoadValue` turns an empty text into that document's JSON for `setInitialValue`, the `value` setter, `setDiffValue`, the replica and the peer. So the replicated `editor.loadJson` carries text that any peer, a released one included, parses to the same document.
- **A file keeps the locks it names.** One that names none (an older v3 file, a v2 `.vuerd`) opens with all of them on. Its origin, zoom and tab are where a new document's are (`erd-editor-schema`'s `resetPreLockView`). A load from a release before the locks names none, so it turns every lock on, as opening a file it wrote would.
- **An import keeps the settings it replaces.** A SQL, DBML, AML or GraphQL import keeps every setting of the document it replaces but the view, the locks included. The locked view is set where the parser left the view (`withImportSettings`, under `toSchemaImportJson`, which `loadSchema*Action$` and a placed import share).
  - A source given to an element with no value, as `app`'s `convertSource` does, so becomes a new document too.
  - A source imported into a file keeps that file's locks (`useErdEditorAttachElement.test.ts`).
  - Placed imports and Import and Add appends: `src/utils/AGENTS.md`.
- **An import keeps the dictionaries too** (owner decisions of 2026-10-20). The clear and the load of a SQL, DBML, AML or GraphQL import carry `keepDictionaries: true`: `loadSchemaAction$` and a placed import's landing pass it to `loadJsonAction$`. Both reducers then leave the store's words, terms and domains and its three `doc` lists as they are, the arrays themselves, so no membership set is built again. The text holds no dictionary, so nothing copies one into it.
  - The undo of a flagged clear or load carries the flag, and its text leaves out the words, the terms, `doc.wordIds` and `doc.termIds`. It keeps the domains, since the parser clears every column's link to a domain the text does not hold.
  - So an import's undo and redo leave a dictionary edit made in between as it is, and its undo batch carries no word or term (`editor/history.test.ts`). A column they bring back linking a listed domain off the type it holds now takes that type, and one off a removed domain's type is unlinked, in the second batch any document replay settles with (`replayDocument`, A domain governs the type of every column linking it).
  - Every other replace takes the whole document, dictionaries included: a JSON replace, the `value` setter, the element's `clear()` and the undo of an unflagged load. Such an undo puts the rows back as they stood before the load, over an edit a peer made since.
- **`clear()` keeps every setting**, so a cleared file keeps its locks. It empties the dictionaries with the rest; only a schema import's `keepDictionaries` keeps them.
- **Unreadable text empties the document.** Text the parser cannot read, such as a file with merge-conflict markers, empties the document and changes no setting (r-html logs the reducer's throw). So a store that loaded nothing before shows a new document (`replication-store.test.ts`).
- **Time Travel's preview opens on the reader's view.** It opens on the reader's scroll and zoom whatever the lock says (`toPreviewJson`), since it is the reader's own screen.
- **A replacing load keeps each locked screen.** Every load that replaces the open document goes through `landLoadedSettings` (for imports, an owner decision of 2026-10-06). Such a load is `editor.loadJson`: an import, the undo of a load or a clear, a peer's load, the `value` setter.
  - On each store, it keeps the screen of each locked setting where it was, the viewport excepted.
  - It takes each lock through its register. It takes a bit no lock owns from the load, as it takes `show`.
  - The view lands where the load puts it and is pulled as any load's is.
  - A load that opens a document (`editor.initialLoadJson`) takes everything the file holds.

### Values and `changed`

- **Two values, two readers** (owner decisions of 2026-10-10): every `value` getter (the element's, `ReplicationStore`'s, `PeerStore`'s) returns the file form, `toDocumentJson`, and every `runtimeValue` getter `toJson`, the document as the store holds it, removed entities included, which a collaborator's or a second view's `setInitialValue` takes, since an undo of a removal another peer sends restores the entity whole only where its tombstone is held. Inside the editor what reloads the document reads `toJson` (the undo of a load in `editor/history.ts`, Time Travel, the diff viewer, automatic placement, the image export), and only what leaves as a file writes `toDocumentJson` (the JSON export of the menu and the palette).
- **No collector removes tombstones.** Nothing collects a removed entity: the schema GC, its SharedWorker and the per-entity `meta` it timed itself by are gone, since replicas that loaded at different times collected different tombstones and diverged; the runtime value keeps every tombstone until the document is next opened from its file, whose form leaves them out.
- **`changed` compares values, never the file.** The replica keeps the value its last `change` handed out, the file form `toDocumentJson` writes. After a load it takes the value the first change action finds.
  - That form leaves out removed entities, `zIndex`, the widths, the anchors, the key marks and the relationship flags. So these come out `changed` false: a table added and removed within one change, an edit landing on a removed table, and a load that restacks alone.
  - A file an older release wrote, a v2 `.vuerd`, a byte order mark or a hand edit all differ from that value from the load on. So a host that compared bytes with its file would take the first scroll for an edit.
  - A load that lands while a change is pending reports that change with `changed` false.
  - The cases `replication-store.test.ts` pins are under Testing Requirements.
- **Both load reducers end in `settleDocument`** (`engine/settle.ts`). It runs before the view is pulled and writes what the document derives, listed below. So the element, a replica, a peer and a scratch store all hold those values when the reducer returns. No hook wakes on a load, and a pan replayed right behind it is no edit.
  - The primary key mark of every column, from its options, and the foreign key marks.
  - Every `ui.width*`, measured again with this machine's fonts.
  - The relationship anchors.
  - Every connector's route, in a store that draws. A peer and a replica draw nothing, so their `EngineContext` says `routes: false` and their load routes none. Routing a document of hundreds of relationships was most of its cost, and only a drawing reads a route.
  - Each relationship's `identification` and `startRelationshipType`. One removed, or one whose end columns are all gone, gets a new relationship's values.
- **A value a load derives joins `settleDocument`.** Put it there, never in a hook on an action a load dispatches, that load's `editor.clear` or `editor.initialClear` included.
  - `store-hooks.test.ts` holds this by recording what both load generators and a replica's `setInitialValue` reduce. `engine/settle.test.ts` holds that nothing rewrites the value after it.
  - Keep such a value out of the file form, since a file another machine wrote would differ by it. `app`'s `toFingerprint` and `toDriveFingerprint` read that form whole (`app`'s `utils/documentFingerprint.ts`; `packages/app/AGENTS.md`).

### Derived key values

- **Derived key values read the whole document.** The foreign key bits and each relationship's `identification` and `startRelationshipType` are read whole off the document. So peers that took the same actions in another order hold the same values.
  - The readers are `validateForeignKeys` in `table-column/keys.ts`, and `recalculateIdentification` and `recalculateStartRelationshipType` in `relationship/endFlags.ts`.
  - Those modules import no action module. So `settleDocument` calls them from the load reducers without an import cycle, and the hooks share them.
  - Bits set and cleared one relationship at a time cleared a column another relationship still ended on. A link that woke no hook left the fields at their defaults on one peer and derived on another.
- **A column's bit follows the document.** It is on exactly while its table is in the document, the table lists it, and a relationship in the document ends on it there. So a removed column, or one of a removed table, has it off, whatever order its peers heard the removal and the link in. The runtime value holds such a column, and the file form leaves it out.
- **A relationship reads only live end columns.** It reads only the end columns its end table holds while that table is in the document. With none left it is not identifying and dashed, as a new one starts.
  - A removed relationship reads none. So the tombstone the runtime value holds carries those values on every peer, whatever it was remapped or keyed onto before the removal arrived.
- **The bits are read once per batch**, in the microtask after it. They use no timer, since a host reads a value one scheduler turn after a batch, as `mcp-server`'s headless session does before it writes its file. They are read on these:
  - a relationship added, removed or remapped (`relationship.changeColumns`);
  - a column or table added or removed, an undo's included;
  - a load's reducer, before it returns.
- **The relationship fields follow the same reads.** The two fields are read the same way, on those actions and on the primary key flag. The start is also read on the not null flag, which a key turned on sets with no action of its own, in the microtask after its batch.
  - So the start is read one microtask after the identification. Otherwise a batch keying two end columns at once left it ringed (`peer-store.node.test.ts`).

### View seams

- **While a view is active, two seams act** (`rx-store.ts`). Each applies while `getActiveView` finds a view.
  - `viewActionRedirect` rewrites `settings.scrollTo` / `streamScrollTo` / `changeZoomLevel` / `streamZoomLevel` into their `editor.view*` twin. It leaves a `Tag.shared` or `Tag.following` action as it is, since a peer's placement and a follow of one belong to the document however the reader stands.
  - `viewIgnoreFilter` drops `ViewIgnoreActionTypes` (readonly's list minus `editor.loadJson` / `editor.clear`), letting `Tag.shared` reach the store.
  - `undo` / `redo` no-op while a view is active. In the Flow the Visualization tab takes their chords to step through the centers the view stood on (`src/components/AGENTS.md`, Scene sources and views).
- **Leave a view and move in two dispatches.** Both seams classify a batch by the state it enters with. So leaving a view and moving the document are two dispatches. `goToErdTable` (`components/erd/canvas/table/goToErd.ts`) is the model, and `e2e/specs/visualization-flow.spec.ts` asserts what the host hears.

### Foreign key columns

- **Foreign key names come from `toForeignKeyNames`** (`engine/modules/relationship/fkColumns.ts`). It is the one place they are named. The pointer draw (`selectTableAction$`), `addRelationshipAction$` and a New column row of Map Columns (`mapColumnsAction$`, through `toForeignKeyActions`) all run it. `fkColumns.test.ts` pins each case below.
- **A one-word key gets the table prefix.** A key of one word (`id`, `ID`, `uuid`, `id2`; `isSingleWord`) gets the parent table and an underscore in front. A key of several words (`member_id`, `userId`, `UserID`) or equal to the table name keeps its name. A name the child already holds is numbered `_2`, `_3`.
  - Only an equal name escapes the prefix, an owner decision. A key of one word that holds the table name gets it too (`user.userid` gives `user_userid`, `회원.회원번호` gives `회원_회원번호`).
- **Words split on case and non-letters.**
  - Any character but a letter, mark or digit splits words, so `_id` and `order-no` keep their names.
  - Words split where camelCase splits them, so `IDs` and `UUIDv4` keep theirs too. `Ids` is one word, as is a name in one case (`memberid`, `USERID`: `members_memberid`).
  - Words also split where a letter without case (`\p{Lo}` or `\p{Lm}`: Hangul, kana with its `ー`, Han) meets a cased one, either way. So `회원ID`, `ユーザーID`, `用户ID` and `IDカード` keep theirs, while `회원번호` is one word.
  - Digits and marks are passed over when reading case, so `SHA256sum` is several words and `md5sum` one.
- **The table name is used as written**, dots and spaces included (`public.users` gives `public.users_id`), an owner decision. Such a column makes valid DDL only under a quoting `bracketType`. There every generator also keeps the whole name in the relationship's constraint (`"FK_public.users_TO_orders"`).
  - Unquoted, SQL Server, Oracle, MySQL, MariaDB and PostgreSQL give that constraint the table part alone (`FK_users_TO_orders`; the SQL writers: `src/utils/schema-sql/AGENTS.md`). SQLite writes it unnamed. Snowflake and Databricks keep the whole name (`FK_public.users_TO_orders`).
- **Relating existing columns renames nothing.** That covers Map Columns, `erd_link_columns`, the importers and duplicates. Map Columns alone changes their type: it brings each child column it maps to its parent's type through the data type sync, in the same batch. It does so only while `settings.relationshipDataTypeSync` is on.
- **A serial key's copy takes its integer type** (owner decisions). `toReferenceDataType` (`relationship/referenceType.ts`, DOM-free for the peer) sets it, whatever the data type sync says.
  - PostgreSQL's own `smallserial`, `bigserial` and `serial2` / `4` / `8` map by PostgreSQL's types under any database.
  - A bare `serial` maps by `settings.database`: `integer` in PostgreSQL, `bigint unsigned` in MySQL and MariaDB, kept elsewhere.
  - Only a whole name maps, in capitals when the key's is. No saved document is migrated.
  - The data type sync (`table-column/utils/dataType.ts`) maps a key's change into its foreign keys the same way. It carries a foreign key's change back to its key unless the key's type is serial, which keeps it and stops the change there.
  - The sync reads the relationships once per walk, into each column's steps (`toSyncSteps`), since a domain's type starts it from every column linking it. Read once per column popped, a domain linked by 15,000 columns held the Dictionary tab for 4.8 s on 2026-10-21; read once, 0.19 s. `dataType.test.ts` holds the walk to the one that read each relationship per column, order included.
- **A copy links its key's domain.** `toForeignKeyActions` gives each copy its start column's `domainId` while the document lists that domain (the `domainIds` each caller passes from `doc.domainIds`) and `toReferenceDataType` leaves the type as it was. A serial key's copy that `toReferenceDataType` gives another type (PostgreSQL's own serial types under any database, a bare `serial` under PostgreSQL, MySQL and MariaDB) links none, while a bare `serial` kept as it is elsewhere keeps the link. A key linking a removed domain hands on no link. The copy also takes its key's logical name, when it has one, after the comment (an owner decision of 2026-10-23), whatever name the copy takes, and with its derived flag off, since `toForeignKeyNames` names it. So a copy named `users_id` whose logical name a term matches shows the physical name mismatch, which the owner takes as the right warning. `fkColumns.test.ts` pins each case and `relationship/generator.actions.test.ts` the copy through a store.
- **`mcp-server`'s descriptions state these rules.** The `erd_add_relationship` and `erd_change_column_data_type` descriptions (`tools/copy.ts`) state them to agents, so they change with the code.

### Table groups

- **Membership is the table's `groupId`** (an owner decision). The model is in `engine/modules/table-group/`, and the DOM-free helpers in `utils/tableGroup.ts`, inside the peer graph. `groupId` is written through one register per table (`table.changeGroup`, path `groupId`). So a table is in one group at most, and two peers placing it converge on the later write.
  - A `groupId` naming no group in `doc.tableGroupIds` reads as none everywhere (`getTableGroupId`, `getTableGroupMemberIds`).
- **A group's box covers its members.** A group stores its own rect. Its box is that rect united with each member's rect grown by `TABLE_GROUP_PADDING`, and on top by `TABLE_GROUP_TITLE_HEIGHT` more. So a member that grows sticks out of nothing and writes nothing.
  - `padRect` and `getTableGroupRect` compute the box. `getTableGroupRect`'s `excludeTableIds` leaves out the tables a drag holds, and its `members` spares the walk over every table.
- **Membership reads a table's centre.** A membership test reads a table's centre in the topmost box (`findTableGroupAt`). The topmost box has the highest zIndex; of two at one zIndex, it is the later in `doc.tableGroupIds`.
  - `findTableGroupsAt` answers many points off one read of the boxes, as a drop does, and builds none for no point.
- **Read every group in one walk.** Whatever needs every group reads them out of one walk over the tables, never a walk per group. A pan step reads the content rect several times over, and a drag step reads the drop boxes.
  - `getTableGroupRects` gives every box (`seedTableGroupBoxes` / `growTableGroupBox`, which the content rect folds into its own pass).
  - `getTableGroupMembers` gives every member list.
- **A drop judges the loose selected tables.** `getTableGroupDrops` judges the selected tables no selected group carries. It reads no box with none to judge (a drag of groups alone). It hands each drop the box of the group it lands in.
  - A group the drag leaves standing reaches over the box it held as the drag began (`HeldTableGroupBoxes`; `src/components/erd/AGENTS.md`).
- **Removing a group is one dispatch.** `removeTableGroupAction$` clears every member's `groupId` and removes the group in one dispatch, so one undo brings back both. Removing a table needs nothing more.
- **A group moves with its members.** Moving a group (`moveTableGroupAction$`, and `moveAllAction$` over a selected one, `toMoveTableGroupActions`) moves its members by the same relative step in the same dispatch, tagged as a drag. A member selected beside the group moves once.
  - `tableGroup.move` and `tableGroup.changeColor` regroup with the table and memo streams, so a drag is one undo entry.
- **A drag carries its first step's tables.** A drag carries the tables its first step read (`getCarriedTableIds`), kept in the `MoveAllGesture` that `useMoveEntity` makes per press and hands every step. The history and the outbound compressor sum a burst's steps per table list and drop a list under 20 px. Otherwise a member a peer adds or takes out midway would leave a step applied here and never sent or undone.
- **Four paths select a group** (`SelectType.tableGroup`): a press, adding a group, an append's landing and a marquee that encloses its whole box.
  - A press (`selectTableGroupAction$`) raises the group among groups by `nextTableGroupZIndex`. `tableGroup.changeZIndex` is in no list, as `memo.changeZIndex` is in none.
  - The same press raises the group's tables over every other table and memo, in their own order, with `table.changeZIndex`, as a press on a table raises it, and sends none once they stand there. Otherwise a group drag draws them in the drag layer over the rest and its drop puts them back under it.
  - Adding a group selects it alone.
  - A marquee in the document takes a shown group only once it encloses the group's whole drawn box, edges included (`takenTableGroups` in `dragSelectAction$`, an owner decision of 2026-10-11). A centre rule, which tables and memos follow, would take a group with every marquee drawn inside it to pick a few of its tables, and the drag or Delete after it would reach the whole group.
  - Select all never takes a group. Delete (`removeSelectedAction$`, and `getRemovableColumns` reading a selected group as a selection beside the table) and the color picker reach it.
- **A paste or duplicate carries no `groupId`.** An append carries its document's groups under new ids, its tables put in them by their new ids (`toAppendTableGroups`).
  - A file's rects move with the block, which starts at their corners too.
  - A grid or placed layout wraps each group with members round where they land, the block starting at the wrapped corners as well (`toLayoutGroupRects`).
  - Duplicates and the clipboard: `src/utils/AGENTS.md`. Automatic placement, which keeps table groups together: `src/services/AGENTS.md`.
- **A resize is one undo entry per write.** `tableGroup.resize` is undone to the rect the group stored before it. A sash drag writes it once, at its end (`src/components/erd/AGENTS.md`).
- **A drop's regroup undoes with the drag.** A drop's `table.changeGroup` carries the `groupId` it replaces as `prevValue`, and `Tag.drag`. The `@@move` regroup in `rx-store.ts` takes it in by tag (`groupByStreamActions`), so its undo closes into the drag's entry. The undo builder reads `prevValue`, since that entry is built once the reducer has run.
- **Adding a group takes a name and color.** `addTableGroupAction$` and `addTableGroupFromTablesAction$` take an optional name and color. `mcp-server`'s `erd_add_table_group` sets them in the batch that adds the group, where the editor names a group by its name editor afterwards.
- **`peer.js` exports both group barrels** for `mcp-server`'s group tools. Those tools send every group change type but `tableGroup.moveTo`, which no gesture sends either.

### Dictionaries and derived names

- **Three dictionaries in one module** (owner decisions of 2026-10-20). `engine/modules/dictionary/` holds the words, terms and domains. `dictionary.add`, `dictionary.update` and `dictionary.remove` name the row by its `kind` (`DictionaryKind`: `word`, `term`, `domain`) and `id`. An add or an update carries `values`, the fields `DictionaryStoredFields` lists for the kind: the `DictionaryFields` values and `order`, the row's key (A sheet's order is its rows' keys, below). A kind, a field or a value that is no string, which a later release could send, is passed over.
- **An add makes the identity, then writes each field.** `dictionary.add` makes the row with `getOrCreate` and its id alone and lists it through `addOperator`. Then it writes each value it carries through `replaceOperator` at the add's own version, one register per field, as `dictionary.update` does.
  - Never `addOne` with the values: a peer's update that arrives first leaves a stub, `addOne` passes over a row that is there, and the values are lost. `table.add`, `memo.add` and `tableGroup.add` still carry their `ui` that way, so they are no model for a new add.
  - `column.add` carries the identity alone, as the dictionaries do.
- **A remove keeps the values, and its undo carries none.** `dictionary.remove` unlists the row and keeps its values in the collection. Its undo is an add without values, so the row comes back with what its registers hold, a peer's edit made meanwhile included.
  - A removed row keeps its order key with its values, so an undone removal lists it in its place again (A sheet's order is its rows' keys, below).
  - An update's undo is the value the row held before the batch in each field the update writes. An add that lands on a row already listed lists nothing, so its undo is those values too, never a remove.
- **Membership is one set per list.** `membership.ts` keeps a set per `doc.wordIds`, `doc.termIds` and `doc.domainIds` array in a `WeakMap`, which `isListed` reads and `listId` and `unlistId` write with the list. A load brings new arrays, so a set is built once per list a load brings; one that keeps the dictionaries keeps the arrays and builds none. A list whose length moved past those two writes is read again.
  - Never ask a dictionary list through `arrayHas` in a reducer: it builds a set on every call, which turns an import of thousands of rows quadratic. `membership.test.ts` counts the builds over 13,176 adds.
  - Rows leave a list from its end. `unlistId` looks with `lastIndexOf`, `removeDictionaryEntriesAction$` sends its removes from the end of the list back, and `push` in `history.actions.ts` turns round the adds and removes of each undo (`reverseDictionaryListings`), so the undo of an import removes from the end and the undo of a removal lists the rows again in their order. A splice in a state list moves every later element through the observable proxy, so removing a whole sheet from the front is quadratic in the editor's store, though a peer store's plain arrays hide it.
- **A removed domain keeps its links.** Removing a domain clears no column's `domainId` and keeps the column's `dataType`. `getLiveDomainName` names no domain for an id no row lists, so nothing shows the link, and the file form leaves it out (`packages/erd-editor-schema/AGENTS.md`, Entities). A type written to such a column that differs from the removed domain's type unlinks it as a live domain's would (A domain governs the type of every column linking it, step 3), and so does a document undo or redo that links it back, brings it back or types its domain, leaving it off that type (`replayDocument`), and a sheet replay that writes the removed domain's type, leaving it off that type (`replayRows`, The Dictionary tab's edits undo per sheet). So, crossing peers' writes aside, a link a removed domain keeps holds that domain's type, and listing the domain again, by either history's undo of its removal, leaves no column off it.
- **The domain cell is measured by the domain's name.** A column's `ui.widthDomain` is the width of `getLiveDomainName` of its link: nothing while the domain is not listed.
  - `column.changeDomain` measures its column. A rename of the domain, an add that lists it or renames it (an undone removal's included) and a remove that unlists it measure every column linking it.
  - Those writes measure a removed column too, so each width reads the domain as it stands whatever order a peer heard the domain's and the column's changes in.
  - They find those columns through `domainLinks.ts`, each domain's linking column ids, removed columns included, built once per column collection (a load brings a new one) and moved by `column.changeDomain`, the one write of a link (`domainColumnIds`, `relinkDomainColumn`). Walked over every column per domain, 500 domains listed beside 15,000 columns took 2.7 s in the editor's observable store on 2026-10-22; through the index, 21 ms. `dictionary/atom.actions.test.ts` holds the index to that walk after random writes and loads, and reads each column's link once over 500 domains listed and unlisted.
  - `settleDocument` measures every live column on a load, the logical names' widths beside it.
- **Logical names are plain fields.** `table.changeLogicalName` and `column.changeLogicalName` write `logicalName` through a register of its own and measure `ui.widthLogicalName`. The derived flags are `table.changeNameDerived` (the table's `nameDerived`) and `column.changeNameDerived` (the `ColumnOption.nameDerived` bit, path `options(nameDerived)`).
- **An index is built once per write of its sheet.** `dictionaryCache` keeps what it builds per collection object until the sheet's generation moves or its id list changes. Only the three dictionary reducers raise the generation (`raiseDictionaryGeneration`), so a table or column edit builds nothing again, and a load brings new collections no index was built over.
- **A name is compared trimmed and composed, its case kept** (`normalizeDictionaryName`): a term matched to a logical name, two rows of one name and an import's row matched to the sheet. Only completion compares in lower case. A row with an empty name matches nothing and is never refused.
- **A name splits at its separators, then word by word** (`derive.ts`, owner decisions of 2026-10-20). `decompose` cuts the logical name at blanks, `_`, `-`, `·` and `/`, no word crossing a cut, then reads each part from the left, taking the longest text the word sheet marks and never going back: words 가입, 가입일 and 일자 leave 가입일자 with an unregistered 자. `compose` joins the words' abbreviations as typed with `_`, with no length limit and no name case, which stays the code generators'; a stretch that is no standard word, or a word with no abbreviation, composes nothing. `derivePhysical` takes the term first, else the composition, else null.
- **A logical name derives the physical name.** `setColumnLogicalNameAction$` and `setTableLogicalNameAction$` write the logical name and the derivation in one dispatch; `deriveColumnNameAction$` and `deriveTableNameAction$` derive from the logical name held, as an editor closes. `setColumnLogicalNamesAction$` writes several columns' at once, as Replace All does, reading the domains they link once over all of them, as the rule on a domain's type below asks; only the editor sends it, so it is exported by name and stays out of the barrel.
  - The derivation runs only while the physical name is empty or derived. The term of the logical name comes first: its physical name, or the words' composition when it holds none, and for a column its live domain, linked as `setColumnDomainAction$` links one. Otherwise the words compose the name. A name written turns the flag on.
  - A logical name that derives no name leaves the name and the flag as they are; so do an empty word sheet and an empty term sheet, each passed over. A term with no domain unlinks nothing.
  - Nothing is sent for a value already held, so a repeated write makes no undo entry.
  - A logical name pasted over a column or with a new one derives the same way (`pasteTableAction$` through `toColumnNameWrites`), unless the row pastes a name; the rules of a pasted row are in `src/utils/AGENTS.md`, Name views on the clipboard.
- **Deriving again takes the flag back.** `rederiveNamesAction$` covers one column, one table with its name and every column, the selected tables or the whole document (`RederiveScope`). It turns each covered flag on and derives again, in one dispatch and one undo entry. A name with no logical name is left as it is.
- **The checks only read** (`checks.ts`, owner decisions of 2026-10-20). `DictionaryCheckCode` holds seven: a name two listed rows of a sheet share, a link to a domain the document does not list and a forbidden word are errors, and an unregistered word, a synonym, a physical name other than the one the matched term gives and a column's type other than the type of the listed domain it links (`domainTypeMismatch`, on the domain cell) are warnings (`DictionaryCheckLevelOf`). A synonym and a forbidden word suggest the standard words, a name mismatch the physical name the term gives, a type mismatch the domain's type, and nothing is replaced.
  - Each check runs only while the sheet it reads holds a row, so a document with empty dictionaries marks nothing: the word checks need a word, the name mismatch a term, the unknown domain and the type mismatch a listed domain.
  - The type mismatch marks what no dispatch can keep (an owner decision of 2026-10-22): A domain governs the type of every column linking it (below) holds at the end of each dispatch, but a peer's link that crosses another peer's write of the domain's type converges on a column off that type in every replica, with no undo involved. A removed domain's link shows as the unknown domain alone.
  - `checkTable`, `checkColumn` and `checkDictionaryRow` read the cached indexes, so a mark on the cells in view walks no sheet, and `markOf` gives a cell its loudest level. Only the Dictionary tab and `mcp-server`'s `erd_list_checks` ask for the whole document's checks: the check sheet lists them once a frame (`listDictionaryChecks`, which `peer.js` exports for the tool), and the check sheet's count walks them a slice per idle period while another sheet shows (`walkDictionaryChecks`, `src/components/dictionary/AGENTS.md`).
- **A walk checks a target again only once a value its checks read has moved** (`walkDictionaryChecks`, which `listDictionaryChecks` runs to its end, in the same order and with the same checks a fresh walk of `checkTable`, `checkColumn` and `checkDictionaryRow` gives). It holds each term's, table's and column's checks by id, a map per collection object, so a load starts afresh but for the dictionaries an import keeps, and keys them on values, never on the entity object, which the store writes in place:
  - the reading, the text the words read (a term's name, a logical name) with the word index, which is one object until the word sheet is written again, so a word's write reads every name again, each text decomposed once per walk;
  - a table's name and the physical name of the term its logical name matches; a column's table, name, that physical name, the text its unknown domain shows (`unknownDomainText`), its type and the type of the listed domain it links (`linkedDomainType`); a term's shared name (`sharesName`) and its unknown domain. So a table or a column edit builds that target again alone, a term's write only the term it wrote and the targets whose matched physical name or shared name it moved, and a domain's type write only the columns linking it.
  - The word and the domain sheet's checks are held per index, and the term sheet's per its three indexes, so a write outside the dictionaries walks no row of them.
  - A walk run to its end forgets the targets it did not meet, a removed one among them; one dropped part way forgets nothing. A walk takes the three indexes as it begins, and every check that reads an index reads those: each sheet's duplicate names, the words a name reads and the mismatch. Each step reads the rest as it meets it: a row's, a table's and a column's own values, the domain list a link is checked against and the type of the domain it links. So its steps agree on one state only while no batch comes between them, and a caller that stops between steps drops it on the next batch that raises the checks, as the Dictionary tab does.
  - `checks.walk.test.ts` holds the listing to a fresh walk after every random write, undo, load and walk dropped or interleaved part way, on both kinds of store, and fails when a key leaves out a value read; its random writes part a column's type from its domain's by the atoms, and its unit cases pin what a table's, a term's, a word's, a domain's type and a column's type write build again, what a walk forgets, and the domain sheet's duplicates a walk resumed past a write finds on the index it began on.
- **A domain governs the type of every column linking it.** At the end of a dispatch a column linking a live domain holds that domain's data type. Each generator that writes a domain's type, a link or a column's type reads its whole dispatch once through `toDomainTypeActions`:
  1. Each live column of a live table linking a domain the dispatch changes or links takes that domain's new type first.
  2. While `settings.relationshipDataTypeSync` is on, the data type sync spreads from those columns and writes none of them again (the settled ids `getDataTypeSyncColumns` takes). Read row by row, two related domains changed in one commit, or a serial domain linking a key and its foreign key, would leave a column off its own domain's type by stack order.
  3. A column the dispatch writes a type to that then differs from the type of the domain it links, listed or removed, is unlinked (`column.changeDomain` with `''`) in the same dispatch, a foreign key the sync reached included.
  - `setColumnDomainAction$` links a live domain and writes its type the same way, and `''` unlinks alone. A column whose type a dispatch leaves equal is sent nothing.
  - A typed type unlinks the same way. `changeColumnDataTypeAction$`, which the type cell and `mcp-server`'s `erd_change_column_data_type` send, passes the column as a direct write, always sent, and the sync spreads from it.
  - The unlink is the sending generator's, never a reducer's. A peer of a release before the dictionaries sends `column.changeDataType` alone, so the column keeps its link, and the domain's next type write gives it the domain's type again.
  - A document undo or redo dispatches the batch its entry recorded (`replayDocument`, `history.actions.ts`), so a paste's redo or the undo of a serial key's unlink writes no foreign key the entry did not. Then, read on the state that batch left, a second dispatch of the same command settles the live columns the replay touched (each in its table while the document lists the table) that it leaves off their domains, and only those (`settle`), as the generators would now:
    1. A governed column that links a listed domain off that domain's type takes it through the links of `toDomainTypeActions`, the sync spreading from it over the relationships as the replay left them. Governed are the columns the entry links, those it brings back with themselves or their table, each live column linking a domain the entry types, and after a load that keeps the dictionaries (a schema import's undo or redo, which brings columns back at the types the entry recorded under the domains as they stand now) every live linked column. So the undo of a domain's type written outside its sheet (`mcp-server`'s `erd_update_domain`) types a column a peer linked to it since, and a key brought back with its table spreads its domain's type over the relationships brought back with it.
    2. Step 3 then unlinks each column the entry types, and each governed column of a removed domain, that ends off the type of the domain it links, as a type typed now would be. It reads the links the replay left, the entry's own among them, so a foreign key the entry links back to a domain of the type the sync gives it keeps that link, and a type the entry recorded unlinks the column where its domain has taken another type since, or where a sheet's undo has linked it again.
  - A replay that leaves every live column it touched at its domain's type sends the one batch it recorded, whatever a column it touched that is out of the document holds, as one in a table a peer removed since: the replay that brings that column or its table back settles it. One that settles reaches the store's subscribers, every peer and replica among them, as two batches at two versions (an owner decision of 2026-10-22), so a peer can hold a column off its domain's type between them. The settle's version is the later, so its type overrides the type the first batch wrote to the same column instead of meeting it in a tie.
  - A replay reads the state of the store it dispatches into (`HistoryOptions.getState`), so Time Travel's preview, which replays a clone of the history, works it out on the preview's document.
  - A paste over a column's type cell and Map Columns' alignment (`toAlignTypeActions`) take step 3 alone (`toDomainUnlinkActions`): a paste spreads no sync, and Map Columns spreads it over the relationships as the mapping leaves them, not the document's. A pasted domain, from a domain cell or the logical view's type cell, links with its domain's type and spreads no sync either.
  - A paste of new columns (`pasteEntitiesAction$`, and the columns `pasteTableAction$` adds to the selected tables) writes the type it copied and links its domain only while that domain is live and holds that type (`toPastedDomainId`). So a copy taken before its domain's type changed, or one from another copy of the file whose domain of the same id holds another type, lands unlinked.
- **A dictionary write goes row by row, then once over its domains.** `addDictionaryEntryAction$`, `updateDictionaryEntryAction$`, `commitDictionaryCellsAction$` and `importDictionaryAction$` send only the fields that change (a new row only its values that are not empty), then the column writes of every domain whose type they change, in one dispatch.
  - Each new row a commit, an add or an import brings without a key is keyed after the sheet's last row, in the order given (`placeNewRows`).
- **A sheet's order is its rows' keys** (owner decisions of 2026-10-21). Each word, term and domain carries `order`, a fractional index key (`@dineug/erd-editor-schema`'s `orderKey.ts`), written through its own register like any field (`DictionaryStoredFields`), and every reader shows a sheet sorted by it, a row of one key by id and a row with no key last (`compareByOrder`). So peers that hear the same writes in any order show the same order, which the doc lists, kept in the order rows were listed, do not.
  - `orderedDictionaryRows` sorts a sheet once per write of it and every cached index builds over that order: the Dictionary tab, its CSV export, the term completion, a domain found by name. `doc.<kind>Ids` is membership alone.
  - The key is the runtime value's alone: the storage form writes the rows in key order without it, and a parse keys the rows a file holds by their order (`settleOrderKeys`), so every peer that reads one file holds the same keys.
  - `insertDictionaryEntriesAction$` inserts empty rows before or after a row, at the end when the row is gone, in one dispatch; where no key fits between the neighbours (a row sharing the key below the place, or rows with no key before it) it keys those rows again in the same dispatch (`placeOrderKeys`, `orderKeys.ts`). `sortDictionaryAction$` keys every row again in the order of one field, by the text its cell shows (a term's domain by name) under the reader's language with numbers read as numbers, empty cells last and ties as they stood, and sends nothing for a sheet already in that order. Only the editor sends either, so both are exported by name and stay out of the barrel, as `setColumnLogicalNamesAction$` does.
  - `validateDictionaryValues` gives the reasons a write is refused: a name another listed row of the sheet or another row of the same write holds, or a term's domain the document does not list. A refused add or update sends nothing, and a commit with one refused row sends none of it (`toDictionaryCommit`). A row a peer removed meanwhile is passed over.
  - A term given a name while it holds no physical name gets the one its words compose.
  - An import folds the file's rows by name, the later row's values in the earlier one's place, then updates the listed row of each name and adds the rest. A term's domain is read by its name, `''` where none has it, and counted (`toDictionaryImport`). It compares after the composition, so the same file again sends nothing.
  - `removeDictionaryEntriesAction$` removes each listed row named once, in one dispatch.
- **A name written by hand leaves the dictionaries.** Each of the five paths that write a physical name into an existing table or column also sends its derived flag off in the same dispatch while the flag is on, and nothing for the flag while it is off, so one undo puts both back.
  - A table: `changeTableNameAction$` (`table/generator.actions.ts`), which the canvas header cell, a find and replace of a table name and `mcp-server`'s `erd_change_table_name` send.
  - A column: the name branch of `changeColumnValueAction$` (`table-column/generator.actions.ts`), which the name cell and `mcp-server`'s `erd_change_column_name` send, a find and replace of a column name (`toFieldAction`), and a paste over an existing column's name cell (`pasteTableAction$`).
  - A new table or column and a foreign key copy start with the flag off. A duplicate, a column drag, a paste of copied entities and an append carry the source's flag, and the columns `pasteTableAction$` adds to the selected tables take none unless the dictionaries derive the name the row leaves empty (`src/utils/AGENTS.md`, Duplicates and the clipboard).
- **`mcp-server` declares all eight.** Its dictionary tools send the three dictionary types through the generators above, and its logical name and domain tools the five field types. Its table and column rename, column type and relationship tools go through the same generators, so on a document with dictionaries they send a flag off, an unlink or a foreign key's link as the editor does. Its seed holds two words, a term, a domain the key of users links, and a derived table and column, so a scenario sends each type.
  - `peer.js` exports the dictionary barrel as `dictionaryActions$`, which those tools send, the atom barrel as `dictionaryActions`, which only the seed writes rows with (Peer store internals), and `validateDictionaryValues`, the reasons the tools refuse a write as the sheet refuses it.
- **The Dictionary tab's edits undo per sheet** (owner decisions of 2026-10-21, and one of 2026-10-22 that the canvas's undo never takes back a sheet's edit). A batch the tab sends carries `Tag.dictionarySheet` (`attachDictionarySheetTag$`), and the store puts its undo into the history of the sheet its dictionary rows are on (`sheetHistories`), never into the document's, so the canvas's undo never takes back a sheet's edit and a sheet's undo never takes back another sheet's or the canvas's. A domain's new type and the column types it carries are one batch, so one undo of the domain sheet takes back both.
  - `editor.dictionaryHistory` holds what each sheet's history can undo and redo, as `hasUndo` and `hasRedo` hold the document's, through `editor.changeHasHistory` with its `sheet`.
  - `undoSheet` and `redoSheet` refuse a read-only document and an active view as `undo` does, and `resetHistory` empties every sheet's history with the document's. Time Travel replays the document's history alone.
  - Every `editor.loadJson` or `editor.clear` without `keepDictionaries` that reaches the store empties every sheet's history, a local one, a peer's (`Tag.shared`) and the document history's undo or redo of one alike (`isDocumentReplace`, read on the store's own subscription): it replaces the rows the entries were made on, and an undo would bring an old row back into the new ones. A schema import's clear and load, their undo and their redo keep the rows, so they keep every sheet's history. A peer's replace leaves the document's history as it is.
  - A sheet entry holds its row actions and no column write (`pushSheetHistory`, `history.actions.ts`). The column writes a domain's type spread to are worked out again at each replay from the domain types the replayed rows set (`toDomainTypeActions`), so an undo or a redo types the columns the domain links then, and leaves a column the canvas linked elsewhere or typed by hand since.
  - The entry also keeps each link its own batch took off a column, a foreign key the sync carried off another domain, with the type the batch left the column at, and then each link its last replay took off, an undo's or a redo's, with the type that replay left. The next replay links that column again at that domain's type then while the column is still unlinked and still holds that type; one the canvas linked or typed since keeps its link or its type. A link to a removed domain comes back only where the column ends at that domain's type, since a type off it would unlink it.
  - A replay whose rows write the type of a removed domain, as the undo of a domain's type the document or a peer removed since does, also unlinks in the same batch each live column linking that domain that ends off that type (step 3), and keeps that link as it keeps the others, so the reverse replay links it again as above. Listing the domain again, by either history's undo of its removal, then finds no link off its type (A removed domain keeps its links).
  - A tagged batch with no dictionary row goes into the document's history.

### Peer store internals

The peer entry's Node and import rules and its key set spec: `src/peer/AGENTS.md`.

- **Eight `peer.js` keys serve specs alone**: `createEngineContext`, `ChangeActionTypes`, `StreamActionTypes`, `SharedFollowingActionTypes`, `SelectType`, `settingsActions$`, `dictionaryActions` (the dictionary atoms, which `mcp-server`'s seed writes its rows with by fixed ids) and `CanvasType` (a tab the snapshot and fingerprint specs move to).
  - `defaultToWidth` serves those specs and also sizes tables for `erd_list` (`mcp-server`'s `src/tools/outline.ts`).
  - Keep them in the entry. `mcp-server` holds each tool declaration to what the engine measurably does, so its specs need the real context, the real text measure, the real type lists and the real generator barrel. A `./peer/testing.js` subpath would make a fourth entry and split the chunks again.
  - `mcp-server`'s `src/peerSurface.test.ts` proves no key is dead.
  - `app`'s Drive, fingerprint, IndexedDB schema service and collaborative host specs import the entry too (`createPeerStore`, the table, column, table group and settings barrels, `CanvasType`, `LockSettingType`, and `SharedFollowingActionTypes`, which `documentController.test.ts` holds `NON_EDIT_ACTIONS` to), and so do `vuerd-vscode`'s `src/runtime-value.test.ts` and `obsidian-plugin`'s `src/__test-utils__/diagram.ts` (`createPeerStore` and the table and column barrels), so a change to the key set runs the `test` of `app`, `vuerd-vscode` and `obsidian-plugin` beside `mcp-server`'s.
- **Labelled undo units are the peer's bookkeeping**, not the engine's. The engine's history knows only entries.
  - `dispatch(actions, { label })` records one unit.
  - `group(label, run)` gathers the dispatches `run` makes into one unit under its own label. A group inside a group joins the outer one, and a group that dispatched nothing leaves none.
  - `undo`, `redo` and `setInitialValue` throw inside a group, since the unit would no longer match the history.
  - `undo` pops the newest unit that made an entry and names the labels it passed over.
  - `setInitialValue` forgets all of them.
- **`manualStreamFlush` closes a stream group on demand.** `createRxStore(context, { manualStreamFlush })` and `createSharedStore(store, config, { manualStreamFlush })` close a stream group (colors, memo resizes) on `flushStreamBuffers()`. That replaces `groupByStreamActions`' 200 ms quiet period. The flush goes through `flushOnNotifier` over a `Subject` the store owns.
  - Each store owns its tick count too. The rx-store has one, in its single history stage. The shared store has `FLUSH_TICKS = 2`: its compressor stands on each side of the circuit breaker, and its second stage arms too late for the first tick.
  - So `stream-flush.ts` flushes history first, then the outbound pipe, and knows neither the count nor an rxjs type.
  - Without the flag the rx-store's `flushStreamBuffers` is a no-op and the editor keeps its timing. A stream edit reaches peers after the two stages' 200 ms each, 400 ms.
  - The shared store's flush still works there (`quietPeriodOrNotifier`: the quiet period or the flush, whichever comes first). So a host can send a drag still held back before it lets the store go. `obsidian-plugin` does when a tab closes, so the other tabs of its file keep what it held.
  - The shared store takes the option as an internal third argument (`SharedStoreInternalOptions`). So neither `SharedStoreConfig` nor the config `getSharedStore` takes carries a stream option.
- **Deep-import the two stream operators.** `flushOnNotifier` and `createSharedStreamActionsCompressor` are deep-imported and stay out of the `rx-operators` barrel. `rx-operators/index.test.ts` pins the barrel's export set, as it keeps `readonlyIgnoreFilter` out.
- **`observable: false` keeps a Node store plain.** `createRxStore`'s internal `observable` option (default true), set to false, keeps the state a plain object.
  - r-html's reactive proxy reads `value instanceof Node`, a `ReferenceError` in plain Node. The replica store never hit it, because it already ran with observation off.
  - The peer passes false and first dispatches `changeViewportAction({ width: 0, height: 0 })`, so a load never reaches the pull's view lookup.
  - `RxStoreOptions` is not public surface.
- **A replicated sort sends `table.moveTo`, never `table.sort`.** `sortTable` places by each replica's own `toWidth`, so replaying it lands tables apart.
  - `sortTablesToMoveAction$` runs the reducer on copies of the live tables and groups. It sends the absolute points, and for each group with members its `tableGroup.resize`, in one undoable batch.
  - An import sends no `table.sort` either. `withGridPoints` (`editor/generator.actions.ts`) runs the reducer on a copy of the parsed document, its widths measured as the sender's store measures them, in the name view it shows, since a locked file holds the lock's.
  - `withGridPoints` writes each table's point and each group's rect into the `loadJson` value, which every peer loads as it is. The load reducer measures widths again with its own fonts.
  - `toLayoutPoints` sorts an append's grid on its copy the same way.
  - The reducer and its change type stay for an older editor that still sends one.
