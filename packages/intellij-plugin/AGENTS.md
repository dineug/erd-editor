# intellij-plugin

## Purpose

The Kotlin/JVM half of the JetBrains plugin: a `FileEditor` for `.erd`, `.vuerd`, `.erd.json` and `.vuerd.json` files, in any letter case, running a JCEF browser bridged to the IDE, and the document side of the hub coding agents join, in Kotlin. All editing logic is the bundle `intellij-webview` builds into `src/main/resources/assets`, served over a custom CEF scheme. The hub (`hub/`) ports `agent-hub`'s wire spec, `agent-hub-host`'s connection side, lock lifecycle, join window and document rules, and the Obsidian plugin's document registry and handlers, with no build edge to any of them: both packages' conformance corpora and a run of the built MCP server hold it to them. One IDE process runs one hub for every project open in it: one lock, `~/.erd-editor/ide/<pid>.json` with `ide` `intellij`, and one unix socket or named pipe. pnpm sees only a `private` package.json holding the `smoke` and `mcp-probe` scripts; `pnpm build` and `pnpm test` skip it.

## For AI Agents

### Working In This Directory

- **Gradle only, from this directory**: `./gradlew buildWebview` (the pnpm webview build), `buildPlugin` (zip in `build/distributions/`), `runIde`, `verifyPlugin` (the 252 floor and the latest release), `check` (the JVM tests, the Kotlin hub suite with the conformance run, and Kover). `buildPlugin` (so `verifyPlugin` too), `runIde` and `runIdeSmoke` never build the webview (`verifyWebviewAssets` only checks it exists), so run `buildWebview` first on a fresh tree or after a webview change. `buildWebview` is an `Exec` of `pnpm`, which Windows' `ProcessBuilder` cannot resolve to corepack's `pnpm.cmd`: on Windows run `pnpm exec vp run --filter @dineug/erd-editor-intellij-webview --fail-if-no-match build` from the repository root instead.
- **Publishing is manual**: bump `pluginVersion`, fill its `CHANGELOG.md` section, upload the zip.
- **Libraries come from the platform** (Jackson, kotlinx.coroutines, JNA, `org.cef.*`); adding one invites classloader conflicts. `apiVersion = KOTLIN_2_1` and no bundled stdlib keep to what the 2025.2 floor ships, and JDK 21 APIs only; use `intellijIdea(...)`, never `intellijIdeaCommunity(...)`.
- **No `@ApiStatus.Internal` or `@ApiStatus.Experimental` API**: `verifyPlugin` must say `Compatible` with no internal usage at both ends. Two calls went internal at 263 and were replaced: `UnixProcessManager.sendSignal`, so liveness binds libc's `kill` through JNA itself, and `PluginManagerCore.getPlugin`, so the lock's version comes from the plugin class loader's descriptor (`PluginAwareClassLoader`). `TrustedProjectsListener` is experimental, so trust is read per request; `AppMode` and `PlatformUtils` are internal and `ClientKind` experimental, so nothing detects a remote-development backend. The one deprecated usage, `ObjectMapper.setSerializationInclusion` in `WebviewScripts`, predates the hub.
- **Bridge `type` strings match `packages/webview-bridge` by hand.** A host command Jackson cannot map is dropped with only a WARN in `idea.log`; a `webview*` type the page does not register vanishes with no log at all. A new host command also needs its `@JsonSubTypes` entry.
- **Host → webview goes through `WebviewScripts.postMessageScript`**: JSON as a JS string literal, never a template literal, where a backtick in any name kills the script and `${…}` executes (`WebviewScriptsTest`).
- **Order across the bridge.** `onQuery` finds the editor whose browser sent the query (JCEF Gotchas), only offers the raw request to that editor's `WebviewBridge` channel and answers `callback.success("")`, since the router keeps an unanswered query pending in the browser and the renderer; one consumer per editor parses and handles the commands in the order CEF delivered them, which is the page's order as long as CEF calls `onQuery` serially per browser (smoke step A11 sends 1,000 and checks; should it ever fail, stamp each command with a per-page sequence number in `intellij-webview`'s `main.ts` and restore the order here). `WebviewPanel.dispatch` only enqueues on the page's script channel, whose one consumer encodes and runs each script in dispatch order, whichever thread dispatched it; one relayed batch is encoded once for every page (`WebviewScripts.scriptFor`). A save carries the whole document as one string, so `WebviewScripts.mapper` lifts Jackson's 20,000,000-character string limit.
- **Threading**: file writes inside `readAndEdtWriteAction { writeAction { … } }`, file dialogs on the EDT via `invokeLater`. **Disposable chain** `ErdEditor` → `WebviewPanel` → `Webview` → `JBCefBrowser`: register new resources into it and guard async callbacks with the `isDisposed` flags.
- **Saves**: every editor of a file autosaves its page's `SaveValue`, debounced 100 ms after the replica's own 200 ms, so a change reaches the file a fraction of a second after editing stops and the tab never shows modified. `ErdEditor.dispose()` flushes the pending value before cancelling its scope — reversed, the last edit is lost. `SaveReplication` of a file the hub's registry holds goes to the registry only (`onViewActions`), which injects it into the file's other ready pages and hands it to the joined peers; `WebviewPanel.dispatchBroadcast` over the provider's `docToEditorsMap` relays the rest: a file outside the local file system, and the editors the registry let go of (see Known Limitations).
- Pre-commit (`vp staged`) never sees Kotlin, and the root `.gitignore` has a bare `build`, so a Kotlin package named `build` would stay untracked.

- **Thread rules.** The registry thread never blocks: no `invokeAndWait`, no `Future.get`, no file or socket call, no read lock; a handler that needs the IDE suspends on io or the EDT instead. **`AgentHubService.dispose()` runs on the EDT inside a write action**, at IDE exit and at a dynamic unload, and waits on the hub through bounded `Future.get`s, so no hub thread may ever wait for a read lock: `host.folders()`, the listing and the trust read use the suspending, cancellable `readAction {}` on io (never `runReadAction`), and `close` cancels the running state task before it waits. The EDT waits on the hub only in `shutdownPeers` and `dispose`, both bounded, and a hub coroutine that needs the EDT (`openInEditor`, `writeNow`) suspends, so neither wait can deadlock. `Dispatchers.EDT` with no modality in the context runs at `NON_MODAL`, so the autosave and `writeNow` both wait out a modal dialog, in submission order; `openInEditor` and `writeNow` name `ModalityState.nonModal()` anyway, while the autosave (`readAndEdtWriteAction` in the editor's scope, no modality in its context) relies on that default, and the handler answers by its own bounds meanwhile (the open 5 s, the save's write 10 s). No JDK-global timer or pool (`completeOnTimeout`, `orTimeout`, `delayedExecutor`, an `*Async` without an executor): timers run on the registry executor, which `dispose` shuts down. Hub threads are daemons with the system class loader as context loader, so nothing they leave behind pins the plugin's.
- **Order**, as the TypeScript hub keeps it but for `join`. One connection's frames pass authorization in arrival order and start their handlers on the FIFO registry thread in that order, and a handler runs alone there until it first suspends; `applyActions` holds the frames behind it until it is answered, and the loop's own refusals are posted behind the handlers started before them. `join` of a path inside a lock folder reads trust on io before it registers the peer, where the TypeScript registries register at once, so a later frame of the same connection can be handled first: a `leave` then undoes nothing and the peer stays joined, and an `applyActions` can be refused `notJoined`. A document the lock lists alone reads no trust and registers in the handler's first step. The MCP server sends nothing for a path before its join is answered, so it never meets the difference; and a connection that hangs up while its join reads trust registers nothing, since the registry keeps (weakly) every connection the server let go of. A response is queued before any action it releases, since `afterResponse` runs next on the registry thread. A page receives its initial value before any batch that value does not hold: the one registry step that picks the value (the mirror once the document is quiet, else the page's disk read) sends it and marks the page ready without suspending, and the registry injects only into ready pages, over the same script channel. Lock writes run in change order on one `StateQueue`; `DocumentHub.scope` is replaced right before each write and read once per request, so a request sees the old scope or the new one, never a mix.
- **The lock and the pipe.** `~/.erd-editor/ide/<pid>.json`, written through `<pid>.json.tmp` and a rename (`0600`, directory `0700`): `ide` `intellij`; `version` the plugin's; `workspaceFolders` the local content roots then the base path of every open, non-default project, trusted or not, each realpathed; `documents` the open ERD files by real path. The pipe is `<pid>.sock` beside it, or `<tmp>/erd-editor-ide-<pid>.sock` when that path is over 100 bytes (none when both are, and the lock says `hub: false`), or `\\.\pipe\erd-editor-ide-<pid>` on Windows. Home and temp are Node's `os.homedir()` and `os.tmpdir()` (on POSIX `HOME` whenever set, even empty; `USERPROFILE` on Windows), since the MCP server looks there. The JDK refuses to bind over an existing socket file and leaves its own on close, where Node's server unlinks it, so `DocumentHub`, the one owner of the path, deletes it before it listens and after it stops, through `removeFileSync`, which leaves a directory alone. A listen that fails, JNA natives that do not load (`LinkageError`) included, still writes a `hub: false` lock: a lock always guards the paths. Folder changes (a project opening or closing, `rootsChanged` storms such as a Gradle sync) coalesce: 200 ms after a burst pauses, 1 s after it began at most. At startup it sweeps the lock, temp file and sockets of every dead pid whose lock reads, whatever its `ide`; a live pid's lock stays, even a malformed one.
- **Liveness.** A pid outside `1..Int.MAX_VALUE` is dead without asking. POSIX: libc's `kill(pid, 0)` through JNA as a `Function` (`NativeLibrary.getInstance(Platform.C_LIBRARY_NAME).getFunction("kill")`), never a `Library` interface of the plugin's own, which `Native.load` would keep in JNA's static option maps (Known Limitations); Node's own rule, so any refusal, `EPERM` too, is dead; a throwable from the binding other than `IllegalArgumentException` switches this JVM to `ProcessHandle.of(pid).isAlive`, logged once, so a broken JNA never makes the sweep delete live locks. Windows: `ProcessHandle` always.
- **Real paths.** POSIX: `toRealPath()` plus a missing tail as given, never Unicode-normalized; `ENOTDIR` is normalized to Node's, since JBR 21 reports it and JBR 25 a missing entry. Windows: `WindowsRealPath`, `CreateFile` then `GetFinalPathNameByHandleW` (`VOLUME_NAME_DOS`) as libuv, because the JDK's `toRealPath` keeps a `subst` or mapped drive letter that the MCP server's realpath resolves. When it answers no real path, `toRealPath` answers, as both Node sides go on to the JS realpath for a volume that gives no final path, where a `subst` letter stays there as here. A path of 260 characters or more differs: Node namespaces it (`\\?\`) and resolves it natively, while here no prefix is added and it goes to `toRealPath` (Known Limitations). What `WindowsRealPath` found missing stays missing when the JDK refuses the path (a `?` in a name, an entry under a file), as the JS realpath's `lstat` finds it.
- **Where no hub runs.** `AgentHubService` starts with the first project (`AgentHubStartupActivity`, `DumbAware`) or the first ERD editor (`ErdEditorProvider`), whichever comes first; the listeners use `getInstanceIfCreated` and start nothing. It builds the registry always, and the hub unless one of these holds, checked in this order: JCEF unsupported (`JBCefApp.isSupported()` false, or a `LinkageError`, JCEF being an optional module from 2026.2: no ERD editor can exist), a headless IDE, unit-test mode, a Flatpak on Linux (`FLATPAK_ID` or `/.flatpak-info`: its pids name no process outside the sandbox). Then there is no lock, no socket and no sweep, and the settings page names the reason. A hub that fails to build leaves a registry-only runtime and the reason `the document hub could not start (idea.log has the error)`. A remote-development backend counts only through JCEF (see Known Limitations).
- **Trust, per request.** One lock covers every project, trusted or not, so the handlers read trust when a request comes: `IdeFacade.trustedProjects()` reads the open projects on io, their folders realpathed and `TrustedProjects.isProjectTrusted` once each (a throw counts untrusted). A path is untrusted-only when it lies inside an untrusted project's folder and no trusted one's, or inside a lock folder but no open project's, which fails closed while a project opens or closes. `openDocument`, `applyActions` and `save` refuse it with `hubDisabled` (`DocumentRules.untrustedProject`); `join` answers it from disk, unregistered but tracked; `listDocuments` marks it `readonly`. `openDocument`, `applyActions`, `save` and `join` read no trust for a path outside every lock folder (a document the lock lists alone) and never count it untrusted-only, while `listDocuments` reads trust for the whole listing and marks such a path `readonly` when it lies in an untrusted open project and in no trusted one. The two differ only while the folders of a project that just opened are not in the lock yet (folder changes coalesce for up to 1 s): a diagram of an untrusted project open in an editor then lists `readonly` and can still be written.
- **Documents and editors.** The registry holds every local ERD file open in an ERD editor, whether or not a hub runs. `ErdEditor` declares the service, registry and timings before its first `init`, and posts `register` and `addView` before it builds its `WebviewPanel`, whose page starts loading at once, so the page's first command always reaches the registry after them. Its hooks: `Initial` sends the theme and the read-only flag, reads the file through the VFS (no BOM), holds 1 s at most until the lock lists the file (`awaitListed`), then posts `onViewReady`, where the registry picks and sends the value (an editor the registry does not hold sends the file's text itself); `SaveValue` → `onValueSaved` (the mirror); `SaveReplication` → `onViewActions`; a write → `onWritten`; the page starting a load (a reload, the timeout page) → `onViewUnready`; JCEF focus → `setActive`, so `listDocuments`' `active` follows focus and an agent's open never changes it; `dispose` flushes, then `removeView`. `openInEditor` takes the file registered on the path if any (one opened through a symlink stays one tab), in the project already showing it, else the one whose folder holds it deepest, else the last focused, and opens it with `FileEditorManager.openFile(vf, false)`, which takes no focus. `listDocuments` lists the open documents, writable first, then every ERD file of the open projects' content (`ProjectFileIndex.iterateContent`, `node_modules` pruned, the name checked before a path is built), each once by real path. A local file or folder renamed or moved (`PROP_NAME`, `VFileMoveEvent`) makes the registry read every document's path again: its peers hear `documentClosed` under the old path, and it is served under the new one, or let go once no longer an ERD file. A writability flip (`PROP_WRITABLE`) pushes `readonly` to every page, closes the document for its peers and wakes open waits. A deleted file goes with its editors' disposal.
- **The hub's save** waits 2 s at most for the replicas to hold every edit, then writes the mirror through the first editor opened (`writeNow`), reading it inside the EDT write action, so no older bytes land over an autosave made meanwhile. It answers `saved: false`, logged, when the replicas do not settle in those 2 s or the write does not land within 10 s or fails, and without a log when the file is no longer valid or writable or no editor is left to write it. `dirty` is the mirror differing from what an editor last wrote, or a replica save still owed.
- **Project close, as revoke.** After every folders or documents lock write the registry revokes: each tracked (connection, path) the new lock no longer admits hears `documentClosed` and is dropped; a connection then tracking nothing, whose paths closed since it last tracked one all lie outside the new lock, is ended, so the MCP server falls back to the file. A path tracked after a revoke (a join authorized against the old scope) is checked against that revoke's scope and closed the same way.
- **Shutdown order.**
  1. IDE exit: `AgentHubAppListener.appWillBeClosed`, which runs before the projects close, calls `shutdownPeers()`: the hub lets go of the host's events, so the project closes that follow rewrite no lock; the registry's `shutdown()` (through `callBlocking`, 500 ms) sends `documentClosed` for every path each peer joined or read, ends open waits and registers nothing more; then 1 s at most for those frames to drain; then `retire()`, queued on the `StateQueue` without waiting: the lock turns `hub: false` and `pipe` `""`, keeping its folders and documents, then the pipe closes, ending every connection, and no later settings change serves again. So agents are refused writes (`blocked`) to the editors still open while the IDE exits, which can take seconds (the smoke measured about 8 s to dispose; 2025.2 first waits for indexing to end); dispose deletes the lock. Idempotent.
  2. `AgentHubService.dispose()`, at exit or unload, calls `runtime.dispose()`: removes the shutdown hook (an `IllegalStateException` means the JVM is exiting already), `shutdownPeers()` again (the first time, at an unload), `hub.close(1 s)` (skips what is queued, cancels the running state task, waits for it; in time the lock goes, late `releaseSync` deletes it and logs `could not close the document hub`; then the listener stops, destroying every connection, and the socket file goes), then `threads.shutdown(500 ms)`. Nothing survives it: no `erd-editor-hub-*` thread, no hook, no bus connection outside the service's `Disposable`.
  3. A JVM going down without dispose (SIGTERM): the hook runs `releaseSync()` alone, deleting the lock, its temp file and both socket paths.
  4. Coding agents turned off: the `hub: false` lock is written first, then the listener stops; peers hear no `documentClosed`, so agents are refused (`blocked`) rather than sent to the file.
- **Settings.** `AgentHubSettings` is its own `PersistentStateComponent` beside the theme's in `erd-editor.xml` (`codingAgents`, default on); its setter publishes `Listener.TOPIC` only on a change and `loadState` publishes nothing, so the host reads the flag fresh in `isEnabled()` and takes the topic as a hint. `ErdEditorAppSettings` keeps the theme, default `auto`, which it resolves by `!JBColor.isBright()` before any page sees it (`shownTheme`); `updateTheme` publishes only a change, a stored value missing or unknown reads as the default, and a pick from a page's theme builder keeps `auto` when it equals what auto shows (`ErdEditorTheme`, the Obsidian plugin's rules). Open editors re-send the theme on `LafManagerListener` while the setting is auto. The old default was `dark`, a class default the serializer never wrote, so a user who never picked a theme now gets `auto`. `ErdEditorConfigurable` (Tools, `ERD Editor`) edits the theme's three fields and the Coding agents box, whose comment adds `Coding agents are unavailable: <reason>` from `AgentHubService.whyUnavailable()`, which finds the reason without starting the service.
- **Changing the hub.** A change to `agent-hub` or `agent-hub-host` (a message, the lock, a refusal text, a join rule, a corpus vector) is ported here and `./gradlew check` run; the Gradle tests read both corpora, so a vector change fails here until it is ported. A refusal every host meets is a constructor in `agent-hub-host`'s `documentRules.ts`, pinned in its corpus, and its twin in `DocumentRules.kt`; one only the IDE meets stays in `DocumentRules.kt`, pinned literally by `DocumentRulesTest`. A new class under `hub/` comes with tests that cover it (Testing Requirements) and imports nothing but what `HubImportsTest` allows. Check a change here with `ERD_MCP_CONFORMANCE=required ./gradlew check`, the MCP server built; one that touches `hub/win/` or `hub/transport/` also needs CI's `test-windows` job and the Windows verification below.

### Known Limitations

- **A remote-development backend** cannot be detected with public API (a `remoteDevHost` start is not headless), so it counts only through JCEF: no hub where no ERD editor can run, and where JCEF works on a backend, the hub serves the agents of that machine.
- **One frame can exhaust the IDE's heap**: a process of the same user that reaches the `0700` socket can send one frame under 64 MiB that Jackson's tree inflates past it (`[{},…]` with 22.4 million items ran `-Xmx2048m` out of memory). The VS Code hub loses only its extension host; here the IDE is hit. Kept for parity with the other hubs: no hello deadline, no connection cap.
- **Named pipes use the default security descriptor** (null `SECURITY_ATTRIBUTES`, as libuv): another local user can open read-only instances and hold a channel and an io thread each, with no token or data exposed, since a peer must write its hello.
- **A change made outside the IDE is not reloaded**: an editor reads its file once per page load, so an outside change to an open diagram goes unseen and the next autosave overwrites it. The lock keeps agents from writing such a file while a hub runs or is turned off; where none runs (a Flatpak, no JCEF), close the diagram before an agent edits the file.
- **A diagram renamed to another extension and back while its editors stay open** is served by those editors unregistered: they relay among themselves, and a new editor of the file joins them, so until they all close the lock does not list it and an agent's `openDocument` times out (`No ERD editor on … reported ready within 5000 ms`). Closing and reopening the file ends it.
- **A second editor of a file, or a page that reloads, can miss the latest edits**: `onViewReady` waits at most 500 ms for every replica to save what reached it, then seeds the page from the mirror, so a batch the other pages took before that, which no replica save has brought into the mirror yet, never reaches the page, whose own saves then lack it. It is the trade-off the TypeScript join makes at the same cap, where a peer can miss such a batch too.
- **A path of 260 characters or more on a `subst` or mapped drive** keeps its drive letter in the lock (the JDK fallback of Real Paths), where the MCP server resolves it to the target, so the agent finds no lock covering such a file and edits it on disk, under an editor that may hold it.
- **A dynamic unload may keep the plugin's class loader**: the scheme handler factory registered on the global `CefApp` is never removed, since only a global clear exists, and on Windows `Kernel32Ex`, a `Library` interface of the plugin's own that `Native.load` binds, stays in JNA's static option maps with its class loader. Liveness calls `kill` as a JNA `Function`, which registers nothing, so macOS and Linux keep only the scheme handler's. The smoke's step B7 reports the loader's verdict apart from the hub's.

### JCEF Gotchas

- `plugin.xml` depends on `com.intellij.modules.jcef` optionally (`jcef.xml`): mandatory stops loading on 2025.2/2025.3, absent kills the editor on 2026.2+ with `NoClassDefFoundError: JBCefApp`. The Verifier says `Compatible` either way; only a real install shows it. For the same reason `AgentHubService` reads `JBCefApp.isSupported()` inside a `LinkageError` catch, at construction, never at class init.
- `SchemeHandlerFactory` extends `CefResourceHandlerAdapter`, never `CefResourceHandler` directly: the interface's abstract methods grew in 2026.2's JCEF, and a direct implementation compiled against the floor is binary-incompatible there.
- `WebviewPanel` init order is load-bearing: `JBCefApp.getInstance()` → register the scheme handler once per app → build `Webview` and `loadURL`. Registering after `loadURL` gives `DNS_PROBE_FINISHED_NXDOMAIN`; raw `CefApp.getInstance()` first gives "JCEF is not supported in this env". Never call the global `CefApp.clearSchemeHandlerFactories()`. `onPageLoadStart` and `onFocus` are `@Volatile` and declared before the `webview` property, since constructing `Webview` starts the load and CEF calls them on its own threads.
- Under out-of-process JCEF at 2025.2 the `CefMessageRouter` registered first hears the queries of every browser, whatever client each router was added to, and the first handler to claim a query wins: with two ERD tabs, the second page's `Initial` reached the first tab's bridge and the second editor stayed blank. So every panel joins the static `livePanels` in `initPanel` (and leaves it in `beforeTreeDispose` and `dispose`), and each `onQuery` hands the query to the live panel whose browser sent it, matched by `CefBrowser.identifier`, since another handle on the same browser can arrive (`isSameBrowser`, `WebviewPanelBrowserTest`); a query of no live panel's browser is left to the other routers. 2026.1, where each router hears only its own client, takes the same path.
- `Webview`'s `onLoadStart` fires for the main frame on every load, the timeout page included (after `html.editor.timeout`, 10 s), so the registry takes the page to hold nothing until its next `Initial`.
- JCEF's DevTools port (`ide.browser.jcef.debug.port`, which the smoke sets) opens only once the first browser exists.
- macOS `⌥`+letter reaches the webview as a wrong `KeyboardEvent.code` (`KeyA`) and fires another shortcut; bind nothing to `Alt`+letter. The IDE keymap takes `⌘Z` / `⌘⇧Z` first.

### Platform And JDK Gotchas

- `appWillBeClosed` runs before the projects close, and the exit is not cancelled after it; the dispose that follows holds the write lock (Thread Rules) and may come seconds later, hence the retire (Shutdown Order).
- JVM hooks through `Runtime.addShutdownHook`, never `ShutDownTracker`, and `dispose` removes the hook: one left behind pins the class loader.
- A project disposed during a read action throws `ProcessCanceledException` from its services (`whileOpen` skips such a project); `Logger` refuses to log a `ProcessCanceledException`, so `IdeHubLog` names a control-flow or cancellation detail instead of attaching it.
- A `PersistentStateComponent` writes no value equal to its default (the theme's migration, Settings), and `loadState` publishes nothing.
- The JDK's unix domain sockets refuse to bind over an existing file, leave the file on close and throw on a path longer than `sun_path`, where Node truncates; `LockPaths.pipePathFits` keeps such a path from being handed out.
- JNA's `Kernel32` (5.17) lacks `GetFinalPathNameByHandle`, `GetOverlappedResult` and `CancelIoEx` and declares the overlapped calls over `byte[]`, hence `Kernel32Ex`. Every pipe handle is overlapped, since a synchronous one serializes I/O and a blocked read would hold every notification back. Nothing calls `DisconnectNamedPipe`, which discards what the peer has not read; closing the handle keeps it readable, then EOF. On a pipe `destroy` and `close` block up to 1 s and `shutdownOutput` up to 2 s while cancelled I/O completes, so io threads call them, never the registry thread.
- The IntelliJ Platform Gradle Plugin passes the product's JVM arguments, `jna.boot.library.path` among them, to `test`, so JNA natives load in plain JUnit (`MachineEnvironmentTest` asks `isAlive` of its own pid). Tests run on the platform's JBR (25 for 2026.1.4) with the coroutines debug agent, so thread names carry ` @coroutine#n`. After `HubThreads.shutdown` a coroutine's `finally` may never run and a later resumption runs off the hub's threads, so cleanup belongs in `close` and `dispose`, before it.
- Jackson at the 252 floor is 2.19.0, whose `StreamReadConstraints` both `WebviewScripts.mapper` and `HubJson` raise.

Every class added under `hub/` is covered by its own tests.

Three skip conditions only: the Windows-only suites (`NamedPipeTransportTest`, `WindowsRealPathTest`) off Windows, the unix-socket and POSIX-mode cases on Windows, and the conformance run without node or the MCP build. Without node or the build it skips, and with `ERD_MCP_CONFORMANCE=required` (CI) it fails instead. Build the server first: `pnpm exec vp run --filter @dineug/erd-editor-mcp --fail-if-no-match build`.

### Windows Verification (named-pipe hub)

The named-pipe hub, the Windows realpath and the conformance run over a pipe execute only on Windows. CI's `test-windows` job runs their JUnit suites; this is the check of the live IDE, done by a person, or by a Claude session opened on the branch to verify together with the person at the machine. Nothing here deletes a lock file of another process, and nothing stops a process except the one a lock names (`Stop-Process -Id <pid>`, never `taskkill /IM`).

Who does what: a Claude session runs steps 1–7, 9, 10, the commands of 11–13 and step 14 itself, and reads every file and output; the GUI actions of steps 8 and 11–13, and whatever in step 1 needs an administrator or the Settings app, need the person, so it asks for each one, then checks the result itself. The commands are PowerShell, run from the repository root unless a step names `packages\intellij-plugin`; a session whose shell is Git Bash runs each through `powershell -NoProfile -Command`, adapting the quotes.

Setup

1. Windows 10 1809 or later, or 11. Git, then `git config --global core.longpaths true`. Node 22.12 or later (`node -v`). A JDK 21 on `PATH` or in `JAVA_HOME`, which the Gradle wrapper needs to start: for example `winget install EclipseAdoptium.Temurin.21.JDK`, then a new shell, where `java -version` says 21 (a running Claude session does not see the new `PATH`: restart it, or set `$env:JAVA_HOME` to the JDK's folder in each command). The symlink privilege, which `AuthzTest` and `MachineEnvironmentTest` need: turn on Developer Mode (Settings, System, For developers), or run the shell as administrator; without it they fail with "A required privilege is not held by the client".
2. `corepack enable` (from an elevated shell when Node is under Program Files); pnpm then comes from `packageManager`.
3. In a fresh clone or worktree checked out at the branch or commit to verify: `pnpm install --frozen-lockfile`.
4. Both builds, with pnpm, since `gradlew buildWebview` cannot start `pnpm.cmd` on Windows:
   `pnpm exec vp run --filter @dineug/erd-editor-mcp --fail-if-no-match build`
   `pnpm exec vp run --filter @dineug/erd-editor-intellij-webview --fail-if-no-match build`

Unit and conformance tests, in `packages\intellij-plugin`

5. `$env:ERD_MCP_CONFORMANCE='required'; .\gradlew.bat test --tests '*NamedPipe*' --tests '*WindowsRealPath*' --tests '*McpConformance*' --tests '*ConnectionServerSocket*' --tests '*JoinOverSocket*'`
   The first Gradle run downloads the IDE, over a gigabyte, and can take longer than ten minutes: a session runs it in the background and waits. Pass: `BUILD SUCCESSFUL`, and `build\test-results\test\TEST-*NamedPipeTransportTest.xml`, `TEST-*WindowsRealPathTest.xml` and `TEST-*McpConformanceTest.xml` each hold a `<testsuite` whose `tests` is 1 or more with `skipped="0" failures="0" errors="0"`, as CI's `test-windows` job demands; `Select-String -Path build\test-results\test\TEST-*.xml -Pattern '<testsuite [^>]*>'` prints them.
6. `.\gradlew.bat test`, the whole suite, `ERD_MCP_CONFORMANCE` still set. `test`, not `check`: the Kover gate is measured on macOS and Linux and is skipped here. Only `UnixSocketTransportTest` and the POSIX-mode cases of `LockFileTest` and `MachineEnvironmentTest` may skip.
7. `mkdir $env:TEMP\erd-probe`, `New-Item -ItemType File $env:TEMP\erd-probe\a.erd.json`, then `subst X: $env:TEMP`, with a free drive letter in place of X throughout.
   `node -e "console.log(require('fs').realpathSync.native(process.argv[1]))" X:\erd-probe` prints the folder under the TEMP path, not under X:. Keep the drive until step 13.

Live IDE

8. `.\gradlew.bat runIde` in `packages\intellij-plugin` (a session starts it in the background; it runs until step 13). A fresh sandbox may first ask about importing settings (do not import) or about a licence or trial (continue without one where offered); note any other dialog for the report. The person, in the sandbox IDE: File | Open `X:\erd-probe`, through the subst drive on purpose; asked whether to trust it, choose Trust Project, leaving unticked any option that trusts every project in its parent folder (step 12 needs a sibling that stays untrusted).     `node packages/intellij-plugin/e2e/mcp-probe.mjs X:\erd-probe a.erd.json`
    `node packages/intellij-plugin/e2e/mcp-probe.mjs $env:TEMP\erd-probe a.erd.json`
    Each prints only `ok` lines and a `PASS` line and exits 0: every call live, one table added, `erd_save` saved. The person sees each table appear on the canvas, and the file on disk holds both within about a second.
11. The person: File | Settings | Tools | ERD Editor, untick Coding agents, Apply. The lock shows `"hub": false` and `"pipe": ""`. `node packages/intellij-plugin/e2e/mcp-probe.mjs X:\erd-probe a.erd.json --expect-blocked` exits 0: every write refused with code `blocked`, naming "a JetBrains IDE (pid N) whose ERD Editor hub is turned off or failed to start".
