# intellij-plugin

## Purpose

The Kotlin/JVM half of the JetBrains plugin: a `FileEditor` for `.erd`, `.vuerd`, `.erd.json` and `.vuerd.json` files in any letter case, running a JCEF browser bridged to the IDE. All editing logic is the bundle `intellij-webview` builds into `src/main/resources/assets`, served from the classpath by a CEF scheme handler for `https://erd-editor-jetbrains-plugin`. `hub/`, the coding-agent hub's document side in Kotlin, ports `agent-hub`'s wire spec, `agent-hub-host`'s connection side, lock lifecycle, join window and document rules, and the Obsidian plugin's document registry and handlers; root § Package Map says what holds it to them. One IDE process runs one hub for all its projects: one lock, `~/.erd-editor/ide/<pid>.json`, and one unix socket or named pipe.

## Making a Change

1. Read the AGENTS.md of each sibling the change crosses: `webview-bridge` and `intellij-webview` for a bridge command, `agent-hub` and `agent-hub-host` for a hub rule, `mcp-server` for what an agent sees.
2. Use Gradle from this directory in place of root steps 3 and 4, since `pnpm test` and `vp staged` never reach the Kotlin. Root step 5's `pnpm check` still lints `e2e/*.mjs`.
3. Build the inputs: `pnpm exec vp run --filter @dineug/erd-editor-mcp --fail-if-no-match build`, and `./gradlew buildWebview` on a fresh tree or after a webview change.
4. Run `ERD_MCP_CONFORMANCE=required ./gradlew check` (JUnit, the conformance run, Kover); the variable turns the conformance run's skips into failures.
5. Run `./gradlew verifyPlugin` (the 252 floor and the latest release) after a change to the platform API used, `plugin.xml` or `gradle.properties`; CI's `verify` runs only on `main` and dispatch.
6. Run the checks JUnit cannot make that the change reaches (Testing Requirements): `runIde` by eye, the smoke, Windows Verification and CI's `test-windows` for `hub/win/` or `hub/transport/`. Report any left out with its need (root step 7): macOS for the smoke, a Windows machine and a person for Windows Verification.
7. Update `README.md` between its `Plugin description` markers for a user-visible change (root § Common Patterns).

## Rules

### Build And Gradle

- **Run `buildWebview` before packaging or running.** It is the pnpm webview build, which `buildPlugin`, `verifyPlugin`, `runIde` and `runIdeSmoke` never run; `verifyWebviewAssets` only checks it exists. On Windows run it from the root as Windows Verification step 3 does, since `ProcessBuilder` cannot resolve the task's `pnpm` to corepack's `pnpm.cmd`.
- **Suspect the build cache on `NoSuchMethodError`.** `org.gradle.caching` once restored test classes calling `HubTimings`' old constructor after a pull. Run the task with `--info`, delete only the entry of the key it loaded under `~/.gradle/caches/build-cache-1`, and rerun.
- **Publish only when a release is prepared.** The release procedure then bumps `pluginVersion`, fills its `CHANGELOG.md` section and uploads `buildPlugin`'s zip from `build/distributions/` by hand. A change outside it leaves both as `main` has them (root § Working In This Directory, What a change carries).
- **Take libraries from the platform.** Jackson, kotlinx.coroutines, JNA and `org.cef.*` ship with it, and another library invites classloader conflicts. `apiVersion = KOTLIN_2_1`, no bundled stdlib and JDK 21 APIs keep to the 2025.2 floor. Use `intellijIdea(...)`, never `intellijIdeaCommunity(...)`.
- **Call no internal or experimental API.** `verifyPlugin` must say `Compatible` with no internal usage at both ends. `UnixProcessManager.sendSignal` and `PluginManagerCore.getPlugin` went internal at 263, hence JNA's `kill` and the version from `PluginAwareClassLoader`'s descriptor; experimental `TrustedProjectsListener` is why trust is read per request; internal `AppMode` and `PlatformUtils` and experimental `ClientKind` leave remote development undetected. The one deprecated call, `ObjectMapper.setSerializationInclusion` in `WebviewScripts`, predates the hub.
- **Name no Kotlin package `build`.** The root `.gitignore`'s bare `build` would leave it untracked.

### Webview Bridge And Saves

- **Match bridge `type` strings to `webview-bridge` by hand.** A host command Jackson cannot map is dropped with a WARN in `idea.log`, an unregistered `webview*` type unlogged. A new host command needs its `@JsonSubTypes` entry.
- **Mirror optional bridge fields as nullable.** Payload classes mirror each optional `webview-bridge` field as nullable with a `null` default (`mode`, `runtimeValue`, `systemAppearance`, `systemLocale`). `WebviewScripts.mapper` ignores unknown properties and writes no null, so a field the bridge adds is dropped with no log until its payload class names it, and a page reads a field left null as absent.
- **Post through `WebviewScripts.postMessageScript`.** It embeds JSON as a JS string literal; in a template literal a backtick kills the script and `${…}` executes (`WebviewScriptsTest`). `mapper` and `HubJson` raise the `StreamReadConstraints` of the 252 floor's Jackson 2.19.0; `mapper` lifts its 20,000,000-character string limit, a save being one string.
- **Keep the page's command order.** `onQuery` offers the request to the sender's `WebviewBridge` channel and answers `callback.success("")`, since the router keeps an unanswered query pending. One consumer per editor handles commands in CEF's order, the page's while CEF calls `onQuery` serially per browser (smoke A11); if that breaks, number commands in `intellij-webview`'s `main.ts` and reorder here. Scripts run in dispatch order on one channel per page; a relayed batch is encoded once (`WebviewScripts.scriptFor`).
- **Write files in an EDT write action.** Autosave and exports: `readAndEdtWriteAction { writeAction { … } }`; `writeNow`: `edtWriteAction` at `ModalityState.nonModal()`; `dispose`'s flush: `invokeAndWait { runWriteAction { … } }`; dialogs: `invokeLater`.
- **Register resources in the disposable chain.** The chain is `ErdEditor` → `WebviewPanel` → `Webview` → `JBCefBrowser`; guard async callbacks with `isDisposed`.
- **Autosave without dirtying the tab.** `SaveValue` is debounced 100 ms after the replica's 200 ms. One with `changed` false (`HostSaveValueCommandPayload`; true when absent), a scroll or zoom, writes nothing and gives `onValueSaved` `null`, which the quiet wait counts, so a file an older release or a hand edit wrote keeps its bytes.
- **Write `value`; keep `runtimeValue` in memory.** Writes, `savePayload`, the mirror, `lastWritten` and the dirty flag hold the storage form `value` only. The page's `runtimeValue` (none from older bundles) seeds new pages and joins ahead of the mirror (`DocumentEntry.seed`), and `OpenEditors` keeps each file's last one for unregistered pages.
- **Flush, then cancel the scope.** `ErdEditor.dispose()` in the other order loses the last edit.
- **Relay replication through the registry.** It injects `SaveReplication` of its files (`onViewActions`) into their other ready pages and joined peers; `WebviewPanel.dispatchBroadcast` over `OpenEditors` relays non-local files and editors the registry let go of.

### Coding-Agent Hub

- **Changing the hub.** Port a change to `agent-hub` or `agent-hub-host` (a message, the lock, a refusal text, a join rule, a corpus vector) here; the Gradle tests read both corpora and fail until it is ported. A refusal every host meets is a constructor in `agent-hub-host`'s `documentRules.ts`, pinned in its corpus, twinned in `DocumentRules.kt`; an IDE-only one lives in `DocumentRules.kt`, pinned literally by `DocumentRulesTest`. A new class under `hub/` comes with tests covering it.
- **Bump the smoke's protocol copies too.** A bump of `HUB_PROTOCOL_VERSION` edits `e2e/peer.mjs`'s `PROTOCOL_VERSION` and smoke step A1's check of the lock's `protocolVersion`, hand-written copies no CI job runs.
- **Keep the core free of IntelliJ API.** `HubImportsTest` lets `hub/**/*.kt` import only `java.`, `kotlin.`, `kotlinx.coroutines.`, `com.fasterxml.jackson.`, `com.sun.jna.` and the hub, refusing a platform name (`com.intellij.`, `org.cef.`, and the rest it lists) anywhere in code, so the core runs in plain JUnit, the conformance run and its own threads.
- **Log only through `HubLog`.** `IdeHubLog` warns `[erd-editor hub] …` under `#com.github.dineug.erdeditorintellijplugin.hub`, never `Logger.error`, which throws outside an Application and raises the plugin error report. Rethrow a `CancellationException` unlogged (`rethrowIfCancellation`).
- **One registry thread owns hub state.** `erd-editor-hub-registry` runs it, every handler in frame order and every timer; blocking work (I/O, the `StateQueue`, realpaths, each handler's `withContext(io)` step) goes to the cached `erd-editor-hub-io-<n>` pool (`HubThreads.kt`), and `erd-editor-hub-release` runs only the JVM hook's `releaseSync()`.
- **Never block the registry thread.** No `invokeAndWait`, `Future.get`, file or socket call or read lock: a handler needing the IDE suspends on io or the EDT.
- **Hub threads never wait for a read lock.** `AgentHubService.dispose()` waits on the hub (bounded `Future.get`s) on the EDT in a write action, at exit and unload. So `host.folders()`, the listing and trust use the cancellable `readAction {}` on io, never `runReadAction`, and `close` cancels the state task before waiting.
- **Bound the EDT's waits on the hub.** It waits only in `shutdownPeers` and `dispose`, both bounded, while hub coroutines needing the EDT (`openInEditor`, `writeNow`) suspend, so neither wait can deadlock. The autosave and `writeNow` wait out a modal dialog at `NON_MODAL`, in submission order, and the handler answers by its own bounds (open 5 s, the save's write 10 s).
- **Use no JDK-global timer or pool.** No `completeOnTimeout`, `orTimeout`, `delayedExecutor` or executor-less `*Async`: timers run on the registry executor, which `dispose` shuts down. Wait through `HubThreads.pause`, never `delay` on `threads.io` (kotlinx's global `DefaultExecutor`) or `Thread.sleep`, which `close` cannot cut short. Hub threads are daemons with the system class loader as context loader, so nothing pins the plugin's.
- **Keep the TypeScript hub's order, but for `join`.** A connection's frames pass authorization in arrival order and start handlers on the FIFO registry thread, each alone until it suspends; `applyActions` holds later frames until answered, and the loop's own refusals queue behind earlier handlers. A response queues before the actions it releases (`afterResponse` runs next).
- **`join` can be overtaken.** Inside a lock folder it reads trust on io before registering, where TypeScript registers at once, so a later `leave` undoes nothing and an `applyActions` may be refused `notJoined`; the MCP server waits for each join's answer. A connection gone mid-join registers nothing, since the registry keeps dropped ones weakly.
- **A page's initial value precedes any batch.** One registry step picks it (runtime value or mirror once quiet, else the disk read), sends it and marks the page ready without suspending, and only ready pages get batches, on the same channel.
- **Lock writes run in change order** on one `StateQueue`; each request reads `DocumentHub.scope` once, so it never sees a mix.

### Hub Lock, Pipe And Paths

- **The lock.** `~/.erd-editor/ide/<pid>.json`, via `<pid>.json.tmp` and a rename (`0600`, folder `0700`): `ide` `intellij`, the plugin's `version`, `workspaceFolders` (local content roots, then each open non-default project's base path, trusted or not, realpathed), `documents` (open ERD files by real path). Home and temp are Node's (`MachineEnvironment.kt`), where the MCP server looks.
- **The pipe.** `<pid>.sock` beside the lock, else `<tmp>/erd-editor-ide-<pid>.sock` past 100 bytes (past both: none, and `hub: false`); `\\.\pipe\erd-editor-ide-<pid>` on Windows. `DocumentHub` alone deletes the socket file before listening and after stopping, since the JDK neither binds over it nor unlinks it as Node does.
- **A lock always guards the paths.** A failed listen, unloadable JNA natives (`LinkageError`) included, writes `hub: false`. Folder changes (projects opening or closing, `rootsChanged` storms like a Gradle sync) coalesce: 200 ms after a burst pauses, 1 s after it began at most. Startup sweeps the lock, temp file and sockets of every dead pid whose lock reads (`LockFile.cleanStale`); a live pid's lock stays, even malformed.
- **Retry and repair lock writes as `agent-hub-host`** (its AGENTS.md, Lock file). A Windows move over a held lock is retried after each of `lockRenameDelaysMs` (10, 20, 40, 80, 160 ms). A write still failing logs once, and a repair after `lockRepairMs` (1 s), doubling to `lockRepairMaxMs` (30 s) while repairs fail, runs `apply` and a rewrite, listening again unless serving or off. `FILE_FLAG_FIRST_PIPE_INSTANCE` rebinds the name while an agent holds the stopped pipe (measured 2026-09-27 with Node's; `agent-hub-host`'s AGENTS.md, Failure handling). `DocumentHub.kt` gives the timer's cancellation and the warnings.
- **POSIX liveness is libc's `kill(pid, 0)`.** Pids outside `1..Int.MAX_VALUE` are dead unasked, on Windows too; any refusal, `EPERM` too, is dead, as in Node. `kill` is a JNA `Function`, since a plugin `Library` would stay in JNA's option maps. A binding throwable other than `IllegalArgumentException` moves this JVM to `ProcessHandle.of(pid).isAlive`, logged once, so broken JNA never sweeps live locks.
- **Windows liveness is `WindowsProcess.query`.** It follows `agent-hub-host`'s rule (its AGENTS.md, Process liveness; exit codes in `WindowsProcess.kt`), except that an exited process a handle still holds is dead. Never `ProcessHandle` on Windows, whose extra `0x40` (`PROCESS_DUP_HANDLE`) no-write-up refuses an unelevated IDE on an elevated window: the sweep deleted that live lock. A query throwable makes this JVM keep every lock, logged once, since a `ProcessHandle` fallback would delete that lock again.
- **Real paths match Node's.** POSIX: `toRealPath()` plus the missing tail, never Unicode-normalized, `ENOTDIR` as Node's (JBR 21 reports it, JBR 25 a missing entry). Windows: `WindowsRealPath`, libuv's final path, because `toRealPath` keeps a `subst` or mapped letter the MCP server resolves; `MachineEnvironment.kt` gives the fallbacks. A path of 260 characters or more goes unprefixed to `toRealPath` and keeps that letter, so an agent finds no lock for it and edits it on disk under an editor.
- **Refuse unsafe names before any realpath.** `Authz.authorizePath` refuses `BAD_REQUEST` (`HubTexts.unsafeName`) a name `HubPaths.unsafeSegment` flags, on the target and the real path, as `authz.ts`. So the unprefixed `CreateFile` never opens a device, stream or Win32-trimmed name; it once resolved `notes.txt:x.erd` and `NUL.erd` (`agent-hub`'s AGENTS.md says why every side refuses). `HubPaths` trims spaces only and matches without `UNICODE_CASE`; `WindowsMachineTest` meets a real stream.

### Hub Documents And Lifecycle

- **Where no hub runs.** `AgentHubService` starts with the first project or ERD editor (listeners start nothing) and always builds the registry. It builds no hub (no lock, socket or sweep) when, in order: JCEF is unsupported (`JBCefApp.isSupported()` false or a `LinkageError`, optional from 2026.2); the IDE is headless; unit-test mode; a Linux Flatpak (`FLATPAK_ID`, `/.flatpak-info`), whose pids name nothing outside. The settings page says why; a failed build reads `the document hub could not start (idea.log has the error)`.
- **Read trust per request.** One lock covers trusted and untrusted projects. Untrusted-only paths (`TrustSnapshot.kt`, failing closed while a project opens or closes) are refused `hubDisabled` by `openDocument`, `applyActions` and `save`, answered from disk by `join` and listed `readonly`. A path only the lock lists reads no trust in those four, but `listDocuments` marks it `readonly` inside an untrusted project and no trusted one, so for up to 1 s after one opens, its open diagram lists `readonly` yet takes writes.
- **Register before the page loads.** The registry holds every local ERD file open in an editor, hub or not; `ErdEditor` posts `register` and `addView` before building `WebviewPanel`, whose page's first command must follow them.
- **Editor hooks.** `Initial` sends theme, language and read-only flag, reads the file via the VFS (no BOM), waits 1 s at most for the lock to list it (`awaitListed`) and posts `onViewReady`; an unregistered editor sends its file's last runtime value, else the text. Focus calls `setActive`, so `active` follows focus, never an agent's open; a page load starting calls `onViewUnready`; `dispose` flushes, then `removeView`. `ErdEditor.kt` wires the rest.
- **`openInEditor` keeps one tab per file.** It takes the registered file, else the project tree's spelling (`spelledUnder`, over `HubPaths.longestPrefixIndex` and `toSegments`, which the corpus holds), else the real path, as VS Code's `openDocument` does (`packages/vscode-extension/AGENTS.md`). It opens in the project already showing it, else the deepest holder, else the last focused (`IntelliJIdeFacade.kt`). The VFS keys by path, so a project opened via a `subst` or mapped drive, symlink or junction gave a second `VirtualFile` (two ids on 2026.1.4, 2026-09-27), tab and entry. `openFile(vf, false)` takes no focus.
- **`listDocuments` order.** Open documents, writable first, then the projects' ERD files (`ProjectFileIndex.iterateContent`, no `node_modules`), each once by real path.
- **Renames, writability, deletes.** A local rename or move rereads every path: peers hear `documentClosed` under the old one, and the document is served under the new one, or let go once not an ERD file. `PROP_WRITABLE` pushes `readonly` to pages, closes the document for peers and wakes waits. A deleted file goes with its editors.
- **The hub's save.** It waits 2 s at most for the replicas, then writes the mirror through the first editor opened (`writeNow`), read inside the EDT write action so no older bytes overwrite an autosave. A document not `dirty` (no replica save owed, the mirror equal to the last write) answers `saved: true` unwritten, its bytes and byte order mark kept. `saved: false` is logged when replicas do not settle or the write fails or misses 10 s, unlogged when the file is invalid, read-only or editorless.
- **Project close revokes.** After each folders or documents lock write, every tracked (connection, path) the lock no longer admits hears `documentClosed`; a connection left with nothing, its closed paths all outside, is ended, so the MCP server falls back to the file. A path tracked after a revoke, authorized against the old scope, is checked against the revoke's and closed alike.
- **Shutdown order** (`HubRuntime.kt`, `DocumentHub.kt`).
  1. IDE exit: `appWillBeClosed`, before projects close, runs `shutdownPeers()` (EDT, 1.5 s at most), as the exit is not cancelled after it and the write-locked dispose may come seconds later. Host events are dropped, so closing projects rewrite no lock; peers hear `documentClosed` for every path; frames drain 1 s at most; `retire()` writes `hub: false`, `pipe` `""` and closes the pipe. Agents are refused `blocked` through an exit of seconds (about 8 s to dispose in the smoke; 2025.2 waits for indexing).
  2. `AgentHubService.dispose()` (EDT, about 3 s at most): remove the hook, `shutdownPeers()`, `hub.close(1 s)`, `threads.shutdown(500 ms)`. `hub.close` deletes the lock in time; late, `releaseSync` deletes it and logs `could not close the document hub`. No `erd-editor-hub-*` thread, hook or bus connection outside the service's `Disposable` survives.
  3. SIGTERM without dispose: the hook's `releaseSync()` deletes the lock, temp file and both socket paths.
  4. Coding agents off: `hub: false`, then the listener stops, without `documentClosed`, so agents are refused `blocked`, not sent to the file.

### Settings

- **Coding agents.** `AgentHubSettings` (`codingAgents`, default on, in `erd-editor.xml`) publishes `Listener.TOPIC` only on change and `loadState` nothing, so the host reads `isEnabled()` fresh.
- **Theme and display language.** `ErdEditorAppSettings` keeps both, default `auto`, sent as stored with what auto shows: `systemAppearance` (`!JBColor.isBright()`) and `systemLocale` (`DynamicBundle.getLocale()`, the IDE's UI language; English if unsupported). Updates publish only a change; `updateLocale` takes `auto` or one of `LocaleLabel`'s 25 codes exactly; unknown stored values read `auto`. Page picks arrive as is, System as `auto`, by the Obsidian plugin's rules (`ErdEditorTheme`, `ErdEditorLocale`). The old `dark` default was never written, a `PersistentStateComponent` storing no default value, so users who never picked get `auto`.
- **Re-send both on every change.** `onSettingsChange` re-sends theme and language on every publish and `LafManagerListener` event, since the builder can pick System any time.
- **The settings page.** `ErdEditorConfigurable` (Tools, `ERD Editor`) edits the theme's three fields, the Display language combo and Coding agents, with `Coding agents are unavailable: <reason>` from `AgentHubService.whyUnavailable()`, which starts nothing.

### Known Limitations

- **Remote development is undetectable.** No public API tells (a `remoteDevHost` start is not headless), so where JCEF works on a backend, the hub serves that machine's agents.
- **One frame can exhaust the heap.** A same-user process reaching the `0700` socket can send a frame under 64 MiB that Jackson's tree inflates past the IDE's heap (`[{},…]` with 22.4 million items ran `-Xmx2048m` out). Kept for parity: no hello deadline or connection cap.
- **Pipes take the default security descriptor**, as libuv. Another local user can hold read-only instances, a channel and io thread each, seeing nothing; an administrator IDE admits only elevated agents (`EPERM`). Kept, as in the TypeScript hubs (`agent-hub-host`'s AGENTS.md, Windows pipe security).
- **Outside changes are not reloaded.** A page reads its file once per load, so the next autosave overwrites an outside edit. The lock keeps agents off; with no hub (Flatpak, no JCEF), close the diagram before an agent edits it.
- **Rename to another extension and back.** Editors kept open serve the file unregistered, relaying among themselves; a new one joins from their last runtime value. Until all close, `openDocument` times out (`No ERD editor on … reported ready within 5000 ms`).
- **A second editor or reload can miss edits.** `onViewReady` waits 500 ms at most for replica saves, so a batch no save holds yet never reaches the page, as in the TypeScript join.
- **Two spellings no rule joins.** A link within a project opens under the target's spelling, a second tab as in VS Code. A file also reached through a loopback mapped drive (`N:` → `\\localhost\C$\…`) has two real paths: the lock keeps the project's, and the MCP server refuses the other `invalidPath` (`packages/mcp-server/AGENTS.md`).
- **A dynamic unload may keep the class loader.** The scheme handler factory stays on the global `CefApp`, which has only a global clear, and on Windows `Kernel32Ex` stays in JNA's option maps. Smoke B7 reports the loader apart from the hub.

### JCEF Gotchas

- **Depend on `com.intellij.modules.jcef` optionally** (`jcef.xml`): mandatory stops loading on 2025.2/2025.3, absent kills the editor on 2026.2+ (`NoClassDefFoundError: JBCefApp`), and the Verifier passes both. So `JBCefApp.isSupported()` is read in a `LinkageError` catch at construction, never class init.
- **Extend `CefResourceHandlerAdapter`.** 2026.2's JCEF added abstract methods to `CefResourceHandler`, breaking a direct implementation built against the floor.
- **Keep `WebviewPanel`'s init order.** `JBCefApp.getInstance()`, the scheme handler once per app, then `Webview` and `loadURL`: later registration gives `DNS_PROBE_FINISHED_NXDOMAIN`, raw `CefApp.getInstance()` first "JCEF is not supported in this env". Never call `CefApp.clearSchemeHandlerFactories()`. `WebviewPanel.kt` notes why its callbacks precede `webview`.
- **Route queries by sender.** Under out-of-process JCEF at 2025.2 the first `CefMessageRouter` hears every browser: a second tab's `Initial` reached the first, leaving it blank. So panels join the static `livePanels`, and `onQuery` hands each query to the live panel whose browser sent it, by `CefBrowser.identifier` (`WebviewPanelBrowserTest`).
- **A main-frame load empties the page.** `onLoadStart` fires on every load, the timeout page too (`html.editor.timeout`, 10 s), so the registry treats the page as empty until its next `Initial`.
- **Bind nothing to `Alt`+letter.** macOS `⌥`+letter arrives as a wrong `KeyboardEvent.code` (`KeyA`) and fires another shortcut. The keymap takes `⌘Z` / `⌘⇧Z` first; whether it takes `⌘F` / `Ctrl+F` is unchecked, since the smoke's CDP keys bypass it.
- **Clipboard export is unchecked in JCEF.** Whether JCEF accepts the export dialog's Copy to clipboard (an `image/png` `ClipboardItem` written inside the click) is unchecked, so the README's Export line leaves the clipboard out. Confirm it in `runIde` before the listing names it.

### Platform And JDK Gotchas

- **Use `Runtime.addShutdownHook`, removed in `dispose`.** Not `ShutDownTracker`: a leftover hook pins the class loader.
- **Disposed projects throw `ProcessCanceledException`** from services in a read action (`whileOpen` skips them); `Logger` refuses one, so `IdeHubLog` logs a detail.
- **JDK unix sockets differ from Node's.** They refuse an existing file, leave theirs and throw past `sun_path` where Node truncates; `LockPaths.pipePathFits` keeps such paths out.
- **Pipe handles are overlapped, via `Kernel32Ex`.** JNA's `Kernel32` (5.17) lacks `GetFinalPathNameByHandle`, `GetOverlappedResult` and `CancelIoEx`; a synchronous handle would stall notifications behind a read. `DisconnectNamedPipe` drops unread data, so handles are only closed. Pipe `destroy` and `close` block up to 1 s, `shutdownOutput` 2 s: io threads only.
- **Tests get the product's JVM arguments**, `jna.boot.library.path` too, so JNA loads in JUnit. They run on the platform's JBR (25 for 2026.1.4) with the coroutines debug agent, naming threads ` @coroutine#n`.
- **Clean up in `close` and `dispose`.** After `HubThreads.shutdown`, a coroutine's `finally` may never run.
- **Tell a held lock by exception class.** `LockFile`'s `refusedWhileHeld` checks the class, never the message. Windows `Files.move` with `ATOMIC_MOVE` throws `AccessDeniedException` for a held target and a `FileSystemException` with a localized reason (Korean on the measuring machine, 2026-09-27) for a held source. `Files.deleteIfExists` of a held lock succeeds.
